## HB-008 供应商超时，为什么不能随便再发一次？

### 现场问题

我们发出付费生成请求后没有收到回包。供应商可能已经开始生成。直接重试或直接退款，各能说明什么、又不能说明什么？

### 旧模型与反例

旧模型：“请求超时等于执行失败。”反例：供应商执行成功，只是响应丢失。另一个错误模型是“退款以后事情就结束了”；退款没有改变供应商实际执行状态。

### 基本事实与不变量

超时只说明本方没有及时拿到证据，不说明远端没执行。任务事实、证据状态、用户等待状态和账务状态要分开表达。一次业务意图必须保持稳定身份，不能为消除未知而制造第二次可能收费的意图。

### 推导与参考回答

保存原操作身份、执行上下文、受理与结果检查点。优先查询原任务或读取已存结果。确有同身份幂等/恢复协议时，按协议执行；上游既无幂等、又不能按原请求查询时，自动判定能力存在边界，应保留未知并对账或核查。

UNKNOWN 是本方知识不足的表达，不强制要求所有表都使用同名枚举；不能把它简化为普通失败，也不能无限无反馈地让用户等待。等待终止与业务定局是不同动作，产品应准确表达。

参考表达：“我先问超时发生在哪条边界，系统已保存什么证据。原身份不能丢。查询可以有界重试；再次发送外部操作要由协议的幂等保证决定，不能以重试次数固定为三次替代正确性判断。”

### L1—L4 追问

- **L1**：没拿到供应商 task ID 能证明未受理吗？要点：不能，ID 的回包也可能丢失。
- **L2**：幂等键怎样定义？要点：绑定原业务意图与作用域；同键不同输入不能悄悄视为同一个正确请求。
- **L3**：POST 能否再次发送？要点：不能一概禁止或一概重试，要看同身份、参数冻结、状态域与上游协议保证。
- **L4**：怎样向用户和运营交代？要点：明确观察不足、等待处理与账务事实，有核查路径与责任，不伪造“供应商已取消”。

### 项目证据与验证

源码：[`DurableImageJobs.paidOperation`](../../../src/lib/durable-image-jobs.ts) 中已有结果复用、已开始检查点、受理身份与网关恢复判断；[`holdImageJobBilling`](../../../src/lib/image-job-repository.ts) 中账务保留与执行权检查。

本基线的恢复逻辑比旧工作区更完整，教学不把某个 HTTP 状态码机械解释为“任何供应商都确定未受理”。错误含义需要具体协议与适配器证据。

验证设想：请求未送达、受理后丢回包、结果保存失败、网关状态域变化、凭据或模型映射改变、原检查点已完成，以及重复回执。检查外部调用身份与次数，不只检查最终页面成功。

### 边界与待追问

本地事务和租约都不能凭空提供跨供应商的恰好一次执行。前置：HB-002、HB-007。后续：HB-009、HB-011。学习状态：未评估。

## HB-009 任务已经完成，页面为什么还卡在 99%？

### 现场问题

服务器记录已完成、作品已保存，页面却持续显示 99%。这能否证明生成失败或扣费错误？

### 旧模型与反例

旧模型：“页面状态就是任务事实。”反例：查询回执挂起，前端再也没收到 done；进度动画只是估计，不是供应商真实百分比。

### 基本事实与不变量

执行完成、结果落库、回执送达、页面渲染是不同步骤。前端停止等待不能自动取消供应商；GET 失败不能自动授权新的生成 POST。

### 推导与参考回答

为单次回执读取设置覆盖响应头与响应体的期限，同时保留整个轮询生命周期的退出条件。传输失败后，在原任务、原账号和原工作空间下继续有界读取；切换上下文后不能把旧结果写到新画布。

参考表达：“我沿结果链分段查：执行、存储、回执、前端。若是回执失联，修复观察路径并读取原任务，而不是重新生成。超时保护要覆盖 response.text()，否则 headers 成功、body 挂起仍会卡住。”

### L1—L4 追问

- **L1**：动画 99% 说明什么？要点：只能说明 UI 估计状态，不能单独证明远端进度。
- **L2**：总体六分钟 deadline 为什么仍可能不够？要点：若只在每轮请求前判断，一次无期限 await 就能越过截止时间。
- **L3**：fetch 已返回 headers、body 不结束呢？要点：同一取消信号与期限覆盖完整体读取。
- **L4**：如何验证实际用户路径？要点：覆盖真实调用循环、上下文变化和重载恢复，不只测试独立 helper。

### 项目证据与验证

源码：[`readCanvasGenerationReceipt`](../../../src/lib/canvas/generation-receipt.ts) 以同一 AbortController 覆盖 fetch 与 `response.text()`，传输异常返回 null；调用方保留原任务轮询语义。历史实现与验证见[回执轮询修复记录](../../changes/2026-10-30-enterprise-pool-deadlock-fix.md)。

最新 [`imagegen/client.ts`](../../../src/lib/imagegen/client.ts) 有独立提交与轮询接口。不要把旧版 `startImagegen` 的 catch 后查询实现原样声称为当前入口；要核对当前调用链。

### 边界与待追问

结束前端等待不是供应商取消成功，退款也不是未受理证明。前置：HB-001、HB-008。后续：HB-010。学习状态：未评估。
