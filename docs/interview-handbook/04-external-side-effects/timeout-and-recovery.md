## HB-008 供应商超时，为什么不能随便再发一次？

### 现场问题

我们发出付费生成请求后没有收到回包。供应商可能已经开始生成。直接重试或直接退款，各能说明什么、又不能说明什么？

### 旧模型与反例

旧模型：“请求超时等于执行失败。”反例：供应商执行成功，只是响应丢失。另一个错误模型是“退款以后事情就结束了”；退款没有改变供应商实际执行状态。

### 基本事实与不变量

超时只说明本方没有及时拿到证据，不说明远端没执行。任务事实、证据状态、用户等待状态和账务状态要分开表达。一次业务意图必须保持稳定身份，不能为消除未知而制造第二次可能收费的意图。

### 推导与参考回答

#### 直接回答

**答案：** 超时首先是观察失败，不是远端执行失败。我们应保留原操作身份、冻结的输入与报价、已有受理证据和结果检查点，先查询原任务，再根据供应商或网关的协议决定如何恢复。没有充分证据时保留 UNKNOWN，并提供可追踪的核查流程。退款是账务决策，不是供应商停止生成的证明；再次发送不同身份的请求，则可能制造第二笔付费工作。

UNKNOWN 表达“本方尚无足够证据”，不要求所有表都使用同名枚举。执行状态、证据状态、用户等待状态与账务状态可以分别是“远端实际完成但本方未知”“页面已结束等待”“积分仍预占”。这些组合需要核查与对账，不能简单压成一个失败标签。

#### 从事实推导

1. 网络只能传递消息，消息可能在请求到达前或响应返回时丢失，因此同一个超时对应多种远端事实。
2. 原身份能把后续查询与原业务意图关联起来；换新身份就失去去重与核对依据。
3. 本地记录 `started` 只能证明曾准备或可能发起调用，不能独立证明供应商已受理，也不能证明未受理。
4. 本地数据库回滚不能撤销远端生成；恢复必须使用远端支持的身份、幂等和查询能力。
5. 用户体验需要明确的等待结束与处理进度，但不能通过虚构“已取消”来消除产品上的不确定感。

#### 示例与落地

以下是教学时序，不是本轮实测：`t0` 保存操作 O 与冻结参数；`t1` 发送 O；`t2` 供应商受理；`t3` 回包丢失；`t4` 本方超时。正确恢复首先读取 O 的检查点和原受理身份。如果查询返回原任务结果，就保存与交付原结果；如果协议明确证明 O 未受理，才按该协议决定重新发起；如果查询不可用或身份缺失，保留待核查，不自动改成 O2。

教学决策可写成：`有已存结果 → 复用；有原任务身份 → 有界查询；有同身份幂等恢复契约 → 按契约恢复；否则 → 保留未知并核查`。所有分支都要保留原操作与账务关联。

#### 面试表达

“我不会看到超时就固定重试三次，因为超时没有告诉我远端是否执行。我先检查原操作身份、输入冻结和受理检查点，再优先查询原任务。若网关保证同身份去重，恢复可以再次发送协议允许的请求；若上游不支持，就不能承诺自动恢复一定成功。账务、等待和执行分开处理：页面可以结束等待，但不能因此宣布供应商取消；释放积分也不能证明远端没发生。最后用原身份对账，并验证受理后丢回包、结果落库失败和配置变化这些边界。”

### L1—L4 追问

#### L1 解释：没拿到供应商 task ID 能证明未受理吗？

**答案：** 不能。供应商可能先创建任务，再把 task ID 放进响应；如果响应在途中丢失，本方看不到 ID，但远端任务已经存在。还要区分“请求明确没有发出”“请求可能发出”“供应商明确拒绝”和“已接受但回包遗失”。没有 ID 只说明缺少一种查询凭据，不是未执行证据。接下来应查已保存的操作身份、网关受理记录及协议支持的查询入口；如果仍不能确认，就保留未知，不把本地缺行或错误日志当成远端未发生的证明。

#### L2 推导：幂等键怎样定义？

**答案：** 幂等键应对应一次稳定的业务意图，并有明确的账号、租户、操作类型和状态域作用范围。用户对同一次提交的网络重试继续用原键，主动发起新的创作才使用新键。服务端还要把关键输入、模型、报价或执行版本绑定到该键：同键但参数不同，应明确冲突或按既定冻结规则处理，不能随机采用后来的参数。键的保留期必须覆盖合理恢复窗口；跨网关、跨数据库或更换状态域后，原键是否仍有去重意义，要由协议重新确认。

#### L3 变式：POST 能否再次发送？

**答案：** HTTP 方法本身不能决定业务是否可重试。若上游明确保证同键、同参数、同状态域下只执行一次，重发原 POST 可能正是协议规定的恢复方式；若它只提供任务 ID 查询，就应查原任务而不是新建。若无法证明请求未发出，又没有幂等契约，自动再发可能重复付费。即便协议支持，也要核对去重有效期、输入冻结、凭据与状态域一致性，并区分重试查询、重试准入和重试实际业务。不能把任意 POST 禁令或统一三次重试当作设计结论。

#### L4 负责：怎样向用户和运营交代？

**答案：** 对用户明确表达“本次暂未取得结果、正在核查”等已知事实，并分别说明等待是否结束、积分是否预占或已释放、结果后续从哪里查看。对运营提供原任务身份、受理证据、最后确认时间、账务金额、核查负责人和下一步，不暴露凭据。设定核查与沟通时限，但不要把时限当作远端自动失败的证据。若业务选择先补偿用户，应记录补偿依据与后续对账责任，而不是声称供应商已经取消。交代的核心是事实一致、身份连续、有人跟进，而非用确定口气掩盖未知。

### 常见误区

- “数据库没查到 task ID，所以可以重发”：把本地证据缺失错误地等同于远端未受理。
- “退款就说明任务取消了”：混淆账务动作与外部执行事实。
- “加了幂等键就绝对恰好一次”：未核实键的作用域、保留期及供应商是否真正执行该契约。

### 跨业务迁移

电商支付请求超时同样要按原交易号查询，避免重复支付；但资金清算、撤销和退款协议需要支付域专门处理。社交推送超时也存在“可能已送达”，只是重复通知的代价通常不同，可以按业务选择允许补发或去重展示。共同原理是信息不足不等于未执行，具体恢复策略取决于副作用成本与外部协议。

### 项目证据与验证

源码：[`DurableImageJobs.paidOperation`](../../../src/lib/durable-image-jobs.ts) 中已有结果复用、已开始检查点、受理身份与网关恢复判断；[`holdImageJobBilling`](../../../src/lib/image-job-repository.ts) 中账务保留与执行权检查。

本基线的恢复逻辑比旧工作区更完整，教学不把某个 HTTP 状态码机械解释为“任何供应商都确定未受理”。错误含义需要具体协议与适配器证据。

验证设想：请求未送达、受理后丢回包、结果保存失败、网关状态域变化、凭据或模型映射改变、原检查点已完成，以及重复回执。检查外部调用身份与次数，不只检查最终页面成功。

### 边界与待追问

本地事务和租约都不能凭空提供跨供应商的恰好一次执行。前置：HB-002、HB-007。后续：HB-009、HB-011。学习状态：未评估。

## HB-009 任务已经完成，页面为什么还卡在 99%？

### 现场问题

服务器记录已完成、作品已保存，页面却持续显示 99%。这能否证明生成失败或扣费错误？

### 旧模型与反例

旧模型：“页面状态就是任务事实。”反例：查询回执挂起，前端再也没收到 done；进度动画只是估计，不是供应商真实百分比。

### 基本事实与不变量

执行完成、结果落库、回执送达、页面渲染是不同步骤。前端停止等待不能自动取消供应商；GET 失败不能自动授权新的生成 POST。

### 推导与参考回答

#### 直接回答

**答案：** 不能仅凭页面 99% 判定生成失败或扣费错误。要沿“供应商执行 → 结果保存 → 回执查询 → 页面落位”分段定位。若任务与作品已经完成，但查询挂住，问题发生在观察链路。应修复回执读取、继续查询原任务，并保护原账号和工作空间上下文，而不是重新提交付费生成。

需要同时设置两类期限：单次请求期限限制一次等待，总体期限限制整个轮询会话。单次期限必须覆盖 headers 与完整 body；总体退出还包括账号、项目、工作空间切换。前端结束等待，只是停止本次观察，不代表供应商取消。

#### 从事实推导

1. 结果先完成、页面后得知，这两个事件之间可能存在网络、数据库或前端错误。
2. 进度动画通常按时间估计，不能作为供应商事实来源，99% 也可能只是动画上限。
3. 总体期限若只在请求前检查，一次永远不返回的 await 会阻止程序进入下一轮检查。
4. 因而单次 I/O 需要可中断边界，且响应体消费必须属于同一次受期限保护的操作。
5. 异步结果还要绑定提交时的上下文，避免旧任务写进当前新账号或新画布。

#### 示例与落地

教学时序：任务 J 已完成且作品存在；浏览器发 GET 查询 J；服务端返回 headers 后 body 停滞。只包住 `fetch()` 的定时器若在 headers 后被清除，`response.text()` 仍可永久挂起。正确做法是同一 AbortController 覆盖 fetch 和 body，完成解析或异常后才在 finally 清理计时器。

一次传输失败后，调用方在原总体截止时间和上下文仍有效的前提下继续读 J；已到截止则结束前台等待并保留恢复入口。该教学流程不改变 J 的业务身份，也不发送第二次生成 POST。

#### 面试表达

“我先区分任务事实和 UI 观察。99% 只是页面估计，先查原任务、作品和账务，再看回执与前端。如果结果已存，我修复的是观察通道，不是让用户再生成。实现上把单次 deadline 覆盖到 response.text()，同时保留总体期限与上下文退出。验证不仅测 helper，还模拟 headers 挂起、body 挂起、网络错误、pending、done 和切换账号，确认真实轮询仍读同一任务，且旧结果不会落到新画布。”

### L1—L4 追问

#### L1 解释：动画 99% 说明什么？

**答案：** 它首先说明前端处于某种估计或等待状态。若进度值是按经过时间计算的，它没有观测供应商内部实际完成度，因此不能据此认定“图片已生成 99%”或“最后一步一定在存图”。应查询原任务状态、检查作品与结果对象，再核对最后一次成功回执及渲染。界面可以用估计动画改善等待体验，但应避免把模拟百分比展示为精确业务事实。反过来，即使页面显示错误，已保存结果和实际账务也可能正常，必须分轴核对。

#### L2 推导：总体六分钟 deadline 为什么仍可能不够？

**答案：** 假设循环在发 GET 前检查“现在是否超过六分钟”，随后执行一个没有超时的 await。若第一次 GET 或 body 读取永远不结束，循环便永远走不到第二次时间检查，总体期限形同虚设。因此总体期限要配合单次 I/O 期限，必要时用剩余总时长收紧本次允许等待。还要注意失败后的退避与间隔也消耗总预算。总期限结束只决定当前观察会话何时退出，不负责判定供应商失败或改变账务，原任务身份仍应保存以便后续恢复。

#### L3 变式：fetch 已返回 headers，body 不结束呢？

**答案：** fetch 的 Promise 通常在响应头可用时即可完成，`response.text()` 或 JSON 消费还可能继续等待。若一拿到 Response 就清除定时器，保护范围只覆盖了半次读取。应把同一个 AbortSignal 传给 fetch，并让期限一直有效到 body 消费与必要解析结束，再在 finally 清理。还要区分传输超时、非成功 HTTP 响应、无效 JSON 和任务终态错误，不能把它们全部吞成“稍后重试”。只读传输失败可按既定策略继续原任务查询，不能因此新建生成任务。

#### L4 负责：如何验证实际用户路径？

**答案：** 先对 helper 验证 headers 挂起、body 挂起、异常清理和定时器释放，再覆盖真正调用它的轮询循环。让一次会话依次经历超时、网络错误、pending 和 done，检查查询身份始终相同、间隔与总期限没有被重置，也没有第二个生成 POST。再测账号/项目切换、关闭重开和结果落位，确认旧会话不能污染新上下文。最后在实际候选版本检查作品可见与账务一致；本地 mock 的成功不能替代部署验收，而浏览器动画正常也不能替代持久结果检查。

### 常见误区

- “总超时有六分钟，所以任意单次请求都能等”：漏掉无法返回循环的 await。
- “fetch 返回了，所以网络读取已经结束”：忽略响应体仍在消费。
- “页面停止等待就是取消成功”：把观察行为误认为外部执行控制。

### 跨业务迁移

电商“支付成功但订单页仍待支付”也要区分交易事实与展示回执，不能因为页面没更新再扣一次钱。社交“发帖已成功但信息流没刷新”可能来自缓存、异步分发或读模型延迟，而非写入失败。共同点是分段核对链路；差异在于支付不能随意补发，部分社交展示则允许短时最终一致，但权限可见性仍需严格处理。
