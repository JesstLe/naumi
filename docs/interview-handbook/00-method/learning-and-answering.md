## 1. 第一性原理：先约束，后工具

先拿掉 Redis、MQ、微服务等名词，回答五个问题。以下附 Naumi 的示范回答，不需要先猜标准术语：

1. **用户到底希望完成什么？** 答案：用户希望把已有商品素材和创作意图转成可用作品，而不是希望“成功调用一次模型 API”。因此提交、等待、结果保存、再次找到作品及正确计费都属于业务完成条件。一个上游 200 不足以代表用户拿到了结果。
2. **哪些事实已经发生，哪些只是观察到的现象？** 答案：页面超时是本方的观察，供应商受理、图片生成和账务扣款是需要各自证据的事实。要沿原任务身份核对记录与回执，不能用“没看到成功”推导“对方没有执行”。
3. **哪些结果绝对不能被破坏？** 答案：同一业务意图不能因盲目重试制造重复付费；任务、作品与账务必须保持真实归属；明确已提交的本地事实不能因后续日志失败被改写成未发生。具体不变量要落到可核验字段与写入条件，而不只说“稳定可靠”。
4. **什么资源有限，什么参与者可能独立失败？** 答案：连接、CPU、内存、存储、供应商并发与费用都有上限；浏览器、Web、Worker、数据库和供应商可能在不同时间失联。即便应用只有一台服务器，也必须处理外部系统独立失败和回包丢失。
5. **用最少机制怎样维持约束，什么证据能检验？** 答案：同库任务与预占用共享事务，多执行者用共同状态和原子领取，外部调用用原身份与检查点。验证要在保存前后、受理前后、提交回包前后注入不同故障，检查原身份、结果和账务，而不只看最终页面能否刷新。

例子：供应商调用很慢，不必然推出“加 Redis”。若问题是请求生命周期过短，先需要持久任务；若问题是执行到达率超过服务能力，先需要容量控制、排队或增加有效处理能力；若问题是多实例各自计数，才需要共享准入状态。

## 2. 发生认识论：让反例推动模型升级

这里借用“同化—顺应—重新平衡”的认识发生思路，是教学组织方法，不声称它是某种软件架构定理。

- **旧模型**：我在进程里加了全局 Map，所以所有请求共享计数。
- **反例**：启动第二个进程，两边各放行一次。
- **认知冲突**：“全局”究竟指模块、进程，还是整个业务系统？
- **新模型**：共享范围要明确；跨执行者的准入需要共同状态和原子更新。
- **再次检验**：共享存储故障了怎么办？多个实例是否连接同一状态域？

**对应答案：** 共享存储故障要按业务契约明确返回基础设施不可用或采用事先约定的降级，不能悄悄改成本地计数后继续承诺全局限流。实例是否共享，要核对数据库/schema、key 构造、密钥与版本；两个进程都写 SQL 不代表它们一定写在同一个状态域。用并发同 key 的实验和实际配置确认，不能从代码名称猜结论。

每次问答都尽量留下“旧认识—反例—修正后认识”，而不只记最终术语。

## 3. 分级追问与判断标准

### 3.1 L1：解释

能用自己的话说清现象，不用另一个陌生术语替代解释。例如“租约”不只解释为“分布式锁”，而是有期限的执行权。

### 3.2 L2：推导

能从约束得到方案。例如任务创建与预占要一起成功，因而同库场景采用共享事务；不是只说“事务保证 ACID”。

### 3.3 L3：变式

能处理条件变化。例如租约过期后旧执行者恢复、响应头返回但响应体挂住、COMMIT 已成功但回包丢失。

### 3.4 L4：负责

能说明替代方案、成本、观测、验证与恢复。能明确哪部分结论来自源码、哪部分已经实测、哪部分仍未知。

**等级不是职级映射。** L4 是本题回答要求，不表示已经具备某家公司的某个职级。

## 4. 通用回答骨架

> 在【业务场景】里，我们观察到【具体症状】。原先假设是【旧模型】，但【证据】排除了它。真正约束是【资源/一致性/故障边界】，必须保持【不变量】。我们比较【方案 A/B】，选择【方案】并实现【关键机制】。通过【验证】证明了【范围内结果】；【未验证范围】仍需进一步验收。恢复采用【方式】，不会破坏【业务事实】。

如果只是读过本项目，使用“项目记录显示”“我的设计判断是”，不要使用“我当时主导”“我解决了某次线上事故”。

## 5. 技术负责人的连续八问与示范回答

下面是项目已经介绍清楚后的一条深挖路线，不是要求面试一开场就进入事故。开场和过渡先按[完整流程](../00-interview-flow/README.md)进行。

### 5.1 现象是什么，影响范围和时间边界在哪里？

**示范答案：** 用具体接口、时间窗口、用户群体、实例和耗时描述，不只说“系统卡”。例如案例分析可以说版本接口正常、依赖数据库的登录与回执超时，并确认它们是否走同一实例。这样建立正常对照和共同依赖；不能从一条 200 推导整个网络、所有实例都正常。

### 5.2 你最初的解释是什么？

**示范答案：** 先列可检验假设：数据库慢 SQL、锁等待、池队列、网络或页面处理分别会产生什么现象。每个假设要能被观测推翻，不把“高并发导致的”当解释，因为它没有说明哪个资源、谁占着、等待多久。复盘时诚实保留曾判断错误的路径。

### 5.3 什么证据支持或推翻它？

**示范答案：** 把应用池 total/idle/waiting、事务年龄、数据库锁与请求时间线关联起来。如果 SQL 本身很快，但请求长期卡在 checkout，“SQL 执行慢”就不是充分解释。若有跨层等待图，还要对应实际调用路径，单独看到五条连接用满不足以证明这个特定等待环。

### 5.4 必须保持什么业务不变量？

**示范答案：** 排障不能让未知付费任务被当成未受理重发，不能为了清理而丢失原身份，也不能覆盖用户数据。修复必须维持原账号归属、共享事务和幂等规则。不变量回答的是“我们可以怎样恢复”，不是故障结束后才补的检查清单。

### 5.5 为什么选这个方案，而不是更简单或不同的方案？

**示范答案：** 已确认事务内二次借池时，传递原连接、缩短事务持有范围比增加中间件更直接。扩池可以缓解容量，但不会删除错误等待关系；加缓存也未必覆盖这条授权素材链。若证据显示的其实是合法吞吐不足，则应承认需要重新测预算，而不是把所有扩容都贬为错误。

### 5.6 哪些故障它仍处理不了？

**示范答案：** 消除嵌套借池只关闭特定路径，不自动修复慢 SQL、泄漏、其他长事务或外部受理不确定性。租约校验保护经过检查的写入，不撤回旧进程已发出的网络请求。说清边界能够指导下一轮验证，也避免把一个局部修复宣传为整个系统已经可靠。

### 5.7 怎么验证，不同证据分别证明什么？

**示范答案：** 先稳定复现，再检查修改后原路径、并发、权限拒绝和错误恢复。fixture 证明其模拟端口和输入下的行为，真实数据库实验补充锁时序，运行版本证明部署对象，用户链路验收证明实际效果。不同证据互相补足，不能用脚本 exit 0 替代所有层次。

### 5.8 如果修坏了，怎样恢复并保护在途业务？

**示范答案：** 保留固定旧版本与兼容入口，按实际发布流程回退程序，核对进行中的会话、任务和租约。数据库和媒体不能简单回灌旧快照，否则会抹掉新产生的业务事实；原身份已接受或未知的付费操作也不能重新提交。恢复完成要核查实际版本、用户路径和账务，而不只看进程活着。

## 6. 学习状态怎么记录

“未评估”表示尚未看到实际回答。“已讨论”表示出现过自己的解释。“需巩固”要写具体误区。“可迁移”需要在至少一个变化场景下给出合理推导。这些都是学习记录，不是生产验收或职业能力认证。
