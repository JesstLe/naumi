# 00-01 学习方法与回答框架

[返回总目录](../README.md)

## 1. 第一性原理：先约束，后工具

先拿掉 Redis、MQ、微服务等名词，回答五个问题：

1. 用户到底希望完成什么？
2. 哪些事实已经发生，哪些只是我们观察到的现象？
3. 哪些结果绝对不能被破坏？
4. 什么资源有限，什么参与者可能独立失败？
5. 用最少机制怎样维持这些约束？什么证据能检验它？

例子：供应商调用很慢，不必然推出“加 Redis”。若问题是请求生命周期过短，先需要持久任务；若问题是执行到达率超过服务能力，先需要容量控制、排队或增加有效处理能力；若问题是多实例各自计数，才需要共享准入状态。

## 2. 发生认识论：让反例推动模型升级

这里借用“同化—顺应—重新平衡”的认识发生思路，是教学组织方法，不声称它是某种软件架构定理。

- **旧模型**：我在进程里加了全局 Map，所以所有请求共享计数。
- **反例**：启动第二个进程，两边各放行一次。
- **认知冲突**：“全局”究竟指模块、进程，还是整个业务系统？
- **新模型**：共享范围要明确；跨执行者的准入需要共同状态和原子更新。
- **再次检验**：共享存储故障了怎么办？多个实例是否连接同一状态域？

每次问答都尽量留下“旧认识—反例—修正后认识”，而不只记最终术语。

## 3. 分级追问与判断标准

### 3.1 L1：解释

能用自己的话说清现象，不用另一个陌生术语替代解释。例如“租约”不只解释为“分布式锁”，而是有期限的执行权。

### 3.2 L2：推导

能从约束得到方案。例如任务创建与预占要一起成功，因而同库场景采用共享事务；不是只说“事务保证 ACID”。

### 3.3 L3：变式

能处理条件变化。例如租约过期后旧执行者恢复、响应头返回但响应体挂住、COMMIT 已成功但回包丢失。

### 3.4 L4：负责

能说明替代方案、成本、观测、验证与恢复。能明确哪部分结论来自源码、哪部分已经实测、哪部分仍未知。

**等级不是职级映射。** L4 是本题回答要求，不表示已经具备某家公司的某个职级。

## 4. 通用回答骨架

> 在【业务场景】里，我们观察到【具体症状】。原先假设是【旧模型】，但【证据】排除了它。真正约束是【资源/一致性/故障边界】，必须保持【不变量】。我们比较【方案 A/B】，选择【方案】并实现【关键机制】。通过【验证】证明了【范围内结果】；【未验证范围】仍需进一步验收。恢复采用【方式】，不会破坏【业务事实】。

如果只是读过本项目，使用“项目记录显示”“我的设计判断是”，不要使用“我当时主导”“我解决了某次线上事故”。

## 5. 技术负责人的连续八问

1. 现象是什么，影响范围和时间边界在哪里？
2. 你最初的解释是什么？
3. 什么证据支持或推翻它？
4. 必须保持什么业务不变量？
5. 为什么选这个方案，而不是更简单或不同的方案？
6. 哪些故障它仍处理不了？
7. 怎么验证，不同证据分别证明什么？
8. 如果修坏了，怎样恢复并保护在途业务？

## 6. 学习状态怎么记录

“未评估”表示尚未看到实际回答。“已讨论”表示出现过自己的解释。“需巩固”要写具体误区。“可迁移”需要在至少一个变化场景下给出合理推导。这些都是学习记录，不是生产验收或职业能力认证。
