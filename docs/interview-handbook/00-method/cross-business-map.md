# 00-02 跨业务迁移：共同原理，不同约束

[返回总目录](../README.md)

## 1. 核心命题

中大型在线业务常常共享一组工程问题，但不能简化为“所有中大厂本质上只是高并发应用”。高并发只是规模维度之一；复杂权限、资金正确性、海量存储、低延迟、合规隔离、成本和组织协作也可能是主导约束。

面试中的共同部分，来自有限资源、并发操作、独立失败、信息不完整和持续变化。这些约束比某一种中间件更基础。

## 2. 把业务名词翻译为工程约束

下表是教学映射，不声称业务完全等价，也不是各平台实际架构的调查结论。

| 共同问题 | 电商场景 | 社交场景 | Naumi 场景 |
|---|---|---|---|
| 一次意图被重复提交 | 重复下单、支付回调 | 重复发帖、重复通知 | 重复生图、重复结算 |
| 有限资源的竞争 | 库存、优惠券、支付通道 | 写入能力、热点分发能力 | 余额、Worker、供应商并发 |
| 操作与观察不一致 | 支付成功但订单仍待支付 | 发帖成功但信息流尚未可见 | 图片完成但回执没有到页面 |
| 多执行者协作 | 订单消费者抢单 | 分发消费者处理事件 | 多 Worker 领取任务 |
| 外部副作用不确定 | 支付请求超时 | 外部推送请求无回包 | 供应商可能受理但回包丢失 |
| 大负载和元数据混用 | 大附件与订单状态混存 | 视频字节与帖子索引混存 | 图片字节与任务快照混存 |
| 持续更新时的连续性 | 在途交易不被切断 | 长连接、消息游标连续 | Agent/SSE、生成任务与旧资源兼容 |

## 3. 同一原理，不等于相同容错策略

### 3.1 电商和支付

余额、库存、订单状态有严格正确性要求。支付是否成功不能凭客户端动画判定；状态不明时通常需要原交易身份查询和对账。

### 3.2 社交平台

内容写入、可见性、通知、点赞计数是不同事实。一些展示计数允许短时陈旧，但权限、私密内容可见性、删除和封禁不能因为“社交可以最终一致”就随意放宽。

### 3.3 AI 创作

长任务、外部付费调用、大媒体和账务同时存在。页面结束等待、任务执行停止、供应商取消成功、积分释放是不同事件。

## 4. 三个不要机械等同的类比

1. **预占积分类似冻结资金，但不等于商品库存。** 生命周期、退款依据和最终成本可能不同。
2. **一次生图类似一次履约，但不是普通短事务。** 外部生成不能被本地数据库 ROLLBACK 撤销。
3. **重复消息与重复业务效果相关，但不是一回事。** 可以允许投递重复，再用业务键保护结果；有些外部系统缺少幂等协议，边界必须单独说明。

## 5. 换场景练习

先回答 HB-008 的供应商超时，再把它改成“支付网关超时”；保留证据与原身份原则，重新说明资金处理。再改成“推送平台超时”；重新评估重复通知的代价、是否可以补发及用户体验。

判断标准：能保留共同原理，也能解释不同业务的正确性、延迟与成本取舍。只把“图片”替换成“订单”不算迁移成功。

### 5.1 支付网关超时的参考答案

**答案：** 先保留原交易号、订单和金额，明确“本方超时”不等于“支付未发生”。按网关协议查询原交易、接收幂等回调并对账；用户端避免把支付未知立即展示为肯定失败后诱导再次支付。若协议支持同交易号幂等恢复，按其约束处理，不能随意换交易号再扣一次。账户记账、订单状态和渠道状态分别核对，退款同样有独立身份和结果，不是点一次按钮就证明完成。

与 Naumi 相同的是原身份、证据和外部副作用原则；不同的是资金到账、订单履约与退款规则。不能把生成任务的积分释放条件机械当作支付网关的退款依据，也不能把某个非成功 HTTP 状态码当作通用的未扣款证明。

### 5.2 推送平台超时的参考答案

**答案：** 先看业务是否允许重复通知。普通提醒可能在受控去重、次数与时间窗内补发，但重要安全通知、验证码或财务提醒有不同代价，不能说“社交消息重复无所谓”。若平台支持消息 ID 查询或幂等发送，沿原消息身份恢复；不支持时，在重复风险与漏送风险之间作显式选择，并记录未知投递状态。平台接受、设备到达、用户阅读是三层事实，即便拿到发送回执也不能宣称用户已读。

和付费生图相比，单次调用成本可能不同，但用户打扰、时效和隐私可见性可能成为主约束。迁移成功体现在重新评估代价，而不是所有超时都统一重试三次或统一等待人工核查。

## 6. 后续扩展方向

共同基础继续补充缓存、消息、热点、数据模型与可靠性；业务差异继续补充支付、内容分发、搜索和媒体处理。具体待补条目见[主题队列](../90-growth/backlog.md)。
