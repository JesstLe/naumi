## HB-017 你用了这些技术，关键基础原理怎么解释？

### 现场问题

面试官听完“前端 React、服务端 Node.js、数据库 PostgreSQL、后台执行生成任务”后问：“先聊基础。HTTP 请求和任务是什么关系？Node 的异步是不是多线程？事务、索引和缓存各解决什么？”这些是教学用问法，不是某家公司固定题单。

### 旧模型与反例

旧模型：“讲出框架和中间件名字，就说明掌握基础。”反例：知道 `async/await`，却把长时间 CPU 计算放进请求线程；知道事务，却误以为数据库回滚能撤销供应商生成；加了索引，却无法说明查询为何仍扫描大量数据。

### 基本事实与不变量

协议、运行时、存储和业务是不同层次。答案要解释各层的能力和边界，再说明调用链如何组合；既不把所有问题都归为业务状态机，也不脱离项目只背定义。

### 推导与参考回答

#### 直接回答

**答案：**我会沿一次请求解释基础：HTTP 传送提交或查询，应用代码解析和鉴权，运行时调度 I/O，数据库保证限定范围内的持久性与事务正确性，索引帮助定位数据，缓存减少重复取数。持久任务把长业务从某次连接中独立出来。这些机制各管一层，并不会互相替代。

**HTTP 与任务：**HTTP 是请求—响应协议。200 代表该接口按其契约成功响应；若接口返回“已受理”，它不等于图片已经完成。202 常用于表达已接受但尚未完成，但具体业务仍要看响应与接口契约。GET 查询和 POST 提交的重试代价不同；POST 是否可重试要看业务幂等协议，不能只依据方法名决定。

**异步、并发与并行：**`await` 等待 Promise 时，运行时可以让其他可推进的工作执行；它不把当前 JavaScript CPU 计算自动搬到另一个核心。一个 Node 进程通常由事件循环线程执行 JavaScript，网络 I/O 可以并发进行，部分原生任务会使用线程池；CPU 密集任务仍可能阻塞该事件循环。增加 Worker Thread、进程或独立执行服务是另一层选择，不是给函数加 `async` 就实现并行。

**进程与状态：**一个服务可以运行多个进程，每个进程有独立内存和故障生命周期。进程内的 Map 与 Symbol 状态不自动跨进程共享；共享数据库、任务身份和协调协议才让多个执行者协作。进程数量增加也会增加连接、内存与外部配额压力。

**事务原子性与隔离性：**原子性描述事务里的写入一起提交或回滚；隔离性描述多个事务并发时如何观察和影响彼此。一个业务使用了事务，仍可能出现不符合业务约束的并发结果，需要合适的行锁、唯一约束、条件更新或隔离等级。供应商执行不属于本地数据库事务。

**索引与缓存：**索引是帮助数据库按条件定位数据的结构；缓存保存可复用结果或数据副本。索引仍从数据库访问数据并有维护成本，缓存引入失效、陈旧与权限隔离问题。索引不等于缓存，缓存也不补偿错误的查询条件、事务规则或授权设计。

#### 从事实推导

1. 从用户动作开始区分“协议请求”和“需要履约的业务”，避免把接口响应当成任务最终结果。
2. 从等待和计算开始区分异步并发与 CPU 并行，判断到底该减少阻塞、增加执行者还是优化算法。
3. 从一个执行者扩到多个，检查内存、连接、身份和共享状态的作用域。
4. 从一条 SQL 扩到多个并发事务，分别检查本地原子提交、业务不变量与读写竞争。
5. 最后根据查询和复用模式选择索引或缓存，测量效果并接受对应维护成本。

#### 示例与落地

教学对话：“你为什么不在 POST 里一直等图？”回答：“因为生成可能跨连接超时或进程重启，所以 POST 提交持久任务，用户按原任务读取状态。它解释了业务异步，不意味着 Node 用多核执行图像计算。”

教学时序：A、B 都读到余额 10，各准备消费 8。即使各自的“扣款与流水”放在事务里，如果没有正确的并发控制，两边仍可能基于相同旧余额作决定。原子性保证各自事务内部一致，跨事务的余量竞争还需要条件扣减、锁或其他正确协议。这里是推理示例，不是在宣称当前项目存在该缺陷。

#### 面试表达（约90秒）

“我通常沿调用链解释基础，而不只列技术栈。HTTP 负责传送提交和查询，接口受理不等于生成完成；长任务要有独立身份。Node 的异步主要让 I/O 等待期间可以推进其他请求，不会把同步 CPU 工作自动并行化。多进程可以扩执行者，但内存状态和连接预算要重新检查。数据库方面，我会把原子性和隔离性分开：一个事务内部一起提交，不代表多个事务间没有竞争。性能上，索引解决定位，缓存解决重复访问，两者成本不同。我再用这些基础解释项目为何需要持久任务、共享领取和短事务，而不是先背一个固定架构。”

### L1—L4 追问

#### L1 解释：Node 是单线程，为什么还能处理很多请求？

**答案：**“单线程”通常指一个事件循环线程执行 JavaScript，并非进程内所有工作都只有一个线程。大量请求常在等网络或磁盘，并不一直消耗 CPU；非阻塞 I/O 让等待期间可以处理其他事件。部分原生计算或文件操作还会交给底层线程池。并发因此可以很高，但一个长时间同步循环仍会阻塞同一事件循环。判断瓶颈时要看 CPU、事件循环延迟、原生线程池与 I/O，而不是把“异步”直接当成无限处理能力。

#### L2 推导：有事务为什么还会余额竞争，怎样选隔离与约束？

**答案：**事务原子性保护本事务内的一组修改，余量竞争涉及多个事务观察同一资源。先写出“不超额消费、同业务只记一次”的不变量，再让条件更新、唯一约束或锁在数据库权威状态上执行。隔离等级可以改变异常出现的条件，但更高等级也可能增加等待或序列化失败，需要明确重试整个事务的条件。外部付费请求不应塞进可重试事务里，否则事务重试可能重复产生副作用。要依据真实 SQL 和并发时序选择，而非统一回答“开最高隔离”。

#### L3 变式：加了索引仍很慢，要直接加缓存吗？

**答案：**先确认查询条件是否能利用索引、选择性与返回行宽、排序分页方式、锁等待，以及连接是否花在排队而非执行。即便走索引，返回大量大字段或随机 I/O 仍可能很贵；缓存命中率低也不会消除首次查询成本。只有读多、结果可复用且允许明确陈旧窗口时，缓存才可能收益明显。还要设计权限维度、失效与击穿保护。这个顺序不是永远反对缓存，而是先知道慢在哪、复用什么，再用实测解释缓存的收益。

#### L4 负责：面试官连续问你不熟悉的底层细节，怎么回答？

**答案：**先明确自己能确认的机制，再界定待核细节。例如能解释事件循环与 CPU 阻塞，但对某个 Node 版本下某 API 的线程池实现不确定，就把判断限定在已核范围，并说明准备查官方实现或做什么隔离实验。接着回到工程决策：不同实现会如何影响并发预算、延迟和恢复。这样既不以“项目能跑”逃避基础，也不现场编造运行时行为。面试官看的是知识、推理和边界意识；临时猜一个确定答案反而会破坏后续所有推导。

### 常见误区

- “加 `async` 就能多核并行”：同步计算仍在当前执行线程，是否并行要看实际调度机制。
- “事务保证一切正确”：需要分别讨论原子性、隔离、约束和外部副作用。
- “索引、缓存都只是让查询变快”：定位结构和可复用副本有不同一致性、成本与失效问题。
- “一个服务器就不是分布式”：接入供应商、对象存储等独立失败组件以后，已经需要处理跨边界不确定性。

### 跨业务迁移

电商的提交订单与查询订单、社交的发帖与信息流可见、Naumi 的提交生成与查询作品，都需要区分接口响应和后续业务状态。但支付余额、私密内容权限和展示计数的正确性要求不同。基础原理可以复用，陈旧窗口与失败策略要按业务分别定义。

### 项目证据与验证

源码入口：[`readCanvasGenerationReceipt`](../../../src/lib/canvas/generation-receipt.ts)、[`createImageJob`](../../../src/lib/image-job-repository.ts)、[`databasePoolBudget`](../../../src/lib/db/connection.ts)、[`rateLimit`](../../../src/lib/rate-limit.ts)。它们分别提供协议观察、事务、进程预算和共享状态的项目落点。本题运行时与数据库段落是基础原理解释，不是本轮性能测试；具体 Node/PG 版本、SQL 计划和部署结构以实际验证为准。

这是从项目进入基础的入口，不声称覆盖网络、操作系统与数据库所有知识。深入时分别接 HB-002、HB-003、HB-005、HB-009；没有实际答题记录前，学习状态：未评估。

## HB-018 为什么这样选型，不直接上 Redis、消息队列和微服务？

### 现场问题

面试官问：“你说面向更大规模，为什么任务和共享限流还用数据库？为什么没把生成、账务、媒体都拆成微服务？是不是项目还不够成熟？”

### 旧模型与反例

旧模型：“使用的中间件越多，架构级别越高。”反例：加一个服务就增加部署、权限、网络失败、状态同步和监控成本；不明确事务边界就拆服务，原本同库的一致性问题可能变成难以恢复的跨系统问题。反过来，永久拒绝增加服务也可能把真实瓶颈留在原地。

### 基本事实与不变量

选型服务于具体约束，而不是证明技术标签。要同时比较正确性、吞吐延迟、成本、成熟能力、故障行为与演进代价。模块边界、进程边界和部署边界不是同一件事；模块化单体也可以有独立 Worker。

### 推导与参考回答

#### 直接回答

**答案：**先明确当前问题需要什么能力，再解释现有方案是否满足、代价在哪、什么证据会触发升级。Naumi 这一基线复用 PostgreSQL 做持久任务与配置数据库时的共享限流，具备现成存储与事务能力；这不是证明数据库在任何流量下都最优。Redis、消息队列和微服务分别补充不同能力，不是同一条从低级到高级的升级阶梯。

Redis 可以承担低延迟共享状态或缓存，但仍需定义数据丢失、原子性、故障与恢复；它不自动保证账务正确。消息队列可以承担持久投递、消费者解耦和积压管理，但重复消费、事务内写事件和业务幂等仍要设计。微服务适合真实独立部署、隔离或伸缩边界，但把函数改成 HTTP 不会自动增加容量。

#### 从事实推导

1. 写出业务不变量：任务可恢复、执行权明确、账务一致、外部请求身份连续。
2. 明确负载与瓶颈：任务到达率、活跃 key、连接持有时长、热点、长尾和供应商配额；没有实测时保持假设。
3. 比较已有能力：复用 PG 的短事务和持久记录，通常比立即引入全新状态系统更容易维护，但要预算数据库竞争。
4. 比较新增收益与代价：若共享准入压垮数据库，就评估迁移准入层；若媒体处理需要独立伸缩，就评估执行隔离；不要整套替换所有模块。
5. 设计可退出的迁移：保留稳定业务身份、参数语义、错误分类和双版本兼容，迁移不是重新定义业务规则。

#### 示例与落地

教学决策记录可以写成：“当前选择 PG 共享限流，依据是已具备同一数据库状态域与短事务能力；待验证风险是热点 key 锁竞争和业务池等待。若实测准入层成为延迟与连接瓶颈，则对比 Redis 脚本或统一网关，要求保持原窗口语义，并有故障策略、迁移历史和回退方案。”这是一份决策模板，不是宣称线上已经触发该迁移。

再如拆分任务：入口先持久接受任务，独立 Worker 执行生成，已经能让请求处理与耗时工作分离。是否进一步拆成独立服务，需要看是否存在独立资源预算、发布节奏或扩缩容收益；无需为了“微服务”把账务写入拆成不能共享事务的远程调用。

#### 面试表达（约90秒）

“我的选型不是从中间件清单出发，而是先列正确性和资源约束。这个基线已有 PG，因此持久任务、本地事务和共享限流可以复用成熟能力，减少多一套状态与运维成本。同时我不会说数据库能扛任何规模，热点、连接与尾延迟都需要测。Redis 主要是共享状态或缓存选项，MQ 是投递与解耦选项，微服务是独立部署与隔离选项；它们解决的问题不同。如果测到某层成为瓶颈，我会把那一层迁移出去，保持身份、幂等和事务不变量，而不是因为面试希望听见某个名字就全盘拆分。”

### L1—L4 追问

#### L1 解释：数据库任务表和消息队列有什么区别？

**答案：**数据库任务表可以让任务与本地业务状态共享事务，并按条件领取、记录进度和恢复；成熟消息系统通常在投递、消费者协调、积压、广播或分区顺序方面提供专门能力。它们有重叠，但不完全替代。使用队列还要处理“数据库提交但消息未发出”的一致性窗口，常见做法之一是事务 outbox，再幂等投递和消费。使用任务表则要自己治理扫描、索引、并发和历史数据。选哪种取决于能力需求，而不是哪一种听起来更分布式。

#### L2 推导：为什么模块拆分不必立刻变成微服务？

**答案：**模块解决职责、依赖和变化范围；服务增加独立部署、网络边界和运行隔离。先把账务规则集中在明确接口，任务模块通过同一事务调用它，就能改善边界而保留本地原子性。若仅因文件很大就拆为远程服务，会新增超时和未知状态，却没有必然吞吐收益。当某模块确有独立伸缩、资源隔离、团队发布或稳定性需求时，再评估服务化及数据归属。架构成熟度体现在边界与证据，而非进程数。

#### L3 变式：流量增长后现有 PG 限流真的成为瓶颈，怎样迁移？

**答案：**先确定瓶颈来自准入记录而非其他 SQL，测量 key 热点、锁等待、延迟和池竞争。迁移前固定 key、窗口边界、跨实例状态域和故障错误语义，对目标方案做等价性与容量测试。过渡期要处理已有窗口历史，避免新旧各发一份额度；也要规划存储故障和回退，避免回退到独立 Map 后悄悄超放。切换验证看的是全局准入结果与业务影响，不只是 Redis 返回成功；本题没有宣称当前项目已做这次迁移。

#### L4 负责：团队有人坚持“中大厂都这样做”，怎样推进决策？

**答案：**把分歧转成可检验的决策记录：目标、候选方案、负载假设、不变量、成本、风险、验收门槛和回退方式。先用小范围实验比较延迟、吞吐、恢复复杂度与维护成本，记录哪些结论仍未验证。复用成熟方案有价值，但其他公司的工作负载与团队能力不自动适用于当前项目。最终选择要能说明为什么此时值得做、谁负责、怎样退出，而不是以保守或激进给方案贴标签。真实证据变化时，也应允许修订选择。

### 常见误区

- “没用 Redis 就没有分布式能力”：PG 或统一网关也可以提供共享状态与原子协议，具体边界仍要验证。
- “有 MQ 就不会丢任务、不会重复”：写事件窗口、投递和消费语义、业务幂等需要分别设计。
- “微服务能解决一切高并发”：共享数据库和供应商瓶颈可能没有变化，网络与运维成本却增加了。
- “复用现有能力就是永久不升级”：正确的决定包含适用条件和升级信号，而不是承诺当前方案永远合适。

### 跨业务迁移

电商订单更看重交易与库存不变量，社交内容分发可能更需要大规模扇出与消费者解耦，Naumi 需要长任务与付费受理身份。相同工具可能适合不同环节，但选型依据要换成各自的负载、正确性和延迟目标，不能只把“订单”替换为“图片”。
