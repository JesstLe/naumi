# 项目开场：概述、架构与本人贡献

[返回总目录](../README.md)

本章承接自我介绍和简单交流，先建立“项目是什么、怎么工作、本人做什么”的共同背景，再进入实际故障、并发与一致性的深挖。代码能证明仓库有什么实现，不能单独证明某个学习者亲自完成过什么。

## HB-015 请用两三分钟介绍一下 Naumi 项目

### 现场问题

面试官从背景交流转向项目：“刚才提到 Naumi，你简单介绍一下，主要解决什么问题，整体怎么做的？”对方此时需要项目地图，而不是从某次数据库故障开始听起。

### 旧模型与反例

教学用旧模型：“介绍项目就是把功能菜单和技术栈列全。”反例：面试官知道它有画布、批量和 Agent，却仍不知道用户完成一次任务要经过哪些模块，也无法选择下一步问题。

### 基本事实与不变量

项目概述需要同时回答产品目标、主路径、核心模块、主要约束和个人范围。功能存在不等于某实例启用并验收；技术选择不等于个人职责；目标规模不等于已经达到的容量。两三分钟应给结构化地图，具体参数、SQL 和事故细节留作后续展开。

### 推导与参考回答

#### 直接回答

**答案：**Naumi 是面向电商视觉创作的 AI 工作站，把参考素材、提示词、画布、创作 Agent、生成任务和作品管理放进一个工作流。介绍时用一次付费生图作主线：用户组织输入，服务端校验归属与模型能力并冻结执行上下文，持久保存任务与应有预占，执行通道领取并调用供应商，随后保存结果、处理结算，再向用户交付回执。围绕这条路径解释前端、服务端、数据库、执行者和媒体存储的职责，比逐个念页面更清楚。

仓库以 React/Next.js 构建交互和 Web 服务，Node.js 环境承载服务端逻辑，PostgreSQL 保存任务与账务等结构化事实，并与供应商、媒体存储及 Worker 通道协作。具体运行实例和供应商能力需要单独核查，不把仓库结构直接说成当前所有站点的部署图。

#### 从事实推导

1. 用户目标是完成并复用视觉创作，不是单纯“调用一次模型 API”。
2. 抓住输入到交付的一条主链，面试官才能理解各模块为什么存在。
3. 长生成与外部付费使请求、任务、回执和账务具有不同生命周期，因此要说明持久事实和边界。
4. 技术按职责出现：React 负责交互，Web 负责协议与编排，数据库负责本地事实，执行通道负责生成推进，存储负责媒体字节。
5. 在概述结尾交代本人真实范围，再给一到两个可选深挖点，让面试官顺着追问。

#### 示例与落地

**教学用两三分钟项目概述，不包含个人经历断言：**

> Naumi 服务电商视觉创作，用户可以在画布、批量工作台或者 Agent 中整理商品参考图、描述和生成结果，最后保存或导出作品。它的主要价值是把素材组织、生成和后续编辑放进连续工作流，而不是让用户在多个分散工具间搬运内容。
>
> 技术上，仓库用 React/Next.js 组织界面与 Web 入口，后端围绕账号和素材归属、模型与报价、持久任务、供应商适配、媒体和账务分工。拿一次付费生图来说，提交以后先保存能够恢复的任务及上下文，再由执行通道推进生成；浏览器离开不意味着供应商取消。生成结果、账务处理和用户收到回执也要分别确认。
>
> 这类项目的难点不只在流量，还在长任务、外部副作用和用户观察状态之间的协调。可以继续展开两条线：一条是页面失联以后如何读取原任务，另一条是多执行者与数据库竞争时怎样保护任务和账务。至于我本人参与的部分，需要按【真实模块、动作和证据】补充，不能由项目整体能力代替个人贡献。

概述后，面试官可能追问“为什么不直接同步生成”“数据库保存什么”“你负责哪个模块”；分别转向 HB-001、HB-002 与 HB-016，再进入故障深挖。

#### 面试表达（约90秒）

“Naumi 是电商视觉创作工作站，核心不是一个出图按钮，而是素材、画布、Agent、任务与作品组成的工作流。以付费生图为例，服务端校验输入和归属、冻结执行上下文、保存任务与应有预占，再由执行通道调用供应商，保存结果、处理结算并返回回执。仓库主要使用 React/Next.js、Node.js 和 PostgreSQL，并适配外部生成与媒体存储。我会把它的工程约束概括为长任务、付费副作用、媒体体量和状态恢复，具体个人职责按实际参与记录说明。”这段是项目概述示范，不是个人工作履历。

### L1—L4 追问

#### L1 解释：这个项目和普通的模型 API 包装器有什么区别？

**答案：**直接包装 API 通常只负责转发输入和返回结果，而完整工作站还需要组织创作上下文、检查素材和账号归属、管理任务生命周期、保存作品、处理团队访问以及账务。Naumi 的生成可能跨越浏览器连接和 Web 进程生命周期，结果也可能先完成、后交付回执，因此需要持久状态和恢复机制。区别不是页面数量或代码量，而是用户工作流与系统责任扩大了；也不能因为责任多就认为每项能力在所有实例都已完成验收。

#### L2 推导：为什么项目介绍最好围绕一条主链，而不是功能列表？

**答案：**主链能够把用户目标、模块协作、状态归属和设计约束放在同一个时间顺序里。听者知道任务从哪里进入、哪些事实需要保存、外部调用在哪里发生、结果怎样交付，才有依据判断后续并发、事务和恢复问题。功能列表适合说明产品范围，却很难证明技术理解；可以先用一句话列出画布、Agent 和批量等入口，再用一次生图讲清共同底座，避免每个入口重复解释一遍。

#### L3 变式：面试官问“你们支持多少用户、QPS 和并发”，怎么回答？

**答案：**先区分产品目标和测量结果，再区分活跃用户、峰值在线、API 请求速率、生成到达率与在途生成并发。仓库规则中的十万＋活跃用户是建设目标，不应回答成已经支持十万并发。若有真实压测，提供日期、版本、工作负载、资源规格、延迟和错误率；若没有对应证据，就说明尚未核实该指标，并解释要怎样测量。仅有池大小、某次健康 200 或少数生成成功，都不足以推导整站容量。

#### L4 负责：概述里怎样解释技术选型，而不是说“这些技术热门”？

**答案：**把技术放回职责和约束：界面需要复杂状态与交互，Web 需要明确协议入口与业务编排，本地任务与账务需要事务和持久查询，外部媒体需要适合大字节对象的存储。再说明已有能力与维护成本，避免为名称增加新组件。例如本手册基线的共享限流使用 PostgreSQL，不能为了显得高并发就说项目上了 Redis。具体是否替换某技术，要由负载、故障、成本和团队维护能力支持，而不是技术流行程度。

### 常见误区

- **把宏观架构画成所有站点的当前运行事实。** 仓库实现、部署规则、实际镜像和真实验收分别核查。
- **从一开始只讲事故。** 先让面试官理解用户路径和模块关系，故障才有发生背景。
- **把技术名词当作设计理由。** 说明该组件承担的状态与失败责任，才能解释它为什么在这里。

### 跨业务迁移

电商项目可用“选品—下单—支付—履约—退款”作主链，社交项目可用“发布—持久化—审核/权限—分发—用户可见”作主链；介绍方法相同，业务事实不同。Naumi 的供应商付费生成不能被简单替换成订单数据库写入，社交展示计数的短时陈旧也不能直接迁移到余额或权限判断。

### 项目证据与验证

产品范围见[项目 README](../../../README.md)，依赖见[package.json](../../../package.json)；任务创建与预占见[`createImageJob`](../../../src/lib/image-job-repository.ts)，执行并发与派发见[`image-job-queue.ts`](../../../src/lib/image-job-queue.ts)，持久付费检查点见[`durable-image-jobs.ts`](../../../src/lib/durable-image-jobs.ts)。本题按仓库结构介绍，未核查任何服务器当下的版本与吞吐。

### 边界与待追问

项目概述负责建立背景，不替代完整部署图、容量报告或个人贡献证明。前置：HB-013、HB-014。后续：HB-016、HB-001、HB-003。学习状态：未评估。

## HB-016 你本人具体负责什么，贡献怎样证明？

### 现场问题

面试官听完项目介绍后问：“这个系统里你自己做了哪些部分？哪些设计是你决定的？怎么证明效果？”这是从项目整体能力转向个人能力的关键步骤。

### 旧模型与反例

教学用旧模型：“项目是我的，所以里面的能力都可以算我的贡献。”反例：面试官进一步问某个设计的替代方案、验证命令和上线结果，候选人只能复述文档，无法说明自己当时的动作。

### 基本事实与不变量

读懂、动手执行、参与设计和承担结果是不同层次；团队成果可以介绍，但个人贡献必须有明确边界。工具或 AI 辅助不自动取消贡献，也不自动证明使用者理解全部实现。个人贡献的证据应同时回答做了什么、为什么做、怎样验证和留下了什么未完成项。

### 推导与参考回答

#### 直接回答

**答案：**使用“范围—动作—决策—验证—边界”的结构。先说本人负责哪一个模块或业务切片，再说具体修改与协作方式，区分自己提出并比较过的方案、按既定方案执行的工作，以及只是学习或审阅的部分。结果给可追溯证据：提交差异、评审记录、定向测试、构建与部署身份、实际验收或复盘；没有指标就不给提升百分比。个人职责尚未确认时，先给可填写模板和学习分析版，不能替用户生成主导事故、容量优化或上线经历。

#### 从事实推导

1. 面试官招聘个人，需要知道可独立完成的范围，而不是项目功能总表。
2. 职责边界先限定问题对象，例如任务回执读取，而不是笼统“负责稳定性”。
3. 具体动作把参与变成可核查事实；决策说明理解了为什么这样做。
4. 验证证据连接动作和结果，避免把代码合并误写成生产效果。
5. 未完成项与协作边界说明结果责任没有被夸大，也为后续追问提供诚实入口。

#### 示例与落地

**待填写的真实开发贡献模板：**

> 我在 Naumi 中实际负责【模块或业务切片】，相关入口是【接口/页面】，主要依赖【模块】。这次工作最初要解决【可观测问题】，我完成了【自己的具体动作】。方案上我比较过【真实替代方案】，选择【实际方案】是因为【约束】。验证使用【命令/用例/环境】，能证明【限定结果】；【部署或线上部分】由【实际协作者/实际状态】负责，目前还有【未完成项】。

**仅做学习分析时的示范：**

> 我目前对这个项目的贡献主要是【已经完成的阅读、梳理或文档动作】，并没有证据把某次历史线上修复说成本人执行。我可以解释任务创建与预占的事务边界，也能分析旧执行者恢复为什么需要执行权校验；如果继续追问实现，我会按源码说明已核对部分，并把设计推演和实际改动分开。

方括号不能被自动填成“独立负责全部”“吞吐提升十倍”等未经提供的内容。读者可以用自己的真实工作替换，再由面试官沿代码、时间线和验证继续核查。

#### 面试表达（约90秒）

“我先把项目整体与个人范围分开。整体包含【产品链路】，我实际负责【明确范围】，最能说明我工作的例子是【真实切片】。我具体做了【动作】，在【约束】下选择【方案】，用【验证】确认【结果边界】。其中【另一部分】是已有能力或他人负责，我目前主要了解其接口；【尚未完成部分】仍未验收。”这是待填模板。若没有真实开发参与，改用学习分析身份，不把理解能力伪装成执行或上线经验。

### L1—L4 追问

#### L1 解释：“读过、执行、设计、负责”有什么区别？

**答案：**读过表示能解释已有实现和证据；执行表示实际完成过明确动作并有产物；设计表示参与提出机制、比较方案并做出选择；负责还要包含推进、验证、处理失败和交代结果边界。这些层次可以重叠，但不能互相自动推出。读懂恢复代码不等于亲自处置过线上恢复，跑过脚本也不等于决定了恢复策略。回答时用准确动词和实例，让面试官知道下一步应该核查理解、操作还是决策能力。

#### L2 推导：一个提交或一张截图足以证明贡献和结果吗？

**答案：**提交可以证明某些代码变更存在，但不直接证明作者理解全部设计，也不证明已经发布；截图可以证明某时某界面状态，却未必证明任务、账务或并发行为正确。更完整的证据链包括问题背景、相关差异、个人决策、用例与实际输出、固定构建和运行身份，以及受影响链路验收。并非每个小改动都需要所有层次，但声称的结果必须由相应层次的证据支持，不能拿一个局部产物替代整个闭环。

#### L3 变式：使用 AI 或团队协作后，怎样描述自己的贡献？

**答案：**说明分工和自己真正承担的判断：谁提出目标，谁生成或实现代码，自己怎样核对约束、审查差异、设计验证并处理失败。AI 辅助产生代码并不自动等于使用者没有贡献，但如果不能解释接口、状态和测试边界，也不能把全部技术决策归于自己。团队场景同样如此：可以介绍共同成果，再把自己的模块和协作接口说清楚。面试官通常会通过变化条件追问，检验你是否拥有超出复述的理解和推进能力。

#### L4 负责：如果个人负责模块上线后出了问题，回答应体现什么？

**答案：**先明确用户影响和当前业务事实，再区分止血、回退、根因修复和最终验收。说明自己如何收集证据、协调相关模块、保护在途任务与账务，并留下未完成项，而不是只说“我修好了”。如果并非亲历，就作为假设场景回答，不编造过去的操作。负责人视角不是保证永远不出错，而是在不确定性下作出有依据的决策，并对验证范围、恢复结果和后续预防负责。

### 常见误区

- **把“我们”永远替代“我”。** 共同成果可以归团队，但要补本人动作，不能让面试官猜贡献比例。
- **把文档结论复制成履历。** 能讲清历史案例是学习成果，亲自执行过的事故处理是另一种事实。
- **只报结果，不说验证层次。** 合并、部署和用户验收要分别陈述，尤其不能由测试通过推导线上已经稳定。

### 跨业务迁移

电商项目的“负责支付回调”需要说明是接口实现、账务设计还是生产值守；社交项目的“负责信息流”需要说明是排序、分发、存储还是客户端展示。贡献结构可以共用，但指标与正确性标准不能共用：退款准确、内容可见性和生图恢复各有自己的验收对象。本人范围越清楚，跨业务追问越容易检验真正可迁移的能力。

### 项目证据与验证

项目能力可参考[项目 README](../../../README.md) 与[验证和叙事章节](../05-engineering/verification-and-narrative.md)。个人贡献要另用真实提交、评审、模块记录和实际验收建立证据链；这些材料未由本题替学习者生成。本轮仅编写面试教学文档，没有新的个人生产经历或容量结果。
