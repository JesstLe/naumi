## HB-005 扩成两个实例后，内存限流为什么失效？

### 现场问题

教学假设：每个用户每分钟最多 10 次。单实例的 Map 计数正常，两个实例轮流接请求后，全局总次数可能超过 10 次。问题在哪里？

### 旧模型与反例

旧模型：“全局变量就是整个系统共享。”反例：模块级全局、进程级全局和跨进程共享是不同范围。即便同一进程，独立 bundle 也需要注意状态复用。

### 基本事实与不变量

如果业务定义全局限制，多个执行者要共享准入历史，并原子地判断与记录。仅把数据搬到共享存储，若仍先读后写，也可能并发超放。

### 推导与参考回答

#### 直接回答

**答案：**内存限流的计数归属于进程，而业务限制通常归属于账号、接口或整站。两个实例各保存一份 Map，就会各自发放一份额度；要执行全局限制，需要多个实例共同访问同一个状态域，并把“检查余量、记录本次命中”作为原子操作。Redis 是一种实现工具，不是这个问题的定义。**Naumi 本手册基线在配置数据库时采用 PostgreSQL 共享滑窗；无数据库配置时才使用本地 Map，数据库故障时不会静默切回本地。**

#### 从事实推导

1. 先定义限制对象：是每个账号、每个 IP、每个模型，还是整站？“每分钟十次”还缺少 key、窗口边界和跨实例范围。
2. 再明确内存边界：模块全局只在某个模块实例内有效；进程级 Symbol 可以复用同进程状态，仍不会把不同进程的内存连起来。
3. 多实例读取共同历史还不够。最后一个名额如果被两边同时读到，两边仍可能放行，所以检查与消费需要同一原子协议。
4. 共享存储引入新的依赖。配额用完和存储故障是不同事实，应有不同错误语义；否则用户和运维会把系统不可用误认为用户操作过频。
5. 最后才选实现：既有数据库短事务、Redis 脚本或统一网关均可比较。关注延迟、热点、连接竞争、运维成本和故障代价，而非“规模大就必须 Redis”。

#### 示例与落地

教学时序：同一窗口内已经放行 9 次，额度为 10。A 读取 9，B 也读取 9；若各自判断后写入 10，实际放行两次，但最终计数仍可能只是 10。共享数据并未消除先读后写的竞争窗口。

教学伪代码如下，不是将当前滑窗实现替换为计数器：

```text
atomic_admit(key, window, limit):
    在同一原子边界里读取该窗口历史
    若有效命中已达上限，返回 quota_exhausted
    否则记录本次命中并返回 admitted
```

Naumi 当前 PostgreSQL 实现按 key 取得行锁后读取数据库时钟，再计算和更新窗口历史。不同实例还要连接同一数据库/schema，并使用一致的 key 派生契约，才是在操作同一份限流状态。

#### 面试表达（约90秒）

“我会先确认业务要求是实例内保护还是全局准入。原来的 Map 对单进程成立，扩容后每个进程各自计数，额度就被复制了。修复的核心是共享状态和原子消费，不是 Redis 这个产品名。Naumi 复用了 PostgreSQL 的短事务和行锁，并区分额度耗尽与共享存储故障。如果后续证明热点和数据库竞争成为瓶颈，再考虑迁移；迁移要保留窗口、key、时钟和失败语义，不能只做到命令执行成功。”

### L1—L4 追问

#### L1 解释：两个 Map 为什么不共享？

**答案：**A、B 是两个独立进程，各有自己的地址空间。A 对 Map 的修改只改变 A 内存中的对象，B 没有收到复制或共享内存协议，自然仍读到自己的旧值。即使代码文件相同、容器镜像相同、进程启动在同一台机器上，也不会自动共享 JavaScript 对象。还要区分同进程多 bundle：用进程级状态可以避免一部分重复模块实例，但作用域仍只是该进程。判断“全局”的第一步，就是问清究竟跨模块、跨进程还是跨站点。

#### L2 推导：为什么共享存储仍要原子性？

**答案：**共享存储解决“大家看到同一份数据”，原子性解决“并发操作怎样合法地改变它”。当只剩一个名额时，A、B 可能都在对方写入前读取到有余量，随后同时放行。两次独立 GET/SET，或者事务外 SELECT 再 UPDATE，都可能留下这个窗口。应让判断与记录在同一个受保护操作里完成，例如条件更新、行锁短事务或 Redis 脚本。原子范围还必须覆盖真实算法所需状态：滑窗历史和过期清理的语义，通常比一个自增计数器更复杂。

#### L3 变式：共享存储挂了怎么办？

**答案：**先依据业务代价决定失败策略，并把它写成明确契约。昂贵付费操作通常不宜在准入状态未知时悄悄无限放行；低风险读取可能有不同选择。Naumi 当前实现区分配额耗尽和存储不可用：前者是限额判定，后者抛出专门错误，由调用方映射基础设施故障，而非退回各实例 Map。静默本地回退会在扩容时复制额度，故障期间改变业务保证。还要限制等待、释放迟到连接、避免故障引发重试风暴，并确认业务工作尚未开始。

#### L4 负责：什么时候才值得换成 Redis？

**答案：**当实测表明现有 PostgreSQL 限流在目标负载下产生不可接受的延迟、同 key 锁竞争、连接池挤占或存储开销，而且优化现有实现仍不划算时，再评估迁移。Redis 可能提供更低延迟的原子计数或脚本执行，但也增加高可用、容量、持久性与故障恢复责任。迁移方案要验证同 key 路由、窗口边界、时钟、脚本原子范围和故障策略；灰度期间还要避免新旧状态各自发额度。数据库尚未成为瓶颈时，多一个服务可能只增加系统复杂度。

### 项目证据与验证

源码：[`rateLimit`](../../../src/lib/rate-limit.ts)、[`consumePostgresRateLimit`](../../../src/lib/rate-limit-store.ts)。当前实现使用同 key 行锁，在取得锁后读取数据库时钟，再判断窗口与更新命中。

历史实现与验证记录：[共享限流变更](../../changes/2026-10-29-capacity-distributed-rate-limit.md)。多个实例要连接相同 DB/schema 并满足同一密钥等配置契约；仅部署新版代码不足以证明共享状态域一致。

验证设想：多进程同时请求同一 key、窗口边界、不同窗口共用历史、数据库故障、迟到连接释放及调用方确实 await。具体业务阈值不是本题新增要求。

### 常见误区

- “上 Redis 就是分布式限流”：如果各实例 key 不同、连接不同状态域，或者分两条命令先判断后写入，仍可能失效。
- “存储错误等于用户超限”：二者的归因和恢复动作不同；把基础设施故障伪装成 429 会误导用户并掩盖容量问题。
- “限流通过就不用幂等”：限流按调用准入计数，业务幂等按原意图保护副作用，两者服务不同的不变量。

### 跨业务迁移

电商抢券需要共享额度与原子领取，但“每秒限流”和“券总库存扣减”仍是不同约束；通过限流不代表有库存。社交平台可以对发帖、点赞或搜索分别限流，热点账号与共享出口 IP 的公平性也不同。Naumi 的付费生图更关注供应商成本和既有受理身份；限流结果并不是供应商是否接受上一次请求的证明。

### 边界与待追问

限流只决定准入，不是业务幂等回执，也不证明供应商是否受理。按 IP 限流还可能影响共享出口用户，维度应按真实产品要求选择。前置：HB-003。后续：HB-006、HB-008。学习状态：未评估。
