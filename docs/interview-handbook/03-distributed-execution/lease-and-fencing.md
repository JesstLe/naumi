## HB-006 两个 Worker 同时抢到一单怎么办？

### 现场问题

A、B 同时扫描到同一条 pending 任务；两边都准备调用付费供应商。

### 旧模型与反例

旧模型：“先 SELECT 未处理，再 UPDATE 处理中。”反例：A、B 同时通过 SELECT，之后都认为自己有权执行。

### 基本事实与不变量

检查与领取必须原子完成；同一时刻有效执行权要有可核查的归属。类别级总并发也是共享约束，不能每实例各自计数后假装整站受控。

### 推导与参考回答

#### 直接回答

**答案：**把“任务符合领取条件”和“授予本次执行权”放进同一原子协议，只有成功返回执行凭据的 Worker 才推进业务。对同一任务需要防止双领取，对同一类别还需要协调全局并发额度；这两个约束不是同一把本地锁能保证的。Naumi 当前 claim 在数据库事务内取得类别级协调锁，再通过带状态、租约和活跃数量条件的 UPDATE 领取任务，返回新的随机 token。未领取成功属于正常竞争，不应因此新建一笔生图。

#### 从事实推导

1. 多个扫描器看到同一条 pending 记录是正常现象；“看见候选任务”不等于“获得执行授权”。
2. 单独 SELECT 只是观察。必须使用条件更新、受锁保护的事务或队列领取协议，在竞争中选出有效持有人。
3. 领取结果要有可核验凭据，例如当前 token 和期限。后续写入与续租必须绑定该凭据，而不是只相信调用方说自己领过。
4. 如果产品还要求某类任务整站最多执行 N 个，两个 Worker 领取不同任务也会竞争最后一个名额，因此类别配额的检查和分配也需协调。
5. 领取后不长期持有数据库事务。长任务靠租约、心跳和持久检查点继续运行，外部付费调用另外遵守原身份恢复协议。

#### 示例与落地

教学时序：同类任务上限为 5，目前活跃 4 个。A、B 即便领取不同任务，如果各自只看“还有一个名额”，仍可能把活跃数推成 6。类别级协调用于串行化这段短的准入判定，并非让整段图片生成都串行。

以下为缩写的教学伪 SQL，不是可替代现有生产函数的补丁：

```sql
BEGIN;
-- 按任务类别取得事务级协调锁。
-- 在同一协议内确认类别余量，并以条件更新授予任务租约。
UPDATE jobs
SET lease_token = :new_token, lease_until = :new_deadline
WHERE id = :id AND claim_conditions_hold
RETURNING id, lease_token, lease_until;
COMMIT;
```

真实实现还处理任务类别、终态、导入历史隔离和共享并发条件。领取失败或提交回执不明时，按原任务身份确认状态，不把调用异常自动当成“肯定没领到”。

#### 面试表达（约90秒）

“我先区分候选发现和执行授权。多个 Worker 扫到同一条任务没有问题，问题在于谁能原子地取得有效执行权。Naumi 在短事务里协调类别额度，并用条件更新写入租约和 token，只有成功领取的一方继续。领取后释放数据库连接，用心跳和持久检查点支持长任务。单任务防双领取与整类并发上限分别验证；领取正确也不等于上游付费调用天然恰好一次，后者仍需要原业务身份和协议保证。”

### L1—L4 追问

#### L1 解释：先读后写有什么竞争窗口？

**答案：**A 查询到任务未处理之后，调度器可能先运行 B；B 也查到未处理，然后两边分别写成处理中。普通更新都可能成功，因为更新条件没有重新判断执行权是否仍空闲。把 SELECT 和 UPDATE 写在同一个函数里，不会自动产生原子性；普通事务也不等于所有读取都串行。应让授予授权的数据库操作检查当前条件，并依据受影响行或返回凭据决定是否继续。SELECT 可以用于发现候选，但候选发现不应成为执行授权本身。

#### L2 推导：原子领取成功后应该保存和传递什么？

**答案：**至少需要稳定任务身份、本次执行凭据、有效期限，以及恢复所需的冻结输入或其引用。执行者后续续租、存检查点、结算时要携带当前凭据，由权威状态再次验证，而不是只在内存标记 `running=true`。凭据的作用是识别这一次授权，任务身份则识别同一个业务意图，两者不应混成每次重试都新建的 ID。还要保留已发生外部操作的检查点；否则新执行者即使合法接管，也可能因不知道旧副作用而重复提交供应商。

#### L3 变式：每实例并发上限为 5，三实例后整站仍是 5 吗？

**答案：**如果只是各进程的信号量或计数器，三实例合计可能执行到 15 个。是否错误取决于约束定义：保护各实例 CPU 的上限可以是局部的，保护供应商账号配额、整站成本或共享资源的上限通常需要全局协调。即使把活跃任务放进数据库，两个事务同时数到 4 后各领一个，仍会突破上限；计数和分配必须处于共同的并发控制协议。Naumi 用类别级事务协调锁保护领取过程，但所有参与者还必须遵循同一状态域和锁契约。

#### L4 负责：领取成功但执行者立刻退出，任务怎么办？

**答案：**永久 `locked=true` 会留下无人能继续的任务，所以执行权应有期限，并由存活执行者续租。恢复器在到期且满足领取规则时接管原任务，再读取原检查点判断下一步。如果退出发生在外部调用之前，可以按已确认未发生的进度继续；若调用可能已经发出，则先做原身份恢复或核查，不能仅凭租约到期重发。还要测试领取 COMMIT 成功但回包丢失的边界：新执行者需要查明授权和业务状态，而不是依靠客户端异常推断数据库未提交。

### 项目证据与验证

源码：[`claimImageJob`](../../../src/lib/image-job-repository.ts)、[`imageJobConcurrency`](../../../src/lib/image-job-queue.ts)。验证设想：并发 claim 仅有一个有效所有者，类别总额度不因实例数被重复计算。

### 常见误区

- “一个任务只会被扫描一次”：扫描可能重复，正确性应落在领取与后续授权校验，而不是寄希望于扫描去重。
- “单行原子更新就解决整站并发”：不同任务竞争同一全局名额时，单任务互斥不足以保护类别总上限。
- “抢锁失败就是任务失败”：大多只是其他执行者取得授权；错误地新建任务会把正常竞争变成重复业务。

### 跨业务迁移

电商订单消费者可以重复收到同一订单事件，但真正履约前要确认当前状态与业务幂等键；整仓发货能力又是独立的容量约束。社交分发 Worker 可以采用队列消费组、分区或数据库领取，但“消息分给谁”和“通知是否已经发送”仍要分开。Naumi 的特点是长任务和外部付费副作用，接管原任务时尤其要保留供应商受理身份。

### 边界与待追问

领取正确不等于外部副作用恰好一次。前置：HB-005。后续：HB-007、HB-008。学习状态：未评估。

## HB-007 旧 Worker 恢复后，为什么租约过期还不够？

### 现场问题

A 领取任务后卡住，租约过期，B 接管；A 随后恢复并准备写结果。允许谁写？

### 旧模型与反例

旧模型：“锁过期了，旧任务肯定停止了。”反例：锁存储只撤销执行权，不会自动终止旧进程或撤回已发出的网络请求。

### 基本事实与不变量

执行权是一份限时授权，不是进程存活证明。过期持有人不能覆盖新持有人的事实；心跳失败和任务最大耗时需要联动分析。

### 推导与参考回答

#### 直接回答

**答案：**租约过期只是撤销 A 的执行授权，并不会自动终止 A 的进程。A 卡顿恢复后仍可能继续运行，因此保存结果、续租和其他受保护写入必须再次核对当前 token 与有效期限；已确认失权的本地执行也应停止推进。Naumi 用当前持有人 token、数据库行锁后的实时租约检查以及本地失权状态隔离迟到执行者。该机制保护经过检查的操作，不会撤回 A 已经发出的供应商请求，外部副作用仍要依赖原身份和幂等协议。

#### 从事实推导

1. 永不失效的锁利于互斥，却会在持有人崩溃后阻碍恢复；可过期的租约解决“谁都无法继续”的活性问题。
2. 过期与进程死亡没有必然关系。长暂停、网络分区、数据库拥塞都可能导致 A 失权后还活着，于是接管与陈旧写隔离必须一起设计。
3. 执行 token 标识当前授权代次。新持有人取得不同 token 后，旧 token 的写入应由权威存储拒绝，本地失权标志则避免继续发起后续动作。
4. 时间判断要放在真正取得资源以后。SQL 等行锁时租约可能跨过截止点，PostgreSQL `now()` 又固定在事务起始时刻，因此关键租约校验使用取锁后的 `clock_timestamp()`。
5. 期限、心跳和重试要联动预算。租约可以短于总任务耗时，但续租必须留出暂停、网络、排队和长尾余量；一旦无法证明授权仍有效，就停止本次执行而不是靠迟到心跳复活。

#### 示例与落地

教学时序：A 获得 token-a，截止时刻为 120；A 在 100 时刻暂停，125 时 B 获得 token-b，130 时 A 恢复。此时即使 A 持有正确任务 ID，也不再拥有当前授权；它的 token-a 写入应被拒绝。

另一个教学时序：某事务在 110 时开始，等待行锁到 130 时才取得锁。若拿事务起点 110 判断截止点 120，会把过期授权看成有效。Naumi 的对应做法是先取任务行锁，再实时确认 token 与期限，更新检查点后还会再次检查。

这不是“从此所有效果都恰好一次”。若 A 在暂停前已经发出供应商请求，数据库后来拒绝它写入，不代表那个请求已经被取消。

#### 面试表达（约90秒）

“我把互斥、安全与可恢复分开。租约让崩溃任务以后能被接管，但它不会杀掉旧 Worker，所以后续副作用必须验证当前执行权。Naumi 在锁住任务行后，以实时数据库时钟核对 token 和期限，本地确认失权后永久停止这次执行。心跳可在最后已证明有效的期限内有界重试，迟到成功也不复活失权执行者。随机 token 的当前持有人校验不等同于所有外部资源都支持的单调 fencing 序号，更不等于供应商恰好执行一次。”

### L1—L4 追问

#### L1 解释：租约到期能证明 A 已经死亡吗？

**答案：**不能仅由租约推断进程死亡。租约是权威系统记录的限时授权；A 可能因为进程暂停、网络故障、续租排队或运行环境抖动，没有及时续约，但其线程和网络请求仍可能存在。系统允许 B 接管是为了恢复进展，不是因为获得了 A 已停止的事实。因此，后续写入必须拒绝 A 的旧授权，并且恢复流程要检查它此前可能留下的外部副作用。把“无有效租约”直接当成“供应商没有受理”，会混淆执行权证据和业务执行事实。

#### L2 推导：心跳失败一次就永远停止合理吗？

**答案：**需要区分瞬时续租错误和已确认失权。短暂连接错误发生时，最后一次已成功证明的租约可能仍有余量，可以在这个范围内有界退避重试；若数据库明确拒绝旧 token，或者本地保守期限已到，就应永久停止本次执行。Naumi 的调度器只重试续租，不重新执行付费工作，并用单调时钟约束本地期限。迟到的续租成功响应也不会把已经失权的执行者复活。租约不必大于整个任务耗时，但心跳间隔和余量必须覆盖合理长尾，且失权路径要完整。

#### L3 变式：SQL 等待行锁期间，租约到期怎么办？

**答案：**取得行锁以后重新验证当前 token 与实时期限，不能只依靠等待之前算出的布尔值。PostgreSQL 的 `now()` 表示事务开始时刻，长事务中它不随墙上时间推进；即便 SQL 使用时间条件，某些谓词求值与锁等待的时序也需要分析。Naumi 的关键写入先 `SELECT ... FOR UPDATE`，然后由 `assertLeaseTx` 使用 `clock_timestamp()` 检查授权，检查点更新后再次校验。这样可以拒绝已知过期或被接管的写入；也不宜把短事务提交的物理瞬间宣传成绝对实时互斥的数学保证。

#### L4 负责：随机 token 是否等于通用 fencing 序号？

**答案：**随机 token 可以标识当前持有人，权威数据库通过相等比较拒绝旧值，但它本身没有可比较的先后顺序。经典单调 fencing 序号要求每次授权得到递增代次，受保护资源保存已见最高代次并拒绝更旧操作；这还要求那个资源真正执行检查。对象存储、供应商 API 或其他数据库若不识别该协议，给请求附一个 token 也不会自动获得隔离。应逐项列出哪些写入受当前数据库校验保护、哪些外部效果依赖业务幂等或原身份恢复，而不是笼统宣布整个系统已实现 fencing。

源码：[`assertLeaseTx`、`saveImageJob`、`heartbeatImageJob`](../../../src/lib/image-job-repository.ts) 与 [`startImageJobHeartbeat`](../../../src/lib/image-job-lease.ts)。历史验证见[租约隔离记录](../../changes/2026-10-29-capacity-x2-lease-fencing.md)。

### 常见误区

- “租约大于最长任务就万无一失”：暂停和故障未必有可靠上界，过长租约还拖慢接管；核心是续租、失权和副作用边界一起成立。
- “心跳请求成功就能恢复旧执行”：响应可能迟到；本地已经失权后重新推进，会与新持有人竞争。
- “写数据库被挡住就不会重复付费”：供应商请求可能早已发出，隔离范围到哪里，保证才到哪里。

### 跨业务迁移

电商履约 Worker 失权后，数据库可以拒绝旧订单更新，但已发给仓库的出库请求未必撤回，需要仓库侧业务单号幂等与对账。社交内容分发 Worker 失权后，旧执行者仍可能发出通知；允许重复、去重窗口和用户体验要按业务选择。Naumi 的付费调用更需要保留原操作身份：合法接管不等于有权再创建一次供应商任务。
