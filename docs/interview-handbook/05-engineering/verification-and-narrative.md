## HB-011 测试通过、合并、上线、验收为什么不是一回事？

### 现场问题

修复脚本 exit 0，代码合入 main，健康检查 200。能否宣布用户问题已经解决？

### 旧模型与反例

旧模型：“任何一个绿色状态等于全链路完成。”反例：测的是 mock；服务器运行的仍是旧镜像；新版本健康但付费生成、作品回执或账务链路失败。

### 基本事实与不变量

每条证据都有对象、输入、环境和证明范围。源码存在、局部测试、主线整合、构建、部署切流、业务验收及旧槽排空是不同事实。

### 推导与参考回答

#### 直接回答

**答案：** 不能仅凭这些绿色状态宣布用户问题已经解决，因为它们验证的是不同对象。测试说明特定输入与环境下的行为；main 说明源码已经整合；构建说明得到一个候选产物；运行版本证明实际部署身份；业务验收才覆盖受影响的用户链路。健康检查只验证它自身设计的探测范围，可能完全没有触发生成、结果保存或结算。

对发布还要区分候选就绪、切流与旧槽排空。新槽正常但旧任务归属未知，意味着仍有生命周期债务。回滚应恢复兼容入口与程序，不自动恢复历史数据库快照，更不通过重新提交已接受或未知付费任务来“找回结果”。

#### 从事实推导

1. 任何验证都只能对它实际接触的对象、输入和环境给证据；mock 不会自动覆盖真实数据库与供应商。
2. 代码进入仓库以后，服务器仍可能运行旧镜像，所以需要把完整提交、产物与运行实例绑定。
3. 进程可启动与功能可用是不同条件；真实鉴权、DB、媒体和任务恢复可能在首次业务调用时才暴露问题。
4. 切换入口只改变新流量方向，在途连接、任务和旧前端资源仍可能依赖旧槽。
5. 验收和回退必须保护这些持久业务事实，否则“部署成功”可能同时制造用户损失。

#### 示例与落地

教学验证矩阵可以这样填写：单元测试证明状态分支；本地数据库集成证明事务与锁；固定构建绑定 SHA/镜像；候选旁路核对登录、DB 和受影响接口；切流后按原任务核对回执、作品与账务；排空阶段核对会话、Worker 租约和旧资源。每项写清实际结果与未覆盖范围，而不是统一填“通过”。

教学反例：某 helper 在 mock 下成功，main 已合并，公网 health 200；若公网版本仍是旧 SHA，则只完成源码交付和旧版本可用性观察，尚无目标部署证据。即便目标 SHA 已运行，也仍需检查那条原本失败的业务路径。

#### 面试表达

“我会分层报告进度，避免把测试、main、部署与验收混成一个完成状态。先固定修复提交和构建产物，再确认候选真实就绪、平滑切流、原业务连续以及旧槽排空。健康 200 只对健康探测作证，不能替付费链路验收。回退还要考虑旧前端资源、协议与数据库兼容，不能回灌旧业务数据或重放未知付费请求。我的完成标准是受影响链路有实际证据，剩余债务有明确记录，而不是所有表面指示灯变绿。”

### L1—L4 追问

#### L1 解释：HTTP 200 能证明什么？

**答案：** 它说明这次请求获得了成功类 HTTP 响应，进一步的业务含义还取决于响应体契约、探测内容和实际响应实例。某些系统可能在 200 里包装业务错误；某些 health 只检查进程存活，不访问数据库。即使深度健康检查通过，也只是证明检查覆盖的依赖在当时可用，不能证明所有账号权限、生成结果和账务都正确。应核对响应内容、时间、实例与版本，再明确该证据能支持的结论。一个局部成功适合缩小故障范围，不适合替整个系统签发验收结论。

#### L2 推导：为什么固定完整 SHA 和镜像？

**答案：** 分支名和标签可以移动，完整提交 SHA 与产物内容身份能使验证对象明确。仅有源码 SHA 还不够：依赖、构建参数和运行配置可能影响结果，因此要保留构建记录、镜像 ID/摘要以及必要配置修订，再核对实际 Web 和 Worker。这样才能回答“测的是哪个版本、部署的是不是它、失败时退到哪里”。固定身份不自动保证构建完全可复现或业务正确，但它提供追踪与复验的基础，避免拿 A 的测试、B 的镜像和 C 的线上现象拼成一份看似完成的报告。

#### L3 变式：新槽正常但旧任务没排空呢？

**答案：** 应保留仍承载工作的旧槽，并记录未排空的会话、任务、租约和归属证据，不能为了收尾强制停止。切流通常只改变后续入口，SSE、旧页面资源、长请求和 Worker 原执行身份可能继续依赖旧环境。要按生命周期协议观察排空，核对新旧实例交接不会重复生成或结算；状态未知时明确 CLEANUP_PENDING 等债务。只有适用证据确认旧工作结束或已被正确接续，才停止旧槽并关闭自启。新槽 health 正常与整个发布完成是两个结论。

#### L4 负责：上线后怎样回退？

**答案：** 先准备可读的固定旧产物、入口与配置恢复材料，再确认旧程序能兼容当前数据库模式、媒体引用和新旧前端协议。数据库演进优先采用扩展、回填、收缩，给程序回退留窗口；不把生产数据库回灌成旧快照，以免丢失切换后的业务。回退时仍需部署锁、路由核验和在途任务保护，继续按原身份查询或恢复，不重新发送未知付费工作。回退完成还要验证公网、实际版本、关键链路与旧槽状态；回退过程本身失败也必须如实保留，不能只报告“已执行命令”。

### 常见误区

- “CI 绿了就是线上修好了”：测试环境和线上运行身份尚未建立关联。
- “切回旧镜像就该恢复旧数据库”：可能覆盖上线后的合法业务与媒体数据。
- “新槽正常，可以直接停全部旧容器”：忽视在途会话、任务与回滚引用。

### 跨业务迁移

电商发布需要保护在途支付、订单状态和回调兼容；社交发布可能更关注长连接、消息游标、缓存键与旧客户端协议；Naumi 还要保护长生成任务、SSE、作品结果和积分。共同原理是让版本身份与验证对象一致，并保持在途业务连续；需要排空的对象和兼容窗口由业务决定。

### 项目证据与验证

规则入口：[`RELEASE_RUNBOOK.md`](../../RELEASE_RUNBOOK.md)、[`RELEASE_LIFECYCLE.md`](../../RELEASE_LIFECYCLE.md)。这些是现行发布要求与实现说明，历史段落需结合最新规则，不表示本次执行了发布。

## HB-012 怎样把一次修复讲成有含金量的项目经历？

### 现场问题

面试官问“介绍一个最难的问题”。回答“用了 Redis、做了分布式、性能提高很多”为什么说服力不足？

### 旧模型与反例

旧模型：“技术名词多就有深度。”反例：无法解释当时的症状、替代方案、因果证据或效果口径。

### 基本事实与不变量

个人经历必须真实，项目事实要有证据，效果数据要有统计口径。局部结果不能包装成全项目或生产容量结论。

### 推导与参考回答

#### 直接回答

**答案：** 项目经历的含金量来自可核查的因果链和你实际承担的决策，不来自技术名词数量。先讲业务影响与具体症状，再讲初始假设、证据、根因、替代方案、实际改动、验证结果和剩余边界。每个数字都要有对象、时间窗和统计口径；每个“我做了”都要对应真实参与。读过案例可以展示分析能力，但应明确称为项目案例分析，不冒充亲历。

一句“性能提高很多”会留下关键空白：提高的是吞吐还是尾部延迟，工作负载是否相同，错误率和成本怎样，结果是本地还是线上？把这些条件交代清楚，面试官才能判断方案是否真的有效以及你的认识是否可迁移。

#### 从事实推导

1. 面试官看不到项目现场，需要你提供可追问、可复核的事实，而非仅表达信心。
2. 只说最终方案无法区分亲自推理与事后背答案，因此要解释旧假设怎样被证据推翻。
3. 多个方案通常都能改善表面症状，讲取舍才能展示你理解根因和成本。
4. 指标缺少口径时容易产生虚假改善，验证必须说明工作负载、环境、时间窗与未覆盖范围。
5. 个人贡献和团队成果分开，才有真实责任边界；仍未知的部分应成为下一步，而非被叙事掩盖。

#### 示例与落地

以下是可练习的案例分析，不是学习者亲历声明：项目记录里，登录和回执同时挂起，版本接口却正常。先提出共享数据库依赖假设；结合连接持有与锁关系，解释事务内二次借池的等待环。对比扩池、加缓存和复用事务连接：前两者可能缓解症状，后者直接改变本案例的等待结构。再说明元数据查询留在事务内、媒体体读取移出事务，以及回执期限覆盖 body。

效果应引用实际证据，例如记录中的 `borrowed=1 → 0`、`bodyReads=1 → 0` 属局部验证口径，不把它扩写成“生产吞吐提升十倍”。若本人只分析代码，就说“我核对并解释了实现”；若本人执行过修复，再补真实提交、决策与验收，不填虚构数字。

#### 面试表达

“我分析过 Naumi 的连接池等待案例。价值不在于池从多少调到多少，而在于发现了跨应用池队列和数据库行锁的闭环。版本接口正常、登录与回执异常提供依赖线索；记录中的结构修复是复用事务连接，把媒体体移到事务外，回执读取补完整期限。我能说明为什么简单扩池不是根因修复，也能区分局部 fixture 验证与今天线上状态。若迁移到订单系统，我会重查交易事务与外部支付边界，而不是照搬生图处理。”

### L1—L4 追问

#### L1 解释：你本人做了什么？

**答案：** 按真实参与拆成阅读理解、调查取证、方案设计、编码、验证、发布和协调等活动，说明哪部分由自己完成，哪部分依赖同事或既有机制。例如只读过复盘，可以说“我复核了调用链并能解释等待环”；不能说“我主导恢复了线上”。参与实现但没有负责发布，就把源码交付与线上验收分开。面试官继续问具体决策、失败尝试和证据时，真实边界反而更有说服力。参考答案帮助组织表达，不授予任何未发生的个人经历，也不自动证明已经能独立完成同类任务。

#### L2 推导：为什么排除了其他方案？

**答案：** 不应为了故事完整而宣称所有替代方案都被实测否定，而要分别说明不匹配的原因。比如本案例的证据是持有资源后再等待资源形成环，缓存不直接改变这条依赖，扩池可能暂时解环但保留结构缺陷；复用已有事务连接则直接消除二次借池。若扩池对合法吞吐仍有价值，可以在根因修复后按预算测量。好的回答区分“理论上不解决这个机制”“受成本约束未采用”和“已经实验验证”，避免把个人偏好伪装成普遍技术结论。

#### L3 变式：换成电商订单会怎样？

**答案：** 先保留通用机制：同池嵌套借连接仍可能产生资源等待，外部请求超时仍不等于未执行，原业务身份仍是核查基础。再重新定义业务不变量：订单、库存、优惠与支付的事务关系是什么，哪个系统拥有权威状态，补偿是否可逆，重复效果会造成多少损失。生图预占与库存冻结只是类比，退款也不能代替支付状态核实。选择共享事务、outbox、幂等或对账时要依据新场景的真实边界，而不是把文档里的“图片”替换为“订单”就认为完成迁移。

#### L4 负责：重做一次会改什么？

**答案：** 应提出针对已知盲点且有收益依据的改进，而不是事后堆更多组件。例如提前记录 checkout 与连接持有时长、事务接口显式传递 client、验证媒体读取发生在 COMMIT 后，并增加受理后丢回包和锁等待变式。也可以改交付记录，让源码、本地证据与线上验收不混淆。每项改进说明要避免哪类错误、成本多大、由谁维护和怎样验收；不是所有日志都需要采全，也不是所有模块都要拆服务。负责人复盘的重点是把一次经验变成可持续机制，而不是把事故讲成个人英雄故事。

### 常见误区

- “列出 Redis、MQ、微服务就有深度”：缺少业务约束、因果证据与方案边界。
- “案例属于我们的项目，所以就是我的亲历”：团队成果、阅读理解和本人执行是不同事实。
- “指标越大越有说服力”：没有工作负载、口径和证据的数字会削弱可信度。

### 跨业务迁移

电商案例可以围绕防重复支付、库存一致性与履约讲因果链；社交案例可以围绕热点、分发与可见性讲，但权限和删除正确性仍要单独说明。迁移的是“现象—证据—机制—取舍—验证”的叙事结构，不是某家平台的架构传说，也不是虚构一段与岗位匹配的事故经历。

### 项目证据与验证

依托本手册各题的源码及历史证据，不把本文练习稿当作亲历证明。实际回答后由面试官追问变化条件，能迁移推理才记录相应掌握状态。
