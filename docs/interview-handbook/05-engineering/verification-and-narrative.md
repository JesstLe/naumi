## HB-011 测试通过、合并、上线、验收为什么不是一回事？

### 现场问题

修复脚本 exit 0，代码合入 main，健康检查 200。能否宣布用户问题已经解决？

### 旧模型与反例

旧模型：“任何一个绿色状态等于全链路完成。”反例：测的是 mock；服务器运行的仍是旧镜像；新版本健康但付费生成、作品回执或账务链路失败。

### 基本事实与不变量

每条证据都有对象、输入、环境和证明范围。源码存在、局部测试、主线整合、构建、部署切流、业务验收及旧槽排空是不同事实。

### 推导与参考回答

按证据层次汇报：本地重现/验证 → 主线固定提交 → 固定构建 → 候选就绪 → 切流 → 在途业务及旧槽排空 → 受影响链路验收。顺序可以按项目真实流程细化，但不能跳过未完成事实。

回滚程序不等于回灌数据库和媒体，更不等于重发已经受理或状态未知的付费操作。只切流但旧槽债务未知时，不标整个发布完成。

参考表达：“我能证明的只是具体层次。测试证明用例环境中的行为，main 证明源码整合，实际运行 SHA/镜像证明部署身份，业务验收证明受影响链路。健康 200 不能替代它们。”

### L1—L4 追问

- **L1**：HTTP 200 能证明什么？要点：该请求成功响应，不自动证明目标版本和全业务正确。
- **L2**：为什么固定完整 SHA/镜像？要点：验证对象可重复、源码与运行身份可关联。
- **L3**：新槽正常但旧任务没排空呢？要点：保留旧槽并记录债务，不强行停止来制造完成。
- **L4**：上线后怎样回退？要点：兼容入口、旧资源、数据库扩展兼容、在途身份和恢复材料一起考虑。

### 项目证据与验证

规则入口：[`RELEASE_RUNBOOK.md`](../../RELEASE_RUNBOOK.md)、[`RELEASE_LIFECYCLE.md`](../../RELEASE_LIFECYCLE.md)。这些是现行发布要求与实现说明，历史段落需结合最新规则，不表示本次执行了发布。

本手册是纯文档交付，验证目录、引用、题号和 Git 差异；不运行收费生成、不触发业务发布，也不增加发布次数。

### 边界与待追问

发布流程细节待后续按真实版本展开。前置：HB-008、HB-010。后续：HB-012。学习状态：未评估。

## HB-012 怎样把一次修复讲成有含金量的项目经历？

### 现场问题

面试官问“介绍一个最难的问题”。回答“用了 Redis、做了分布式、性能提高很多”为什么说服力不足？

### 旧模型与反例

旧模型：“技术名词多就有深度。”反例：无法解释当时的症状、替代方案、因果证据或效果口径。

### 基本事实与不变量

个人经历必须真实，项目事实要有证据，效果数据要有统计口径。局部结果不能包装成全项目或生产容量结论。

### 推导与参考回答

按八个部分叙述：业务背景 → 具体症状 → 初始假设 → 推翻假设的证据 → 根因机制 → 方案取舍 → 验证结果 → 剩余边界。

练习稿：“项目记录显示登录与回执同时挂起，但版本接口正常。我的分析会先查共享数据库依赖和等待关系，而非直接加缓存。记录中的根因是事务内嵌套借池形成跨层等待环；修复复用事务连接、把媒体体移到事务外，并补有界回执读取。记录中的局部验证不能被我说成今天线上已经验收。”

若学习者亲自参与过，再补本人职责、决策、实际命令、指标和复盘；没有参与就保持‘分析项目案例’的表达。

### L1—L4 追问

- **L1**：你本人做了什么？要点：区分阅读、协作、执行与负责。
- **L2**：为什么排除了其他方案？要点：证据与约束，不是背标准答案。
- **L3**：换成电商订单会怎样？要点：保留原理、重算业务代价，不机械换名词。
- **L4**：重做一次会改什么？要点：改观测、接口、验证或决策机制，并解释成本收益。

### 项目证据与验证

依托本手册各题的源码及历史证据，不把本文练习稿当作亲历证明。实际回答后由面试官追问变化条件，能迁移推理才记录相应掌握状态。

### 边界与待追问

没有回答记录前不生成“已掌握”结论，不替学习者虚构指标。前置：HB-010、HB-011。后续：跨业务变式。学习状态：未评估。
