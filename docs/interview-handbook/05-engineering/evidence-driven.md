## HB-010 故障发生后，先拿哪三类证据？

### 现场问题

CPU 不高，版本接口正常，登录和生图状态查询超时。有人建议加 Redis、加实例、扩连接池。你先收集什么？

### 旧模型与反例

旧模型：“看到一个症状，立刻匹配一个常见方案。”反例：相同超时可以由池排队、锁等待、媒体 I/O、回包或页面逻辑引起；选错层会增加成本并掩盖故障。

### 基本事实与不变量

先建立影响范围和时间线，再连接资源持有者与等待者，最后核查业务事实。诊断中不通过付费重放、清空未知状态或覆盖数据来制造确定性。

### 三类证据与排除目标

#### 第一类：请求路径与时间线

记录正常和失败接口、起始时间、状态码、耗时、实例归属、请求/任务关联身份。比较不依赖 DB 的版本接口和依赖 DB 的登录/回执。

排除目标：避免把所有故障归为整机宕机、DNS 或反向代理故障。某条接口 200 只能缩小范围，不能排除所有网络或实例差异。

#### 第二类：资源、事务与等待关系

检查池 total/idle/waiting、checkout 时长、事务年龄、SQL、锁持有者、wait event、CPU/内存/I/O 与线程/事件循环。把应用的“持连接又借连接”和数据库锁关系连接起来。

排除目标：区分吞吐不足、池队列、锁竞争、连接泄漏、慢 SQL、外部 I/O 与跨层等待环。低 CPU 不证明这些都正常。

#### 第三类：任务、结果与账务事实

沿原身份核查父子任务、供应商受理证据、结果对象/作品、预占、扣款和释放。把“任务没完成”与“任务完成但回执没送达”分开。

排除目标：防止把页面失败误判为上游未受理，或者误报重复扣费；检查金额和明细，不能只看 settled 等标签。

### 推导与参考回答

#### 直接回答

**答案：** 我先拿三类相互关联的证据：请求路径与时间线、资源与等待关系、任务与账务事实。第一类缩小故障范围，第二类解释阻塞机制，第三类判断用户业务究竟发生了什么。它们应通过同一时间窗、实例和原任务身份关联起来，而不是各截一张看似异常的图就直接下结论。

在本题里，版本接口正常说明至少有一条请求路径可用，但它可能不访问数据库，不能推出数据库正常。登录与回执共同依赖什么，是下一步调查起点。低 CPU 使“纯计算饱和”解释变弱，但并不排除锁、连接池、磁盘或网络等待。证据不足时先保留竞争假设，避免立刻扩容改变现场。

#### 从事实推导

1. 故障是正常行为与异常行为的差异，因此先确定时间、接口、账号范围和实际承载实例。
2. 多个异常路径的共同依赖提供定位线索，但相关不等于根因，还要找到具体等待位置。
3. 等待关系包含持有者与请求者；只看到“池满”不知道谁持有多久，仍不足以选择修复。
4. 用户投诉是业务现象，还要查原任务、结果与账务，防止诊断动作造成重复付费或错误退款。
5. 形成能被反证的假设后，用低影响观测或隔离复现检验，再选择止血与结构修复。

#### 示例与落地

以下是教学诊断路径，不是本轮生产检查：对照版本、登录和回执的请求时间线；若异常路径都等待借池，再查看池 waiting、checkout 耗时与已借出的事务年龄。若 SQL 执行很快但连接仍不释放，检查事务内是否等待另一次池借用或外部 I/O；若数据库报告锁等待，沿阻塞者继续追，而不是终止第一条看到的慢请求。

只读 SQL 例子可从 `pg_stat_activity` 的 `pid、state、xact_start、wait_event_type、wait_event` 和 `pg_blocking_pids(pid)` 建立线索；应用层还必须提供 checkout 与持有时间，因为 PostgreSQL 看不到所有池队列。最后拿一笔投诉的原任务，核对结果对象和预占/扣款金额，确定“未完成”还是“完成但未送达”。观测本身也有成本，要限定范围并保护敏感字段。

#### 面试表达

“我不会先在 Redis、扩实例和扩连接池里三选一。我先建立正常与异常接口的时间线，确认实际实例与共同依赖；再把应用池队列和数据库事务、锁等待连起来，找资源持有者；同时按原任务核查结果与金额，避免把页面超时当成上游未受理。三类证据回答范围、机制和业务后果。拿到等待环或其他可检验机制后，再设计止血与结构修复，并明确哪些结论只是历史记录，哪些已在隔离环境重现。”

### L1—L4 追问

#### L1 解释：为什么先看正常接口？

**答案：** 正常接口是一组有用的对照，它帮助缩小“所有请求都失败”这样的粗糙描述。比如同一入口的版本接口正常、数据库相关接口异常，可能说明问题集中在后者的共同依赖，而不是整机完全离线。不过对照必须可比：需要确认时间、路由、实例、认证和依赖差异；CDN 命中、旧实例响应或不访问 DB 的端点，不能替其他路径作证。看正常接口不是为宣布系统健康，而是利用差异提出下一条可检验假设，之后仍要沿实际异常路径追踪。

#### L2 推导：什么证据会推翻“DB 慢”？

**答案：** 先把“DB 慢”细化：是 SQL 执行慢、等锁、建立连接慢，还是应用等待池槽？如果 SQL 服务时间短、数据库执行活动不多，但 checkout 排队长，瓶颈可能在连接长期被应用持有；若服务器已快速返回而客户端 body 消费挂起，则问题可能在回包或读取路径。反过来，稳定出现的长 SQL、I/O 等待与对应执行计划才支持查询瓶颈。数据库低 CPU 并不足以推翻所有数据库相关问题；要让每条证据对应具体机制，而不是用一个宽泛标签包住所有异常。

#### L3 变式：日志没查到等于没发生吗？

**答案：** 通常不等于。日志可能采样、丢失、尚未刷盘，时间戳可能有时区或时钟偏差，查询还可能使用错误账号、任务号、实例或时间窗。只有在日志覆盖、完整性、身份和时间边界都有保证时，缺失才可能成为特定范围内的否定证据。对外部受理尤其如此：本地没记录返回任务号，可能只是回包或写检查点失败。应交叉查持久任务、受理回执、结果对象及账本；如果仍没有身份绑定的证明，结论保持“未观察到”，不要升级成“确定未发生”。

#### L4 负责：应急与根治怎么分？

**答案：** 应急目标是控制影响并恢复服务，结构修复目标是消除已证实的故障机制，两者需要分别记录。某次释放阻塞事务后页面恢复，只证明这次阻塞被解除；若嵌套借池仍存在，负载回来还可能复发。负责人应保留现场证据、说明应急动作及副作用，再通过隔离复现、定向修复和受影响链路验证证明根因处理。遗留任务、账务与用户沟通也要独立闭环，不能服务恢复就默认它们都正确。最后补观测和预防机制，但避免把超时或扩池护栏说成结构修复。

### 常见误区

- “低 CPU，所以数据库没问题”：忽略锁、I/O、池队列和应用持连接等待。
- “重启后好了，所以已经根治”：恢复动作清除了现场状态，不一定改变触发机制。
- “日志没有成功记录，所以操作失败”：把证据缺失直接提升为否定事实。

### 跨业务迁移

电商订单页超时，同样先查请求链、资源等待与原订单/支付事实，不能直接补扣或退款。社交发帖异常则要区分写入、审核、分发和可见性，不能因为信息流没显示就认定帖子没保存。三类证据框架可以迁移，但每个业务要重新定义权威事实、错误代价与可以接受的延迟。
