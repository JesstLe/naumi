## HB-010 故障发生后，先拿哪三类证据？

### 现场问题

CPU 不高，版本接口正常，登录和生图状态查询超时。有人建议加 Redis、加实例、扩连接池。你先收集什么？

### 旧模型与反例

旧模型：“看到一个症状，立刻匹配一个常见方案。”反例：相同超时可以由池排队、锁等待、媒体 I/O、回包或页面逻辑引起；选错层会增加成本并掩盖故障。

### 基本事实与不变量

先建立影响范围和时间线，再连接资源持有者与等待者，最后核查业务事实。诊断中不通过付费重放、清空未知状态或覆盖数据来制造确定性。

### 三类证据与排除目标

#### 第一类：请求路径与时间线

记录正常和失败接口、起始时间、状态码、耗时、实例归属、请求/任务关联身份。比较不依赖 DB 的版本接口和依赖 DB 的登录/回执。

排除目标：避免把所有故障归为整机宕机、DNS 或反向代理故障。某条接口 200 只能缩小范围，不能排除所有网络或实例差异。

#### 第二类：资源、事务与等待关系

检查池 total/idle/waiting、checkout 时长、事务年龄、SQL、锁持有者、wait event、CPU/内存/I/O 与线程/事件循环。把应用的“持连接又借连接”和数据库锁关系连接起来。

排除目标：区分吞吐不足、池队列、锁竞争、连接泄漏、慢 SQL、外部 I/O 与跨层等待环。低 CPU 不证明这些都正常。

#### 第三类：任务、结果与账务事实

沿原身份核查父子任务、供应商受理证据、结果对象/作品、预占、扣款和释放。把“任务没完成”与“任务完成但回执没送达”分开。

排除目标：防止把页面失败误判为上游未受理，或者误报重复扣费；检查金额和明细，不能只看 settled 等标签。

### 推导与参考回答

“我先建立接口与时间线差异，再追资源等待图，同时沿原任务核对业务事实。三类证据分别回答故障在哪里、为什么阻塞、用户业务实际发生了什么。有证据支持根因后，再选择修复与恢复动作。”

### L1—L4 追问

- **L1**：为什么先看正常接口？要点：对照实验式地定位共同依赖。
- **L2**：什么证据会推翻‘DB 慢’？要点：定义具体假设，而不是把所有等待都叫慢 SQL。
- **L3**：日志没查到等于没发生吗？要点：还要核对采样、丢失、时间窗和身份匹配。
- **L4**：应急与根治怎么分？要点：止血动作、结构修复、验证层次、用户账务处理分别记录，观察到的恢复不自动证明根治。

### 项目证据与验证

案例入口：[企业池等待与回执修复记录](../../changes/2026-10-30-enterprise-pool-deadlock-fix.md)。该记录明确 fixture、真实调用路径提取、模拟池和真实线上验收的差别。

练习只在已有记录或隔离环境里进行，不需要为回答面试题连接生产、终止事务或重新提交生成任务。
