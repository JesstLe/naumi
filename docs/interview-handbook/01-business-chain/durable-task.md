# 01-01 请求、任务与账务事务

[返回总目录](../README.md)

## 1. 主链路与三个状态轴

用户提交意图 → 校验归属、输入和冻结执行上下文 → 保存任务与预占 → 执行者领取 → 供应商受理与生成 → 结果保存 → 账务结算 → 用户获得回执。

- **执行事实**：供应商受理了吗？结果保存了吗？
- **观察状态**：浏览器是否拿到回执？当前页面展示什么？
- **账务状态**：预占、扣除或释放了多少？

它们有关联，但不能用一个状态字段互相替代。

## HB-001 用户关掉页面，任务为什么还要存在？

### 现场问题

用户提交一次生图，页面关闭；或者 Web 在返回响应前重启。再次打开页面时，系统应该知道什么？

### 旧模型与反例

旧模型：“一次请求就是一次任务。”反例：请求消失时，供应商可能仍在执行，积分可能已经预占。

### 基本事实与不变量

连接、页面和进程都可能消失；已接受的业务意图需要可追踪。不能因为丢失连接就把旧任务悄悄变成一次新任务。

### 推导与参考回答

#### 直接回答

**答案：** 页面关闭只结束这次交互，不自动撤销已经接受的业务。任务应当作为独立的持久对象保存：系统要能回答是谁提交、使用哪些输入与版本、积分是否预占、是否调用过供应商、结果在哪里。重开页面时按原任务身份读取；进程重启后由恢复流程核查原事实。只有业务明确取消且取消协议完成，才能把执行或账务转入对应状态，不能把连接断开当作取消成功。

#### 从事实推导

1. 浏览器、HTTP 连接和 Web 进程的生命周期，比业务承诺短，而且它们可以分别失败。
2. 供应商是独立参与者。即使我们的连接消失，远端已经受理的生成仍可能继续并产生费用。
3. 要在故障后恢复判断，就必须把任务身份、冻结执行上下文和副作用证据放在进程之外。
4. 提交入口只负责可靠建立业务事实，执行者负责推进，查询入口负责观察；三种职责不再绑在一次长请求中。
5. 恢复依据是已保存的事实与协议，不是“页面好像失败了”。这一步也解释了为什么持久任务还需要幂等、租约和原身份恢复。

#### 示例与落地

以下是教学时序，不是本轮真实故障注入：

```text
t0 用户携带 operationId=OP-A 提交创作
t1 事务提交：任务 OP-A 与应有的积分预占同时存在
t2 响应在网络中丢失，浏览器关闭
t3 用户重开页面，查询 OP-A，而不是创建 OP-B
t4 恢复器读取 OP-A 的检查点，确定应展示结果、继续查询还是核查
```

如果客户端完全丢失原身份，产品还应提供按用户归属查询近期任务的入口。数据库任务表和执行唤醒也要衔接：提交后唤醒消息丢失时，持久扫描或 outbox 等机制需要能找回任务，不能只有一次进程内回调。

#### 面试表达（约90秒）

“我先区分请求生命周期和业务生命周期。关页面只能证明连接结束，不能证明供应商停止了，所以已接受任务必须持久化，并保留用户、输入、执行版本、预占和上游检查点。重新打开页面读取原任务，恢复器根据原事实推进，不直接再生成。与此同时，任务落库只是恢复的基础，还要保证任务和账务一起提交、执行权可竞争且可接管、外部调用不会因一次回包丢失被盲目重放。我会用提交前后、受理前后和结果保存前后的故障注入来验证，而不只看服务能否重新启动。”

### L1—L4 追问

#### L1 解释：内存 Map 为什么不够？

**答案：** Map 的可靠范围止于它所在的进程。进程退出后内容消失，第二个实例也看不到第一份 Map；即便使用全局 Symbol 复用模块状态，也只是解决同进程多 bundle 或热更新下的复用，不会变成跨进程持久化。对于可以丢弃的临时 UI 缓存，Map 可能合适；对于已接受、已预占或可能收费的任务，它不足以作为唯一事实来源。关键不是“Map 技术低级”，而是它的存活与共享边界不满足业务承诺。

#### L2 推导：最少保存哪些字段？

**答案：** 从“故障后需要做什么决定”倒推字段，而非把整个请求对象随意序列化。至少要有稳定任务/操作身份、账号或租户归属、冻结输入或受控引用、执行配置/报价版本、任务状态与进度、执行权以及已经发生的外部付费证据、结果引用和账务关联。字段可以分属不同表，但关联必须可靠。凭据不应明文落入任务快照；大图片宜存受控对象引用。还要保留更新时间与诊断信息，才能区分正在执行、等待查询和需要核查。

#### L3 变式：插入成功但响应丢失怎么办？

**答案：** 客户端没有收到成功响应，只能说明观察失败，不能推断服务端没有提交。若提交前已建立稳定 operationId，先用它查询或走明确支持同身份幂等的提交协议；同键不同输入需要拒绝或显式核查，不能悄悄覆盖原意图。若查询暂时无记录，还要考虑提交尚未完成、读路径或一致性窗口，不能立即换新 ID 重试付费动作。系统需要定义可判定的受理契约，并保留未知状态，直到有身份绑定的事实支持下一步。

#### L4 负责：怎样证明可恢复？

**答案：** 按业务边界设计故障矩阵：任务提交前、提交后响应前、供应商受理后回包前、结果保存前后，以及账务结算前后分别中断。每个用例核对原任务身份没有变化，任务能被重新发现，结果不会遗失或落到错误账号，预占、扣款与释放满足约定，外部调用次数和身份符合协议。测试进程重启成功仅说明基础服务恢复，不证明履约正确。先在隔离环境用可控上游复现，再将真实站点验收单独记录，不能混为一层证据。

### 常见误区

- “关闭页面等于取消任务”：页面没有控制独立供应商的天然权力，等待结束、执行取消和积分释放要分别确认。
- “任务落库就不会丢”：若没有可靠发现、领取、检查点和恢复路径，落库任务仍可能永久挂起。
- “相同提示词就合并成一个任务”：用户可能有意再生成一次，幂等身份应绑定一次业务意图，不能只按内容相同判断。

### 跨业务迁移

电商订单也独立于下单页面存在，支付回包丢失后应查询原订单/交易；但订单可关闭条件和生成任务可取消条件不同。社交上传视频同样要在断开页面后继续转码或提供准确恢复状态；普通未发布草稿则可能允许只存本地，不能把所有交互都强制做成长任务。

### 项目证据与验证

源码：[`DurableImageJobs.create`](../../../src/lib/durable-image-jobs.ts) 与 [`createImageJob`](../../../src/lib/image-job-repository.ts)。数据库路径和无数据库的本地路径要分开理解；不是所有运行配置都具备同样持久能力。

验证设想：对任务保存前后、供应商受理前后、结果保存前后分别注入中断，核对任务身份连续性。这是验收设计，本轮文档工作未执行业务故障注入。

### 边界与待追问

持久化不自动保证幂等或不重复外部调用。前置题：无。后续：HB-002、HB-008。学习状态：未评估。

## HB-002 任务创建和积分预占为什么要一起提交？

### 现场问题

先预占再保存任务，中途崩溃；反过来先保存任务再预占，中途也可能崩溃。怎样避免两边各成功一半？

### 旧模型与反例

旧模型：“两条 SQL 最后都会执行到。”反例：进程在两条语句之间退出，重试时还可能重复执行。

### 基本事实与不变量

同一次受理中的任务与应有预占需要一致，且重复提交不能多预占。任务事实和账务规则有不同职责，但可以共享同一个事务连接。

### 推导与参考回答

#### 直接回答

**答案：** 因为一次受理要求“有任务且有应有预占”，不能留下“钱冻结了却找不到任务”或“任务开始执行却没有对应预占”的半状态。同一数据库内，最直接的办法是让任务写入与预占规则共用一个事务连接，一起提交或回滚。原子性以这些本地写入为范围；调用供应商放在事务之外，由持久任务、幂等和检查点协调，不能假设数据库回滚会撤销远端生成。

#### 从事实推导

1. 两个分开的提交点之间，总存在进程退出或网络故障的窗口；调整先后次序只是更换半状态的方向。
2. 任务与预占属于不同模块，但同一次受理中的本地不变量要求它们一起成立，因此事务连接必须跨这两个模块显式传递。
3. 数据库事务负责原子提交，唯一业务身份和状态校验负责重复请求不多预占，两者不能互相替代。
4. 外部生成耗时且独立失败，不能拿着用户行锁和连接等待它结束；本地事实提交后再调度执行。
5. 提交响应也可能丢失，因此提交异常后的处理需要按原身份读回确认，而不是无条件重建任务。

#### 示例与落地

以下伪代码只表达事务边界，不是可直接替换 Naumi 的生产代码：

```typescript
await withTransaction(async tx => {
  await tasks.insertTx(tx, frozenTask);
  await billing.reserveTx(tx, operationId, frozenQuote);
});
// 提交后由可靠扫描/调度发现任务；这里不持有上述事务。
await scheduler.notify(operationId);
```

`tasks.insertTx` 与 `billing.reserveTx` 必须使用传入的同一个 `tx`，不能内部重新借池并各自 COMMIT。通知失败时，已提交的任务仍需被恢复扫描发现；更严格的跨消息可靠投递需求可由同事务 outbox 解决。

#### 面试表达（约90秒）

“这题先找不变量：受理成功后任务和应有预占一起存在，失败则不能留半笔。既然当前在同一个数据库，我会共享事务连接，而不是因为模块拆开就拆成两个提交。预占还要按稳定 operationId 幂等，并处理并发余额竞争。事务在建立本地事实后立即释放，外部生成交给任务执行；数据库原子性不覆盖供应商。最后我会验证事务中任一步失败都不留下半状态，以及 COMMIT 回包丢失时能按原身份确认，避免再次冻结或重复调用。”

### L1—L4 追问

#### L1 解释：什么叫原子性？

**答案：** 在本题限定的数据库事务中，任务写入和预占更新要么一起提交，要么一起不成为已提交事实。它不是“每条 SQL 都原子，所以整段业务原子”，也不等于客户端一定知道提交结果：COMMIT 的响应丢失仍可能让客户端不确定。原子性也不独自解决并发余额竞争、重复业务请求或外部收费，分别还需要隔离/原子条件更新、业务幂等以及上游恢复协议。回答时要明确保证的操作集合和边界。

#### L2 推导：模块拆开是否必须拆事务？

**答案：** 不必须。模块边界由职责和变化原因决定，事务边界由哪些写入必须一起成立决定。任务模块拥有任务规则，账务模块拥有预占规则，应用用例可以提供同一个 tx，让两个模块通过窄接口在同一事务内工作。这样既不复制账务 SQL，也不让任务模块穿透账本内部。真正危险的是模块函数隐式开启新连接、新事务，外层以为可统一回滚，内层却已经提交；接口必须声明是否接收和使用调用方事务。

#### L3 变式：COMMIT 实际成功但回包丢失呢？

**答案：** 这时数据库可能已经原子提交，但应用没有确认证据，状态应当视为提交结果未知。随后尝试 ROLLBACK 也不能证明此前 COMMIT 未成功；连接销毁只是清理本地资源，不会撤销已提交事实。恢复时按原 operationId 查任务及账务关联，确认是否已存在，并用同身份幂等协议约束可能的重试。不得为了消除异常而改新 ID 再次预占。若读取也失败，继续保持未知并安排核查，而不是把观察不到变成“没有发生”。

#### L4 负责：若以后真的跨数据库怎么办？

**答案：** 先证明独立部署、伸缩或隔离需求值得放弃同库事务的简单性，不因“要分布式”而先拆库。确需拆分时，把必须原子持久化的本地事实和 outbox 事件一起提交，消费者用稳定业务键幂等推进，建立重试、对账、差异处理与补偿流程。outbox 解决可靠表达发送意图，不自动保证消费者恰好执行一次。积分释放可能是补偿，但已经生成的图片或已支付的供应商成本无法被物理回滚，必须明确业务如何处理这些不可逆效果。

### 常见误区

- “每个 service 都有事务，所以组合起来安全”：多个独立提交仍留下跨模块半状态，必须核对实际使用的连接。
- “把供应商调用放进 BEGIN/COMMIT 就有分布式原子性”：它只会拉长锁和连接持有时间，数据库依然控制不了远端。
- “事务成功就不需要幂等”：两次不同事务都可能成功，业务身份和状态约束仍然必要。

### 跨业务迁移

电商同库创建订单与锁定库存可共享事务，但支付网关扣款需要独立的回执与对账机制。社交平台同库保存帖子与待分发事件可用事务 outbox 保证意图不丢；展示计数可能允许延迟，而私密内容的权限条件不能简单放宽为最终一致。是否要求一起提交，要从业务不变量而非业务名称判断。

### 项目证据与验证

源码：[`createImageJob`](../../../src/lib/image-job-repository.ts) 的 BEGIN、任务 INSERT、`reserveTx(client, ...)` 与 COMMIT；账务接口见 [`createBillingService`](../../../src/lib/billing/service.ts)。

验证设想：预占失败时没有半成品任务；任务写失败时没有残留预占；重复身份不会新增第二笔；提交回执丢失时按原身份确认。
