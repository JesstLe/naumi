## HB-004 CPU 不高，系统为什么也会全站挂起？

### 现场问题

版本接口很快，登录、页面和生图回执却超时，CPU 不高。有人建议增加实例、扩大连接池或加缓存。你先做什么？

### 旧模型与反例

旧模型：“系统挂了就是计算资源不够。”反例：所有关键请求在等待资源释放，CPU 可以很空闲。

### 历史案例与修复依据

项目的[企业读池自死锁修复记录](../../changes/2026-10-30-enterprise-pool-deadlock-fix.md) 说明了事务内再次向同一个池借连接的问题，并记录了去除嵌套借池、媒体体移出事务和回执期限等修复。

用于理解该历史故障的等待关系：四个外层事务各占连接并持有共享行锁，内部等待同池第二条连接；第五条连接上的操作等待这些共享锁释放。前四个事务等连接，第五个操作等它们提交，于是闭环。

这不是本轮在线复现，也不代表当前主线还保留同一个缺陷。具体历史值只用于解释该案例，不是通用池配置建议。

### 基本事实与不变量

连接池、数据库行锁和应用调用栈共同构成资源等待图。数据库能观察部分锁等待，却未必能观察应用层池队列，所以不一定把完整闭环报告为数据库死锁。

### 推导与参考回答

#### 直接回答

**答案：** 系统可能不是忙于计算，而是关键请求全部在等待。CPU、负载和版本接口正常，只能缩小故障范围，不能证明连接池、行锁或外部 I/O 正常。本案例的关键是把应用层的“持有连接又等新连接”和数据库的“持有连接又等行锁”拼成完整等待图。证据确认嵌套借池后，根治方向是复用已有事务连接、缩短持锁范围；扩池和超时可以有价值，但不能替代结构修复。

#### 从事实推导

1. 先比较正常与失败路径。若版本接口不借数据库，而登录和回执都借数据库，共同依赖就是优先排查候选，并非已经定罪数据库。
2. 看池 total/idle/waiting 与 checkout 时长，确认请求是排队借连接，还是借到连接后等待 SQL。
3. 查数据库事务年龄、SQL、等待事件、锁持有者，再对应应用栈上仍未完成的 await。
4. 若外层事务持有共享行锁却在同池借第二连接，而最后一条连接等它释放行锁，就得到了能解释现象的闭环。
5. 修改调用边界后，用并发与权限回归证明环被移除，再用超时、诊断与预算限制未来同类故障的影响范围。

#### 示例与落地

以下时序复述历史等待机制，用于教学，不是本轮线上重现：

```text
事务 A/B/C/D：各持 1 条池连接和用户共享行锁
事务 A/B/C/D：调用内层函数，等待同池第 2 条连接
操作 E：占有池中最后 1 条连接，等待用户排他行锁
A/B/C/D 等 E 归还连接；E 等 A/B/C/D 提交释放锁
```

修复后的接口应表达“已有 tx 就沿用”：外层把 `access.client` 传给素材元数据查询，只在事务内查归属和受控 key/URL；提交并释放后，再读取媒体字节。不能只给调用方套一个超时 Promise，却让未取消的借池操作随后取得连接而无人归还。

#### 面试表达（约90秒）

“CPU 低不等于系统有处理能力，也可能所有请求都在等。我会先用正常接口对照缩小依赖，再把连接池排队、数据库行锁和应用调用栈关联。这个项目历史案例中，外层事务持连接和共享锁，内部又借同池连接，最后一条连接上的操作反过来等待这些共享锁，形成跨层等待环。数据库未必看得到池队列，因此不一定报普通死锁。修复应复用事务 client、把媒体读取移到事务外，再补有界 checkout。最后分别报告并发复现、权限兼容和真实站点验收，不把加大池后暂时恢复当作根治。”

### L1—L4 追问

#### L1 解释：`idle in transaction` 表示什么？

**答案：** 它表示会话已经开启事务，但此刻没有执行 SQL，正在等待客户端下一条命令。事务仍未提交或回滚，已经取得的锁和其他资源可能继续保留，因此“idle”不是“没有影响”。它也不自动意味着泄漏：应用可能正在合法计算或等待某一步，需要结合持续时间、最后语句、事务年龄和调用栈判断。本案例中关键是应用持着事务等待第二条连接；单看数据库最后一条 ledger 查询，可能误以为那条已经结束的 SQL 才是耗时根因。

#### L2 推导：为什么内层函数不能自己随便 `getPool()`？

**答案：** 若调用方已经在事务内，内层重新从池借连接就改变了资源与一致性边界：外层持有的锁不会因内层等待而释放，内层也未必看到同一个事务快照，写入更可能无法统一回滚。正确做法是公开接口显式接收已有 tx，并确保 schema 初始化、辅助查询等路径也不偷偷再借。并非所有函数都禁止独立借池；事务外的独立读取可以合理借用自己的连接，关键在接口清楚表达上下文并符合调用链假设。

#### L3 变式：池从 5 调到 100 会怎样？

**答案：** 多出来的连接可能让本次等待中的内层调用继续完成，从而暂时释放锁，所以扩池不一定完全无效。但结构上每个外层事务仍可能“占一条再等一条”，并发继续上升时可能再次耗尽池；数据库承受更多活跃会话后，锁、内存、I/O 和调度竞争还可能恶化。如果等待根因是别的长锁，增加连接只是增加等待者。因此扩池要有数据库余量、整站预算和实测依据，并与结构修复分开记录，不能将暂时恢复误报为问题彻底消失。

#### L4 负责：怎么证明修复？

**答案：** 先在隔离环境构造旧路径的并发、共享锁与池容量条件，使症状可重复；再运行同样输入验证新路径没有事务内二次 checkout，媒体体读取发生在 COMMIT/release 后。还要覆盖 owner、allowedEmails、缺失素材等权限和返回契约，避免以移出事务为由绕过授权。超时测试要检查迟到连接归还、队列清理及连接异常处置。源码 fixture、真实 PostgreSQL 等待环实验和实际站点用户链路分别汇报，本轮文档扩写不冒称已经执行这些业务验证。

### 常见误区

- “DB 没报 deadlock，就没有等待环”：数据库看不到应用池队列的全部依赖，跨层环需要联合观测。
- “最后一条 SQL 是根因”：`idle in transaction` 的最后语句可能早已结束，真正阻塞在后面的应用 await。
- “媒体端点超时，所以一定 NAS 慢”：必须确认执行是否已经到达媒体 I/O，借池之前卡住时媒体超时只是结果。

### 跨业务迁移

电商结算事务里调用需要另借连接的库存 helper，也可能形成类似资源自等待；社交平台在持有内容权限锁时做慢附件读取，则可能把局部媒体问题扩散成权限查询阻塞。共通规则是明确持有什么、等待什么、何时释放；不应把“缩短事务”误解为把必须原子成立的写入随意拆散。
