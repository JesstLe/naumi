## HB-003 有多少用户，为什么不能直接换算成数据库连接数？

### 现场问题

“我们要支持 10 万＋活跃用户，连接池该设多大？”面试官希望你先指出问题里缺少哪些信息。

### 旧模型与反例

旧模型：“一个用户对应一个连接。”反例：大量用户在编辑画布，未访问数据库；少数用户触发高频大字段事务，反而可能占满池。

### 基本事实与不变量

活跃用户、峰值在线、请求速率、任务到达率、在途任务和数据库在用连接是不同量。有限资源要有明确占用时段，等待和重试不能无限积累。

### 推导与参考回答

#### 直接回答

**答案：** 用户数不是数据库需求的单位。要先知道统计窗口内有多少用户实际操作、每次操作产生多少请求和事务、每个事务占连接多久、是否遇到锁等待，以及 Web/Worker 有多少进程。池大小只能在数据库整站连接预算和真实负载下确定。加连接可能减少借池等待，也可能增加 DB CPU、I/O 和锁竞争；大量任务在等供应商时，完全可能只短暂使用数据库连接。

#### 从事实推导

1. 把“10 万活跃用户”展开为可测量的操作分布：在线比例、每人操作频率、生成/编辑/历史查询的比例和突发性。
2. 为每条业务路径画资源时间线：何时借连接、何时等待行锁、何时释放，外部生成等待是否错误地占着事务。
3. 在统计边界一致且稳定流动的前提下，用 Little 定律 `L = λ × W` 估计平均在途数；任务系统与连接池系统应分别选择边界。
4. 同时检查长尾和积压。平均数满足要求，不代表高峰时 p99 延迟、错误率或最长排队时间可接受。
5. 汇总所有进程的业务池、控制面池和运维预留，再通过负载实验选配置与余量，而不是把数据库连接总上限全部分给单个实例。

#### 示例与落地

以下均是教学假设，不是 Naumi 的压测结果：

```text
生成任务：到达率 2 个/秒 × 平均完成 60 秒 ≈ 120 个平均在途任务
数据库占用：每个任务累计借连接 0.1 秒，则该类流量的平均在用连接约 0.2
```

第二行只估计这一类任务的平均占用，不含登录、历史查询、轮询、控制流量和突发，也不据此建议把池设为 1。若用 5 个槽除以每次 0.2 秒，占槽模型的理想化上限约 25 次/秒；它忽略锁、I/O、调度、竞争和长尾，不是 PostgreSQL 吞吐承诺。两个算式要分别解释统计对象，不能把任务耗时直接当数据库持有时间。

#### 面试表达（约90秒）

“我不会从活跃用户数直接定连接池。我先定义工作负载，测到达率、每次事务的连接持有时间、锁等待与尾部延迟，再看所有实例共享的数据库预算。生成并发高不意味着 DB 连接同时高，因为等待供应商时应释放事务。Little 定律适合在稳定边界下理解平均在途数，但实际配置还要留突发和故障余量。我会通过逐步增加到达率观察排队、错误和积压，找到有效吞吐拐点；如果瓶颈是长事务或共享配额，单纯扩池或加实例都不保证变快。”

### 队列解决什么、不解决什么

队列可以吸收短时突发、控制执行并发，但不会凭空增加处理能力。若长期到达率高于可处理速率，积压会增长，需要增加有效能力、减少工作量或采用符合业务的准入与背压策略。队列持久性、最大等待、取消与失败恢复都要明确。

### L1—L4 追问

#### L1 解释：RPS、任务并发与在线人数有什么区别？

**答案：** RPS 是单位时间进入某个入口的请求数，在线人数是某段时间保持在线或活动的用户数，任务并发是在某个时刻尚未完成或正在执行的任务数，还要区分排队与实际执行。一个在线用户可能长时间不发请求，也可能一次点击带来多次上传和轮询。一个长任务可以在没有持续 HTTP 连接时存在。因此报告数字必须说明统计对象、时间窗口和状态口径，不能用“支持几万人”代替 API、任务与数据库各层的容量指标。

#### L2 推导：先改池大小还是减少事务占用？

**答案：** 先找证据，不预设池越大越好或越小越好。若连接长期被媒体读取、外部调用或嵌套借池占着，优先修正事务和资源边界；若 DB 已有高 CPU/I/O 或锁竞争，扩池可能恶化排队。若事务短、连接确实不足且 DB 有明显余量，适度扩池可以有效提高并行度。判断要结合 checkout 等待、在用连接、事务分位时长、DB 负载及锁图，调整后用相同工作负载比较延迟、错误与有效吞吐，而不只看等待队列变短。

#### L3 变式：两倍实例是否两倍吞吐？

**答案：** 只有原瓶颈主要在可以横向扩展的实例本地资源，而且共享依赖有余量时，吞吐才可能接近按实例增长。实际中数据库、对象存储出口、热点行和供应商并发额度可能没有增加，新增实例还会增加连接池总量、轮询和协调竞争。应按“进程数×各进程预算”汇总连接，而非只看容器数。还要验证进程内限流、任务计数和会话状态是否已经共享，否则扩容可能只是把限制放大，甚至产生重复执行。

#### L4 负责：怎样压测？

**答案：** 先定义代表性混合负载和验收目标，再在隔离环境按到达率阶梯加压，避免只用固定并发的闭环客户端掩盖排队。记录端到端与各层 p50/p95/p99、成功率、借池等待、事务与锁时长、任务积压数量和最老年龄、内存/I/O、供应商额度及成本。要覆盖峰值、持续运行、故障恢复和停止加压后的排空。付费上游先用可控模拟测本地调度，再按明确任务做少量真实链路验证；模拟上限不能被写成供应商或生产整站容量。

### 常见误区

- “120 个在途任务就要 120 条连接”：在途时间不等于连接持有时间，先明确系统边界。
- “排进队列就不会崩”：到达率长期大于处理能力，积压、等待和存储仍会增长。
- “平均延迟低就可以满负载运行”：突发、长尾、抖动和故障接管需要余量；饱和附近排队可能迅速恶化。

### 跨业务迁移

电商大促要分别估计浏览、下单、支付和库存热点；社交业务要区分在线连接、发帖、信息流读取和视频处理。Naumi 的供应商长等待与社交长连接都可能持续很久，却不应持续占用数据库事务。共同方法是按资源持有时间建模，具体工作负载和延迟目标仍由业务决定。
