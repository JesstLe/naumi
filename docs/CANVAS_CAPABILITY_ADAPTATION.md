# 画布能力融合原则：学流程，用 Naumi 原生逻辑实现

用户于 2026-10-27 明确确认。后续涉及 infinite-canvas、Toonflow 或其他上游的画布能力研究、设计、开发时，先读本文；旧设计、旧任务总结或上下文压缩不得覆盖本次明确的产品意图。

## 1. 用户原意

> 当初融合这两个项目，是因为它们已经有做视频等能力，以及先怎么样、后怎么样的一套逻辑。我们把这些成熟能力学过来，以自己的画布逻辑和样式实现同样的功能，避免重新凭空构想。对方的一些设置、字段、参数是按对方的画布逻辑设计的，不一定适合我们；要根据我们的画布设计出同样的功能。

一句话：**借鉴成熟能力和业务流程，转化为 Naumi 的原生功能；不是移植上游页面、字段模型或整套运行系统。**

## 2. 什么要学，什么要重新设计

| 对象 | 做法 |
|---|---|
| 用户要完成的创作任务、输入与输出 | 先看上游实际源码和操作链路，弄清功能目的与完成标准 |
| 先后步骤、依赖关系、引用角色、必要判断、失败反馈 | 吸收已经实现的成熟业务经验，避免凭空重设计或只抄按钮 |
| 决定结果的真实参数，例如机位、姿势、时长、分辨率、首尾帧 | 保留业务含义与真实约束；依据 Naumi 的布局和交互重新表达 |
| 对方节点 ID、状态字段、引用结构、浏览器持久化协议 | 映射到 Naumi 已有数据、权限、任务与存储体系，不强求字段一一对应 |
| 对方专属面板、额外输入、重复设置 | 先检查是否已能由我们的节点、连线、`@`、选择和创作栏表达；已有能力直接复用 |
| 算法、几何计算、协议适配等具体实现 | 在适配性清楚、来源明确时复用；复用代码不代表照搬产品结构 |
| UI、页面路由、独立账号/存储/任务系统 | 使用 Naumi 现有样式与公共能力；不把嵌入上游整页或换皮当作融合完成 |

**功能等价不要求界面、字段、控件数量或操作入口相同。去掉不适用字段也不等于删掉用户能力。**

## 3. 先盘点自己的能力，再设计缺口

1. 说明用户最终要得到什么，以及上游真实的输入→操作→结果链路。
2. 沿当前固定版本 Naumi 源码核对已有节点、连线、`@`、创作栏、媒体/作品、任务、计费和恢复机制。
3. 区分“已有完整入口”“底层已有但缺入口或交互”“有相近功能但用途不同”“确实没有”。
4. 为确有缺口的部分设计 Naumi 原生操作，不重复建立已有体系。
5. 按完整可用切片实现和集中验证；输出能在原画布里继续创作，才算形成闭环。

先保留真实模型与供应商所需的业务含义，再决定用户看见哪些控制项。内部映射和派生信息由代码处理，不转成让用户反复填写的字段。

## 4. 当前必须保持的几个区分

- **3D 导演台 ≠ 3D 产品工作台。** 前者侧重角色/场景/机位与镜头预演；后者侧重瓶罐/包装等产品网格、材质和渲染。可复用底层，不可通过改名或单纯跳转冒充同一能力。
- **音频引用/音轨提取 ≠ 独立音频创作节点。** 有处理链路不代表添加节点、编辑、连接和恢复交互都已完成。
- **视频播放器时间轴/任务阶段调度 ≠ 多轨编辑器。** 播放进度条、分镜计划和真正的轨道素材剪辑分开核验。
- **上游有能力 ≠ 历史融合分支已实现 ≠ 当前 main 仍有完整入口 ≠ 线上已验收。** 每层分别给证据。
- **菜单置灰占位不表示完全没有底层能力。** 后续必须先盘点，再判断应复用、补入口还是新增实现。
- 2026-10-13 视频融合曾把 Director3D 编辑器排除在当时交付矩阵之外；这是历史任务边界，不是永久排除能力。后续按本原则重新设计，不机械嵌入其旧界面。
