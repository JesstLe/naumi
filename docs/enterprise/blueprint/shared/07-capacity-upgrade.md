# 4核8GB起步、容量验证、增配与拆机路线

## 1. 事实、假设与取舍

- **用户确认**：服务器目前4核8GB，必要可升级。不是必须把所有模块永久塞进这台机器。
- **历史仓库证据**：`docs/changes/2026-10-14-mainland-47-preparation.md`记过47为4vCPU/7270MiB。这不等于当前主机余量；本轮未SSH核验，也不假定这台就是所有企业流量的最终目标。
- **待实测**：服务清单、峰值RSS/cgroup、MemAvailable、CPU/磁盘/数据库连接、用户并发、媒体作业、蓝绿双槽占用。先只读采样，不能通过停现有服务腾空间做“验收”。
- **架构原则**：32模块按领域分组，初期少量进程；小机器只限制并发和部署形态，不省责任/权限/审计/版本。资源不足先增配，不降低业务正确性。

## 2. 初期新增常驻预算（建议上限，非测量结果）

| 新增/增量组件 | 常驻预算 | CPU/并发起点 | 备注 |
| --- | --- | --- | --- |
| 企业BFF/页面增量 | 256MiB | 复用现有企业UI槽优先 | 如果完整Next进程超过预算，必须按实测上调而不是强杀 |
| 独立workflow API | 384MiB | 事件循环、短事务；池4 | Node heap可先192—256MiB，容器含native余量 |
| 通知/同步/轻报表worker | 192MiB | 最多2个轻量作业；批次有限 | 耗CPU媒体处理不在这个预算内 |
| PostgreSQL增量工作集 | 384MiB | 新模块池合计建议≤10 | 复用实例可共存但独立库/角色；实际缓存/查询峰值另测 |
| **合计** | **1216MiB≈1.19GiB** | 启动参数待压测 | 落在M32的1.0—1.4GiB新增目标内 |

额外发布峰值：新BFF256+新API384+迁移/验证暂态256≈896MiB（约0.88GiB）。worker保持单活/受控领取，不为了蓝绿复制所有重作业。实际若完整UI/镜像启动峰值更高，以实测p99峰值替换预算。

这些数字不包含已有Naumi、Hub、工作台、现有PostgreSQL/Redis、系统和媒体worker。不能把表格相加后就宣称整机足够；必须先测已有占用。

## 3. 发布准入计算

同一口径：

`实际MemTotal ≥ 既有全机基线已用峰值 + 新增常驻峰值 + 蓝绿额外峰值 + 安全余量`

既有基线包含OS/既有缓存/服务，不重复另算OS。安全余量建议至少1GiB且不低于实际内存15%，取更大；使用稳定采样/容器峰值与MemAvailable对照，不把进程RSS简单相加冒充精确可用内存。

若当前可用不足约“新增1216 + 双槽896 + 安全1024MiB”这一建议规划空间，优先评估复用、限后台或升配；**不能先停在线旧槽腾空间再发新槽**。同理磁盘须容纳候选、当前+回滚版本、备份和临时文件，沿项目80%/10GiB门槛处理。

## 4. 数据库与队列限制

- 新模块连接池建议：BFF2、workflow4、worker2、轻报表2，常驻上限10；蓝绿额外BFF2+workflow4，总16。先核全机existing+16是否在max_connections扣除运维和回滚保留后可承受。
- 不默认每个“模块”各开10连接。长报表有专用受限池，不能吃光交易连接。
- 初始建议连接等待2秒、锁等待3秒、短查询/事务目标10秒内；外部HTTP不在持数据库锁时无限等待。当前代码有锁/语句timeout，远程resolver还需额外超时。
- 通知/组织/主数据同步按通道分队列，轻任务总并发1—2起步；媒体转码/大包生成最多1项受控或外置，CPU负载高暂停新重任务。
- API列表默认20、上限100建议值；全量导出异步分块、限内存，不把大文件Buffer驻留主Web进程。
- PostgreSQL outbox/inbox、索引/日汇总足够起步；没有证据前不引入Kafka、ES、ClickHouse、独立向量数据库或Kubernetes。

## 5. 只读盘点与隔离压测

上线前由运维在明确目标主机执行只读盘点：`nproc`、`free -m`、`df -h`、`docker stats --no-stream`、服务清单和PG连接/慢查询；不输出env、密钥或数据库连接串。
采样至少覆盖代表性业务高峰及一次发布窗口，具体周期由公司流量节奏决定。先用隔离测试库/对象存储桶，禁真实通知、扣费、上架。

**压测档位是场景参数，不是承诺承载人数**：

| 档位 | 模拟在线交互用户 | 目标请求形态 | 用途 |
| --- | --- | --- | --- |
| L1 | 30 | 列表/提单/认领，约5 RPS起 | 验证正确性和瓶颈 |
| L2 | 100 | 约15 RPS，含10%命令、列表分页 | 试点峰值探索 |
| L3 | 300 | 约40 RPS，含任务竞争/后台投影 | 观察是否先增配，非必须在4核8GB通过 |

用户数不能直接换算RPS，脚本需设思考时间并报告实测到达率、成功率和并发连接；多标签页面/大画布资源负载另设场景。
测试数据建议至少2企业、20团队、1万SKU/5万任务历史、资产只用非敏感样本；按实际增长重新校准。聚合数据只用于性能，不冒充公司真实规模。

候选SLO（待公司批准）：交互读/写p95≤800ms/1.5s、非预期限流错误<0.5%、事件投影p95≤60s；上传/AI/压缩包/外部平台等待单列。先测再承诺，不用一次健康200证明达标。

## 6. 升级触发条件（建议，需结合基线）

- 有代表性高峰CPU持续>70%约30分钟并伴业务p95超标，排除坏查询/死循环后仍存在。
- MemAvailable持续<15%、OOM出现、常态使用swap导致尾延迟，或已无法保留双槽发布余量。
- 数据库连接等待、IO/锁竞争持续影响交易；新增索引/分页/限报表后仍未改善。
- 通知/同步/outbox最老积压持续越过获批SLO，且限流来自本机而非外部平台。
- 媒体处理/报表明显抢占登录/提单；磁盘空间/IO成为主要瓶颈。

OOM/数据损坏风险立即处置，不必等30分钟。升级不是替代排查；外部平台限流不能靠加CPU解决。

## 7. 三段扩展路线

### U1：优先增配8核16GB
适用于全机资源普遍紧张且业务量尚可单机管理。保持域接口和独立库/角色，恢复双槽余量；目标不是保证“升级即无限扩展”。云规格升级可能需重启，需新机/旁路候选或获批维护窗口，不能假定热升级无感。

### U2：拆媒体/后台worker
CPU重任务、预览/视频/大包/报表独立节点；Web/工作流优先低延迟。用持久租约/幂等/inbox保证单一有效领取者，原收费任务固定原作业ID恢复，不复制重跑。

### U3：数据库与Web/API分机或托管
先备份/恢复演练，再复制到新库并对账；测试候选只读/隔离，切换时维护单写者。换连接配置按蓝绿发布，旧写者排空和租约收回；回退不能直接用旧库覆盖新写入。
后续按瓶颈独立报表读库，队列/搜索技术替换有明确收益再引入；业务ID、事件契约和权限边界保持稳定。

## 8. 发布/备份的最低要求

目标站最新AGENTS/部署手册优先于历史地址；不连接废弃主机。47若为目标则持Naumi/Hub/参考工作台全部三锁，其他站按其最新要求。
固定镜像构建在本地/CI/隔离构建机，生产不临时重型编译。旁路验证登录/DB/资产/真实命令、新旧JS兼容、队列/租约；排空旧槽后才停。
备份保存到受控独立位置，定期在隔离实例恢复并核对私有媒体引用。RPO/RTO暂不承诺数值，先按公司容忍度设目标并用演练验证。

本文件是容量设计，不是本轮已完成主机检测/压测/扩容的记录。
