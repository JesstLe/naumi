# 可评审样例：系统需求表、按表归属与任务计划

本文件是用于讨论和开发验收的合成样例，不是公司真实表结构。拿现有钉钉表头后逐项映射；不得直接用样例覆盖公司现有需求字段。

## 1. 新品详情页表单字段表

| 分组/字段 | 控件/类型 | 必填与校验 | 参与归属/后续用途 |
| --- | --- | --- | --- |
| 业务归属/事业部 | 受控选项，由授权与店铺归属派生 | 必填，不接受任意字符串 | route.businessUnitId |
| 业务归属/品牌 | 品牌ID | 必填；必须可服务该店铺 | route.brandId |
| 业务归属/店铺 | shopId；跨店需求拆行或明确集合 | 必填；不得含越权店铺 | route.shopId优先 |
| 业务归属/需求类型 | enum：主视觉/详情页/精修/适配等 | 必填，枚举版本化 | route.demandType |
| 商品/商品与SKU | productId+skuIds，版本引用 | 每行需映射；多SKU不混规格 | 输入资料及交付对应关系 |
| 背景/使用位置 | 商品页/活动页/广告位等枚举+补充 | 必填；影响规格/规范 | 模板/平台检查 |
| 内容/目标及卖点 | 限长结构化条目+说明 | 必填；来源/审核状态可见 | brief/内容合规 |
| 内容/参考稿 | 私有assetRevisionIds | 按模板选填；不等于可商用授权 | 制作参考 |
| 交付/数量、尺寸、格式 | 每交付类型一行，不混自由文本 | 必填；单位明确 | task.specs/验收清单 |
| 交付/源文件要求 | 是/否+格式；false是明确值 | 必填，不能把false覆盖成默认true | 交付manifest |

| 责任/需求负责人 | 有权运营人员ID | 必填，代提人自动另记 | 资料补充/业务签收 |

服务端字段：requesterId、enterpriseId、submittedAt、formVersion、sourceKey、commandId、routeDecision、status、version。浏览器可以显示但不能自行决定身份/权限/最终归属。

## 2. 同一次提单的三种责任

- 需求负责人O：补充商品/活动信息，确认业务内容与签收。
- 承接团队T与受理主管L：判断资料是否可做，拆解、承诺排期、安排执行。
- 执行人D/A：认领/确认后承担具体任务，按标准提交；验收由指定他人完成。

字段建议：businessOwnerId、intakeTeamId、intakeOwnerId、taskResponsibleTeamId、assigneeId、reviewerId、deliveryReceiverId。它们不是一个ownerEmail的不同显示名。

## 3. 路由规则样例

```json
{
  "ruleId": "RULE_SHOP_DETAIL_EXAMPLE",
  "revision": 3,
  "priority": 300,
  "scope": { "enterpriseId": "EXAMPLE_ENTERPRISE" },
  "when": { "shopId": "SHOP_A", "demandType": "detail-page" },
  "then": {
    "intakeTeamId": "CREATIVE_TEAM_A",
    "intakeRoleId": "INTAKE_LEAD",
    "reviewerRoleId": "BRAND_REVIEWER",
    "slaTemplateId": "SLA_APPROVED_BY_COMPANY"
  },
  "effectiveAt": "2026-10-16T00:00:00Z"
}
```

这是规则表达形式建议，不是现有API可执行载荷。priority数值只是样例，其范围/排序由M31定义并经公司批准；不能与岗位level混用。

### 执行算法
1. 验证提交人能使用所选企业/店铺/商品；补齐服务器派生的品牌/事业部。
2. 读取一版已批准且已生效规则集，使用同一快照匹配，过滤不合法scope。
3. 按明确优先级/特异性选择最高层级；同优先级多命中视为冲突，不按数组顺序随机选择。
4. 选中规则的承接团队/岗位失效时进入待分配，不悄悄落到低优先级扩大服务范围。
5. 未命中只有在明确配置且获权的公共承接池才路由过去；否则待分配队列负责。
6. 同一事务保存原始输入摘要、规则版本、命中/拒绝解释、决策结果与单据版本；生成受理事件。

规则变更不重路由已批准/开工单据；需要调整的由M12批准变更。预览后到提交前规则升级时，提交响应告知最终结果与变化，不能让员工误以为固定到旧组。

## 4. 预期路由测试样例

| 用例 | 输入 | 结果 |
| --- | --- | --- |
| R01 | SHOP_A+detail-page，唯一有效规则 | 团队A，记录revision3 |
| R02 | 同输入两个同优先级规则 | 待分配+RULE_CONFLICT，不派人 |
| R03 | 未覆盖店铺/类型 | 待分配+NO_RULE，通知值班主管 |
| R04 | 命中团队A已停用 | 待分配+TARGET_INACTIVE，不自动转全公司池 |
| R05 | 运营选了无权店铺 | 403，不允许通过补全字段绕过 |
| R06 | 规则升级后重放旧commandId | 按幂等返回原结果，仍检查当前可见性 |
| R07 | 低优先级宽规则与高优先级店铺规则 | 唯一选高优先级；说明所有命中与取舍 |

## 5. 批准后的任务计划样例

| 任务 | 类型/前置 | 交付规格 | 执行分配 | 验收 |
| --- | --- | --- | --- | --- |
| T1 主视觉 | design，无前置 | 一版批准视觉+源文件 | 主管指派，设计师确认 | 设计/品牌指定角色 |
| T2 商品精修 | artwork，无前置 | 每SKU指定原图/透明底/尺寸 | 美工任务池认领 | 指定美工审核人 |
| T3 详情排版 | artwork，依赖T1/T2验收 | 分段长图+源文件+文案清单 | 前置完成后开放认领 | 运营内容确认+他人终审 |
| T4 渠道适配 | artwork，依赖T1验收 | 各店铺/位置独立规格 | 承接组按服务范围安排 | 平台规格清单 |

点数/期限/质量等级不在本样例拍定；主管按M08标准和M09产能校准后冻结。T1共用给T3/T4不重复算完整原创工作，T3/T4只记录新增排版/适配贡献。
