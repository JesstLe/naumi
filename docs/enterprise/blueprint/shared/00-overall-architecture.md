# 总体方案：电商公司的需求—生产—交付—绩效闭环

## 1. 建设目标与已确认事实

本系统首先是公司的运营与设计生产协作平台，Naumi创作能力是执行工具之一；不是把现有AI生成历史换个名字叫工单。

已确认：公司使用钉钉、聚水潭及其他待盘点系统；运营现在在钉钉填需求表；目标改为在本系统直接填表，按表单字段决定任务归属。钉钉拟承接身份/组织和提醒，聚水潭拟提供店铺/商品/SKU。API授权、字段能力、公司具体组织与业务制度尚未确认。

当前4核8GB，必要可升级。因此采用“业务模型完整、实现分阶段、部署轻量化、瓶颈出现后扩容/拆分”，不为了小机器省掉责任、权限、审计和绩效证据。

## 2. 平台边界

纳入：组织映射、业务权限、需求表单、归属/受理、任务拆解、排期、派单/认领、进度/阻塞、素材/创作、评审/验收、发布回执、贡献/绩效、通知、报表、连接器、审计/运维。

不重建：聚水潭的订单、库存、采购、仓储、财务；钉钉的通用通讯录/考勤/聊天；专业设计软件；薪酬发放；平台自身商家后台。必要时通过授权接口引用结果，数据所有权不迁入本系统。

## 3. 四条核心链

### 业务责任链
提单人 → 运营需求负责人 → 承接团队/受理主管 → 执行人 → 评审人 → 最终验收人 → 业务签收人。

这些角色可以兼任但不能混为同字段；执行人不验收本人任务。业务需求负责人不因交给设计中心就失去补充资料和确认卖点的责任。

### 数据链
钉钉身份/组织 → 本地用户/任职映射；聚水潭店铺/商品 → 本地主数据/映射版本；系统表单 → 归属决策 → 工单/任务 → 资产版本/验收事件 → 贡献事实/周期快照。

任务事实为系统内原生记录，不再把钉钉表和本地库设为两个同时可写权威。切换前历史表只做来源与迁移证据，切换后新增需求在本系统创建。

### 内容链
产品资料/品牌规范 → 授权素材 → 制作候选稿 → 评审轮次 → 批准交付包 → 各渠道发布实例 → 使用/效果复盘。

保存文件≠提交评审≠验收≠业务签收≠外部发布成功，各状态与责任必须分开。

### 绩效链
任务点数/规格冻结 → 执行/交接区间 → 评审与返工归因 → 验收事实 → 去重贡献投影 → 规则试算 → 员工查证 → 主管/独立复核 → 周期锁定。

绩效事实从第一期记录，最终制度在真实样本校准后推出。相关性经营数据不直接变成人员评分。

## 5. 核心设计决策

1. **按表归属，不按员工姓名硬派。** 品牌/店铺/类型决定受理队列；执行人由主管派单或认领。
2. **单一权威，显式来源。** 外部同步更新来源层；人工批准资料/规则优先。未知、false、0和禁用不混淆。
3. **强一致留在域内。** 同一工作流事务写工单、命令去重和事件；资产/组织外部依赖用版本化快照与执行时核验。
4. **跨域最终一致但可对账。** outbox/inbox至少一次，事件有版本、水位和异常队列，不宣称分布式恰好一次。
5. **所有副作用可追踪。** 付费生成/外部上架请求已接受或unknown时先查，不自动重放。
6. **先权限再呈现。** 搜索、任务池、媒体、导出和报表均服务端裁剪，不能只隐藏按钮。
7. **版本冻结。** 表单、归属、规格、点数、规范、交付、绩效规则都能还原当时版本。
8. **扩容优于偷减业务。** 资源不足先控后台并发/增配，不能取消审计、备份或蓝绿余量。

## 7. 使用与治理机制

- 公司设一名业务产品负责人，统一表单、状态、归属和口径；部门主管作为业务流程责任人。
- 每个模块有owner，模块变更回到本目录更新，不凭聊天记忆推进。
- 第一批选一个有代表性的运营组及设计/美工承接组，试点包括正常单、返工单、急单和跨组单。
- 首期不要求所有外部接口齐备：审核导入主数据+原生需求表+受控通知即可跑通；缺接口影响效率，不阻断责任闭环。
- 每个大阶段集中验收，合同/外部授权/绩效制度/发布分别过门槛，不把文档完成当功能完成。
