# M17 最终验收、交付包、签收与结项

服务域：工作流｜阶段：P1｜上游：D07、D08、D09｜依赖：M13、M16

## 1. 使用场景与责任
审核人逐项确认任务符合承诺标准；运营收到明确可用的文件和版本；主管看到需求是否真正完成。任务验收、文件签收、渠道发布是三个不同动作。

## 2. 功能与页面
- 验收清单、最终稿/源文件包、版本manifest、验收意见、业务签收和结项摘要。
- 自动核对交付格式/尺寸/数量；业务内容由指定角色确认。
- 交付包指向不可变revision及hash，下载包可异步生成；大包不在Web请求内同步压缩。
- 已验收纠错提供补交/撤销申请与新事实，不直接编辑旧验收结果。

## 3. 数据获取与关键字段
| 字段 | 类型及规则 | 来源 |
| --- | --- | --- |
| acceptanceId / taskId / aggregateVersion | 一次终审事实及对应任务版本 | 验收事务 |
| acceptedRevisionIds / manifestHash | 文件版本和包内容证明 | M13 |
| checklistSnapshot / reviewRoundIds | 当时标准和评审依据 | M08/M16 |
| acceptedBy / qualityLevel / acceptedAt | 审核人、质量等级、服务端时间 | 终审命令 |
| submittedAt / baselineDueAt / changeRefs | 按时性所需事实，保留原/新基线 | M11/M12 |
| deliveryReceiptId / receiverId / receivedAt | 业务签收，不与审核混同 | 运营签收 |

## 4. 流程与状态
任务 `review → accepted`；所有任务accepted才工单completed。验收事务写入事件，重复命令只能产生一次验收事实。
交付包 `待生成 → 可下载 → 已签收/被替代`；下载失败不取消已经成立的验收事实，而是形成交付故障待办。已验收但待业务签收清楚显示。

## 5. 跨模块联动
M06更新需求完成度，M09释放任务容量，M18取得可发布版本，M19通知签收，M21/M22接收验收证据，M24做交付指标。任务取消不能删除此前已接受的事实。

## 6. 权限与规则
终审权限和下载权限分开。验收者不得为执行人；缺必要审核、缺源文件、资产隔离或授权到期时拒绝终审。验收后文件替换必须产生新包/新版本，运营能看到哪个是当前批准稿。

## 7. 接口与事件（拟定）
v1已有 `accept-delivery`；拟增 `POST /api/enterprise/v2/delivery-packages`、`POST .../{id}:acknowledge`。
产生现有 `workflow.task.accepted.v1` 及拟定 `delivery.receipt.confirmed.v1`；M21/M22按eventId去重，不能根据UI重复点击累加贡献。

## 8. 异常与验收
- 同一commandId重试只有一条accepted事件；不同命令不能重复验收已接受任务。
- 撤回后的发布计划停止新发布，既有发布由M18受控召回；已锁绩效产生调整版本。
- 文件包hash与manifest一致；缩略图可用而源文件丢失不算完整交付。
- 延迟验收与员工晚交分别可计算；需求整体完成不代替各任务验收证据。

## 9. 实现边界
v1验收已记录点数/贡献人/质量/期限/时间/返工与资产ID；尚无签收、manifest、资产权利复核、多角色终审和冲销模型。

## 10. 开发工作包（本模块实施清单）
- **M17-W01** 数据：建立验收/交付manifest/签收记录与冲销引用，冻结source文件hash。
- **M17-W02** 后端：终验核资产/规范/必要评审并原子发事实；异步包失败不改既有验收。
- **M17-W03** 前端：实现最终清单/质量说明/交付包/签收和当前批准稿标识。
- **M17-W04** 验收：重复验收只一事实、缺源文件拒绝、包hash一致、迟到验收与晚提交分离。
