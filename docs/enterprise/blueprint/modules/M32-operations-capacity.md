# M32 部署运维、资源容量、蓝绿发布与升级路线

服务域：运行平台｜阶段：P1并贯穿后续｜上游：D15｜依赖：M02、M29

## 1. 已确认条件与目标
用户确认当前服务器4核8GB，必要时可升级；不为节省资源破坏业务完整性。当前主机归属/全部在用容器、实际可用内存和流量尚未在本轮远程核验，不能把标称8GB当空闲预算。
仓库10月14日47准备记录曾显示4vCPU/7270MiB；这是历史记录，不是当前余量。实施前只读重测，保留已有Naumi/工作台/数据库/供应商执行器。

## 2. 功能与运维台
- 服务版本、真实就绪、CPU/内存/磁盘、数据库连接/慢查询、任务租约、outbox积压、外部API限流和备份恢复记录。
- 发布固定镜像、配置指纹、部署锁、旁路验证、平滑切流、排空/回退。
- 按模块隔离队列和并发，优先保住登录/提单/认领/验收；报告/预览/转码可降速。

## 3. 数据获取与关键字段
| 字段 | 类型及规则 | 来源 |
| --- | --- | --- |
| hostId / totalMemory / availableMemory | 系统实测，保留单位 | Linux/proc与容器指标 |
| service / slot / imageDigest / sourceSha | 固定候选与在线基线 | 容器/版本接口 |
| cpu / rss / cgroupPeak / oomKills | 区分进程与容器峰值 | D15 |
| dbConnections / queryP95 / lockWait | 池统计与数据库事实 | PostgreSQL |
| activeJobs / leases / queueOldestAge | 在途任务与排空依据 | 各worker |
| backupId / restoredAt / checksum | 备份可读和演练证明 | 运维作业 |

## 4. 初期部署形态
32逻辑模块先放少量部署单元：企业BFF/页面、独立工作流API、轻量worker；组织/资产经现有服务适配，独立逻辑库/凭据可暂共用现有PostgreSQL实例。绩效/报表先轻量worker+读模型，资源不足再独立部署。
不上Kubernetes/Kafka/ES，不做服务器重型构建；CI/隔离构建后传固定镜像。媒体大任务独立worker限流，服务器不跑本地大模型。

## 5. 资源预算与扩容
详见共享容量文档。4核8GB上的新增常驻目标约1.0—1.4GiB，新增蓝绿临时峰值约0.8—1.2GiB，均为待压测校准的预算，不是已测占用；已有服务若吃满预算，应先升级而不是强挤上线。
可先升8核16GB，再按瓶颈拆数据库、媒体worker和报表；是否升级由持续指标、峰值排队与双槽发布余量决定，不按员工总人数直接估算。

## 6. 发布、故障与恢复
每次服务器更新蓝绿：持目标全部锁→刷新在线基线/备份→新槽旁路→真实登录/DB/资产/命令验收→nginx语法检查和平滑reload→旧连接/租约/任务排空→只停已排空旧槽。
失败保留旧槽；回退只切程序/兼容入口，不回灌数据库、不重发已接受/unknown付费作业。数据库先扩展、回填，再等窗口结束收缩。

## 7. 权限与接口
指标/管理入口仅运维授权；不公开数据库/worker端口。`/healthz`存活、`/readyz`依赖就绪、版本接口固定SHA；就绪还需真实业务探针，不以HTTP200代替。

## 8. 异常与验收
- CPU/内存压力下优先限制后台队列，登录/认领仍达成获批SLO。
- 新槽失败不影响旧槽；发布过程中双槽无OOM；unknown worker状态不能当已排空。
- 备份在独立实例恢复并核对权限、工单、事件、私有媒体引用；RPO/RTO先演练再承诺。
- 扩容/拆机按复制水位、单写者切换、校验和回退演练执行，不能同时启动两个收费任务领取器。

## 9. 实现边界
本轮不SSH、不部署、不压生产。主机真实余量、容量测试和升级预算待执行；方案写出门槛与路径，不宣称当前机器可承载全公司峰值。

## 10. 开发工作包（本模块实施清单）
- **M32-W01** 数据：采集当前主机/容器/DB/队列基线及峰值，登记镜像SHA/槽位/备份恢复证据。
- **M32-W02** 后端：配置受限池/worker/timeout、就绪/排空/租约指标，生产不重型构建。
- **M32-W03** 前端：运维面板仅展示必要健康/版本/积压/资源与发布审计，不公开内部端口。
- **M32-W04** 验收：隔离压测+双槽峰值+故障切回+备份恢复，资源不足先增配再试点。
