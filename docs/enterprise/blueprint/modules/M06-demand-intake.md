# M06 需求填报、受理与历史钉钉表迁移

服务域：工作流｜阶段：P1｜上游：D06、D07｜依赖：M03、M05、M13

## 1. 使用场景与责任
运营在Naumi填需求表；需求负责人跟进业务信息，受理主管判断是否可执行。钉钉保留消息入口和历史追溯，避免员工双重填表。

## 2. 功能与页面
- 我的需求、代提需求、新需求、保存/恢复草稿、需求详情、退回补充和状态时间线。
- 提交展示必填缺失、商品资料有效性、预计归属与截止风险；提交成功后返回业务号和内部链接。
- 允许批量录入多个SKU任务，但逐条标明对应交付物；批量提交返回成功/失败逐行回执。
- 历史钉钉需求只迁未结单或经确认的范围；原记录ID和链接留作来源，不把历史完成单当新待办。

## 3. 数据获取与关键字段
| 字段 | 类型及规则 | 来源 |
| --- | --- | --- |
| requirementId / businessNo | UUID+便于沟通的编号 | 本地生成 |
| requesterId / businessOwnerId | 提交人和业务负责人分离；代提需记录 | 登录身份+表单 |
| formSnapshot / productSnapshot | 冻结表单版本与商品关键资料 | M05、M03 |
| sourceSystem / sourceRecordId | local或dingtalk；来源组合键唯一 | D06/D07 |
| desiredDueAt / submittedAt | 期望截止和实际提交时间 | 用户/服务端 |
| version / routeDecisionId | 聚合版本和归属决策引用 | 本地工作流 |

## 4. 流程与状态
沿用工单 `draft → submitted → approved → active → completed → archived`；退回变draft并保留原因。新建和提交均有commandId，连点/网络重试不多建单。
受理不是开工：先确认信息和责任，再拆任务发布；运营在“待受理”阶段能看到谁负责处理，不看到虚假的执行百分比。

## 5. 跨模块联动
提交后M07做服务端路由和审核；批准后M08拆单，M19发站内/钉钉通知。M12处理已发布需求变更；M17最终交付；M24统计需求吞吐和等待时长。

## 6. 权限与规则
需求人只能关联有权使用的店铺/素材；代提人不能替验收人确认。管理员补录须标记补录及原始时间，不回填伪造在线提交时间。取消不删除历史交付事实。

## 7. 接口与事件（拟定）
兼容现有 `POST /v1/commands` create/submit-requirement；新增BFF `POST /api/enterprise/v2/requirements` 屏蔽内部身份。
产生现有 `workflow.submit-requirement.v1`；M07/M19消费。拟增表单来源字段不能直接塞入现有strict action，必须升级契约。

## 8. 异常与验收
- 同钉钉来源重复导入不重复建单；关闭切换点后钉钉旧表产生新记录进入人工提醒而非双写。
- 附件未上传完成、商品未确认或归属规则缺失时有清楚的待处理状态。
- 草稿断网恢复、重复提交、退回补充、越权店铺、代提和导入回滚分别验收。
- 导入预演逐行对账：原未结数量=迁入+拒绝+待确认，不能只报告API200。

## 9. 实现边界
v1已有需求状态机，尚无业务表单/列表/迁移适配。历史钉钉字段和开放能力待拿真实样本；正式切换按部门试点，钉钉历史只读保留。

## 10. 开发工作包（本模块实施清单）
- **M06-W01** 数据：扩展需求的formSnapshot/sourceKey/businessOwner，建立来源记录唯一约束和业务编号。
- **M06-W02** 后端：将创建/提交/退回命令接入BFF和幂等事务；旧表未结导入不自动发布任务。
- **M06-W03** 前端：实现我的需求/代提/草稿/退回补充/详情时间线和逐行批量回执。
- **M06-W04** 验收：弱网重复提交一单、来源导入守恒、切换水位和旧表只读链路验证。
