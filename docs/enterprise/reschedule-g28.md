# G28 周排期拖拽改期与影响核对

## 目标及数据口径

沿18482原产品、原正式周视图、同一order/task/version实现改期，不增加第二份任务。桌面拖动任务在某一天的卡片至同执行人/同团队的另一日期，按拖动日期差平移整个计划，保留跨度、预计工时、执行人、承诺截止、标签、自定义字段和交付/验收数据。跨人员或跨团队拖放拒绝，分配/交接沿既有流程。手机、键盘及跨周操作使用每张可编辑卡片的“改期”按钮，直接选择新的开始日期。

只有承接团队dispatch可改approved/active需求中的未验收且无待交接任务；普通员工和来源团队只读。未排期任务沿原“编辑计划”填写，不猜测开始日期。拖动不会直接写入，也不会静默覆盖已被他人更新的任务。

## 预览合同

POST /v1/plan-move/preview，正式BFF action=plan-move-preview。
输入orderId/taskId/expectedVersion/targetStart/reason，严格字段，日期YYYY-MM-DD，原因1–2000字。

服务端在一致读取快照中核验当前成员、团队、dispatch、任务状态及order版本；根据旧计划跨度推导结束日期。只查询同执行团队同执行人、与旧/新区间相交且仍计入周排期的任务；最多1000项，超过明确要求缩小安排，不截断。复用团队日历工时分配及个人容量上限；旧schema8使用原自然日口径，个人开关关闭时不读取个人容量。未分配任务显示汇总工时、不冒充某个人的容量。

返回原计划/目标计划、逐日原负载/调整后负载/有效容量、超载日期、整段无工作日、超承诺日期和同需求前后置任务计划冲突。影响覆盖完整旧/新区间，非仅本周。个人原因不返回。计划冲突为参考提示，不改变执行依赖规则，也不自动挪动其他任务。

previewHash绑定主体/输入/当前订单版本/相交任务版本/日历和容量版本及依赖信息。预览零写入。确认沿原POST /v1/commands的move-task-plan动作，携带同日期/原因/previewHash/acknowledged=true，事务内重新读取影响并比对。目标订单CAS保证改期与执行进度不互相覆盖；其它负载是确认时读取的参考快照，不是跨订单容量预约/强制排他锁，之后其他任务或日历改变仍会影响负载。

## 交互与错误

拖放后显示日期输入及原因，先“预览影响”后“确认改期”，有风险时必须勾选已核对提示。无风险也需明确确认。原卡片不先移动，成功后重读原周视图及详情。失败保留日期和原因；409重新读取最新任务并保留目标日期和原因后重新预览，不自动提交。结果未知时保留原commandId，仅原命令重试，禁止改正文重放。关闭、切团队、切账号或离开页面丢弃迟到响应；未知提交关闭后需在原任务核对结果，不宣称跨刷新自动续传。

## 验收及实际边界

集中验证真实命令建任务、预览零写入、平移跨度/工时/执行人/截止/字段不变、旧新区间负载/日历/个人容量、无工作日与依赖提示、同日拒绝、非法/溢出日期、1000项上限、源团队/普通员工/撤权、CAS/预览过期/幂等重放/事件故障回滚。原生浏览器验证同组拖放、跨组拒绝、按钮/键盘、跨周、确认前不写、实际保存刷新、手机390px、换号/关闭、BFF来源与同源权限。

无DDL迁移；真实schema8与364行/292附件保持，真实身份及公司日历不生成。本模块不改Naumi登录桥接、薪酬、原表或正式生产。整体目标ACTIVE。
