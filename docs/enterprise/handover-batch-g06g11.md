# G06 执行交接与 G11 批量任务操作

## 目标与数据约束

保留原18482页面，不建立第二套产品。正式操作沿用Naumi会话、企业/团队绑定、order版本与不可变事件；Excel姓名不是账号。本文记录本增量设计和实现状态，实际公司绑定与部署另验收。

## 执行交接

1. dispatch主管对制作中、阻塞中、待返工任务发起交接，选择当前团队有效且工种匹配的执行成员；必填原因，禁止交给原执行人。
2. 待接收期间保持原执行人、进度、状态、计划及文件版本不变；冻结开始/进度/阻塞/恢复/提交及新文件上传。主管仍可编辑计划或取消整单。
3. 目标本人确认接收或填写原因拒绝，主管可撤销。所有命令携带handoverId和order.expectedVersion，防止旧窗口确认新交接。
4. 接收时再次验证实时成员/工种，保留startedAt与历史文件，追加不可变交接历史再更换执行人。拒绝/撤销解除冻结但不改变执行人。每次交接均留历史。
5. 待接收成员可在“待我接收”找到任务。成功交接的历史参与者保留同企业同团队只读可见；退组/停用仍拒绝。拒绝后的候选人不因曾获邀请永久获得权限。
6. 任何成功交接参与者均不得自验收。验收后记录参与账号、交接履历、attributionStatus=needs-review、contributionBps=null；不把100%绩效默认给最后执行人。无交接任务保持现有10000基点事实。分摊审核属于G12后续，不自动算薪酬。

## 批量边界与事务

- 首批支持批量指派待认领任务、批量修改排期标签，最多50项；不包含批量认领、验收或身份映射。
- 浏览器仅选当前页，不隐式选中跨页任务；切企业/团队清空选择和内存回执。
- POST batch-preview提交batchId、任务ID/orderID/expectedVersion、操作和原因。服务端按order分组，检查可见性、权限、版本、状态、目标工种或标签定义，返回每组影响前后值、固定commandId和错误。
- 预览不写库、不预约版本。确认逐组提交返回的标准command；同order内的多项操作一个事务、一个版本增量、一个批量审计事件和一个幂等回执。一个任务失败则该组全不写。
- 跨order不伪称全局原子：成功、失败、结果待确认逐组显示。状态或人员在预览后变化会在提交时重新验证。已知失败不重试；结果未知保留原commandId和正文重试。改操作/重新预览使用新batchId。
- 复用commands表持久化成功回执，不另建重复批任务引擎。GET batch-receipts提供本操作者当前团队最近30次成功批量提交记录。未提交/失败预览不持久化；跨刷新不自动续跑未提交分组，重新选择预览即可。
- 批量接口本身仍受服务端权限和版本校验；预览是操作确认流程，不是额外权限凭证。无后台自动派单或通知。

### 文件与接口

- contracts.ts/domain.ts：交接4命令、pendingHandover/handoverHistory、参与者、自验收校验、batch-tasks/set-task-tag、原子领域变换。
- store.ts：同一事务写order/event/command；批量dry-run复用同一状态与目标验证；任务/需求/周计划授权SQL与领域canRead一致；facts识别历史参与者；history按aggregateVersion游标。
- delivery-store.ts：上传前及落盘提交前再次验证pendingHandover；既有文件重试仅返回相同不可变版本，不新增上传。
- server.ts及Naumi workflow BFF：POST /v1/batch-preview；GET /v1/batch-receipts、/v1/orders/:id/history?before=版本；原/v1/commands提交batch-tasks。BFF沿用同源校验、来源会话、服务端签名、128KiB正文上限与60次/分钟写限流。
- 原UI新增handover-batch-ui.js，扩展tasks/delivery/workspace，不使用浏览器存储保存正式业务。任务中心每页30项选择，API最多50项；工作区变化丢弃旧响应。
- 无新SQL迁移、无新增常驻进程。先沿用现有4连接池和分组提交，适配4核8G起步；并未以此替代公司并发容量压测。
