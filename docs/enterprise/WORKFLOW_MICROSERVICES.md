## 1. 产品目标和当前代码事实

统一入口仍为 `/enterprise`，覆盖：运营提需求 → 需求审核 → 拆分设计/美工任务 → 指派或任务池 → 员工确认/认领 → 执行进度与阻塞 → 版本化交付 → 审核/返工 → 结项 → 绩效核算、复核与申诉。

开工实查基线 `c2634fba41fd50a117f9af93e63d865e446f7394`：

- `src/app/enterprise/page.tsx` 加载现有 `EnterpriseConsole`。
- `src/components/enterprise/enterprise-console.tsx` 是概览、成员、岗位、内容四类视图；目前的 tasks 内容是创作任务记录，不是公司的业务工单。
- `src/lib/enterprise/server.ts` 拥有组织层级、岗位、成员范围、企业开关、老板入口 grant 及账号有效期检查。
- 现有 `manage_members` / `view_records` 不等同于运营提单、任务派发、执行、验收或绩效权限。普通员工没有管理岗位也必须能进入自己的业务工作台。
- 企业代码尚在 Next.js 内，部署层面可以存在独立企业槽，但不能把独立容器等同于业务域解耦。
- 本任务不改既有账号、积分、组织表，不读取或搬迁生产数据库，不改变现有公网路由。
- 其他项目的企业架构经验只作为参考，本项目不因该参考而切换为另一个项目或导入其业务数据。

## 2. 按业务域拆分，不按页面/CRUD拆分

| 边界 | 数据所有者与职责 | 第一阶段部署方式 |
| --- | --- | --- |
| 企业入口/BFF | 现有登录、会话、CSRF/限流；组合页面；从会话派生身份 | 保留现有 Next.js；后续新增 workflow BFF 路由 |
| 组织与授权服务 | 企业、部门、岗位、成员、任职/有效期、业务权限、可见范围 | 现有模块先作为权威源，经内部接口适配；不复制密码 |
| **工作流服务** | 需求、任务拆分、依赖、指派/认领、进度、交付引用、验收、审计事件 | **本轮新增独立 Node/TypeScript + PostgreSQL 服务基础** |
| 资产与创作服务 | 原图/源文件/预览、素材版本、访问授权、AI执行任务和积分 | 沿用 Naumi 能力；工作流仅保存资产版本 ID 和任务关联 |
| 绩效与报表服务 | 规则修订、贡献分摊、验收事实投影、周期快照、复核与申诉 | 第二阶段；先消费稳定事件，不在工单事务内计算最终分数 |
| 通知/集成 worker | 派单、到期、阻塞、验收通知与外部系统集成 | 第二阶段 outbox 消费者；不拆成每种通知一个服务 |

一期先形成“企业入口/BFF + 独立工作流 + 既有组织/资产”边界，后续再拆绩效读模型。暂不引入 Kubernetes、服务网格、Kafka、Temporal 或全量重写组织体系；可按需求增长替换传输/编排技术。保留一个 Git monorepo，每个服务独立构建、版本、迁移、健康检查和发布。

工作流内的需求、任务和验收共用一个聚合事务，避免把“认领任务”和“更新需求进度”拆成脆弱的跨服务事务。每个域独立数据库和运行凭据；开发测试仅使用一次性本地 PostgreSQL。

## 3. 角色与操作矩阵

| 角色 | 业务权限 | 可见范围与约束 |
| --- | --- | --- |
| 运营 | request | 提交/修订自己的需求；看自己的进度、交付和验收结果 |
| 设计/美工主管 | dispatch | 审核需求、拆单、排期、派单、发布任务池；受所属企业和管理范围限制 |
| 设计师 | execute + design | 仅认领设计类、能力匹配任务；看任务池和自己任务 |
| 美工 | execute + artwork | 仅认领美工类、能力匹配任务；看任务池和自己任务 |
| 验收人 | review | 验收/返工；不能验收本人执行的任务 |
| 企业负责人 | manage + 按需显式授予的业务权限 | 业务配置与结项管理；不能靠“最高级别”隐式绕过执行/验收条件 |
| 绩效复核人 | performance.review（后续） | 按周期核准、解释修订和处理申诉；与执行/验收分权 |

业务权限分开授予，不能直接通过岗位中文名称推导。默认不向普通员工开放全部成员/绩效信息。首个服务聚合以企业为隔离边界；部门/下属数据范围过滤需要在正式适配阶段补齐，基础服务尚未实现部门级隔离。

员工的业务身份必须由服务端实时解析；禁用、到期、离职、企业开关和 grant 撤销必须拒绝后续命令，包括幂等重放读取。任职冻结不删除历史贡献，进行中任务交接需主管显式确认。入口不能复用当前仅面向企业管理者的 `enterpriseSnapshot()` 作为普通员工唯一授权方法。

## 4. 单据与状态机

### 需求单

字段：企业、需求人、业务项目/活动（后续扩展）、标题、完整 brief、交付验收标准、附件引用、截止时间、优先级、审批记录、版本。

本轮基础字段包含标题、brief、验收标准；任务级类型/工作量点/截止和依赖。优先级、活动分类、需求附件、标准模板及审批流配置留待下一模块。

`draft → submitted → approved → active → completed → archived`

- `submitted → draft`：主管说明退回原因，运营修改后再提交。
- `approved`：允许一次性规划/替换未发布的任务计划；发布前校验 DAG 和未来截止时间。
- `active`：需求文本、任务工作量和期限冻结；不能通过编辑原单静默改变绩效基准。
- 未完结需求可由具备 manage 的人说明原因后取消；取消不会伪造已验收事实。
- 部分任务已验收后整单取消，历史验收事实保留，绩效纳入/冲销需后续有审批的调整事实；不删除历史事件。
- 活跃需求变更、拆单追加、执行后换人、延期和变更责任归因进入后续变更单模块，不能绕过状态机。

### 工作任务

`open → [assigned →] claimed → in_progress → review → accepted`

分支：`in_progress → blocked → in_progress`；`review → rework → in_progress`。

- 主管指派后状态 assigned，员工确认后才 claimed；任务池认领直接 claimed。
- 指派仅给同企业、在职且有相应执行能力的人。
- 未开始的 assigned/claimed 可说明原因退回任务池；开工后交接单独处理，不能简单清空执行人。
- 前置任务全部验收后才允许认领/开工；基础服务支持设计→美工串行依赖，也支持无依赖并行任务。
- 同时认领只成功一人；数据库锁和版本号解决竞争，不依赖前端按钮禁用。
- 进度是工作状态，不是绩效分数；99%封顶，只有验收能置100%。返工重置进度并累加返工次数，保留历史稿件事件。
- 阻塞原因有记录；后续增加阻塞起止区间、依赖方和责任分类，才能扣除外部等待时长。
- 交付只接受资产 ID，不接收任意公网 URL，必须经资产服务核验归属和可用性。
- 首期一个任务一个贡献人；多人合作拆子任务。未来共享任务需贡献比例分摊合计100%，禁止重复计分。
- 单个任务验收与整单完成不同；所有任务 accepted 才完成需求。

## 5. 从工作事实到绩效，不直接按任务数量排名

输入事实：任务类型、冻结工作量点、执行人、贡献比例、冻结截止时间、最后提交时间、验收时间、质量等级、返工次数、交付版本、审核人、需求变更和阻塞责任。

候选规则（**设计草案，未启用**）：

`有效产出 = Σ(冻结工作量点 × 贡献比例 × 质量系数)`

`按时率 = 按时提交且最终验收的有效工作量 / 周期内应交付且可评价的有效工作量`

- 不把主管晚验收误记为员工延期；以可审计的最后有效提交/冻结期限作为基础，业务确认责任归因后定规则。
- 初稿通过率、质量、返工原因、协作响应单独展示；禁止把外部变更返工直接记为员工质量差。
- 难度基准、岗位差异、活动类型、请假/排班和工作量分配先校准；零分母显示“暂无可评价任务”，不是0分。
- AI生成次数/模型费用不等于人的贡献；现有积分消费汇总独立，不能直接转成个人考核扣分。
- 每个周期冻结 `ruleVersion + evidenceCutoff + facts + contributions + reviewer + approvalState`；历史分数不能随规则更新自动漂移。
- 流程：草稿核算 → 员工查证 → 主管复核 → 员工申诉/证据补充 → 独立复核 → 锁定归档；修订产生新版本和差额，不覆盖旧结果。
- 首期仅产出工作事实；最终评分、工资/奖金和自动人事决策均未实现或启用。

## 6. 技术契约、数据归属与一致性

- 新代码：`services/enterprise-workflow`。独立 HTTP server factory，不引入 Next、React、站点配置或供应商 SDK。
- `POST /v1/commands`：`commandId + orderId + expectedVersion + action`；拒绝额外 permissions/actor/enterprise 字段。
- `GET /v1/orders/:id`：按当前身份核验企业与可见关系；无批量列表接口，后续补带游标的任务池/我的任务/管理列表。
- `GET /healthz`：进程存活；`GET /readyz`：工作流数据库迁移v1就绪。ready不代表登录、资产、外部依赖或真实业务已经验收。
- 身份来自可注入的 `Authenticate`，成员/权限来自必填 `ResolveActor`，资产来自必填 `ValidateAssets`；默认没有通行实现，也没有生产启动入口。
- 正式 BFF 需签发短时、限制 issuer/audience/expiry 的内部凭据，服务再查当前权限；禁止信任客户端 `x-user`、`x-enterprise`、permissions。
- 组织服务仍是组织权威；生产 resolver 必须实现本企业成员、账号启停/到期、企业及老板 grant、功能开关和业务授权实时检查。接口失联拒绝变更，不能用永久缓存兜底。
- 独立库拥有 `enterprise_workflow.orders / commands / events / schema_version`；迁移不创建/改写 `app_*`。当前文档JSON聚合带强制租户/版本约束；列表量增长再加查询投影，不能用JSON全表扫描当长期报表方案。
- 一个事务写 order、command去重记录和不可变事件；先取租户命令锁，再取租户工单锁。并发版本失配返回409。
- 同命令同主体同载荷重试返回原结果；同ID不同载荷返回409。重新授权检查先于重放，防止撤权后读取快照。
- `workflow.task.accepted.v1` 包含质量、工作量、贡献人/比例、期限、提交/验收时间、返工数和资产ID；它是测量事实，不是最终绩效。
- events 同时作为持久事件日志/outbox源。本轮**没有事件投递器或绩效消费者**。后续独立维护投递租约/重试/DLQ和消费方 inbox 去重，按 `enterpriseId + orderId + aggregateVersion` 对账；至少一次投递，不声称端到端恰好一次。
- AI创作和付费供应商调用始终归原创作服务；业务重试不得重建已接受或未知状态的付费任务。
- 服务间不使用跨库外键/联合查询、不复制账号密码、不直接写别的域的表。测试 resolver 是隔离夹具，不是生产身份实现。
- 日志后续加 traceId/commandId/orderId、状态转换耗时、认领冲突率、outbox积压、活跃工单和依赖错误；错误响应只返回稳定错误码，不输出数据库凭据/内部堆栈。

## 7. 企业端信息架构（待页面实现）

浅色布局，紧凑表格/看板，无宣传口号：

1. 我的工作台：待认领、待执行、待交付、待验收、被阻塞、临期任务。
2. 需求中心：新建/草稿/审批/详情；清楚区分业务需求与AI创作执行任务。
3. 任务中心：任务池、我的任务、主管排期/指派；看板/表格共用同一状态源。
4. 项目与交付：依赖关系、版本记录、预览/源文件、评审意见与验收。
5. 绩效：个人事实明细、团队工作量、周期复核、申诉；按授权展示。
6. 组织设置：复用现有成员/岗位；新增业务权限映射、任务类型和规则模板。

员工通过会话派生组织，不提供任意填写企业ID的页面；当前管理入口的授权不能成为唯一业务入口。页面接入前不增加指向空功能的导航。

### 上线及回滚边界

本轮不发布；新服务没有生产身份适配和配置。后续按 `docs/RELEASE_RUNBOOK.md` 和目标站最新约定蓝绿发布，全程持目标站要求的所有锁；旧槽服务→新槽旁路→真实登录/数据库/资产/任务验收→nginx语法测试/平滑切流→旧会话和在途任务排空。保护现有企业界面、创作服务和工作台；不能原地重启替代。

用企业功能开关进行单企业试点；旧创作任务不迁成新业务工单。数据迁移使用独立映射/幂等ID/快照水位/只读对账，分配归属后才启用消费者。新服务失败可切回旧入口；保留新库与事件供恢复，不删库、不回灌旧库、不重放付费任务。数据库收缩迁移须等回滚窗口结束。
