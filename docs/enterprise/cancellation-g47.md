# G47 业务取消申请、影响核对与独立批准

## 使用流程

原需求/任务详情中预览取消影响，申请人填写分类与原因。需求方和执行方各由一名独立负责人批准，执行方明确应用。申请不暂停正常工作；原任务/文件/相关业务变化后，旧影响依据失效，必须重新申请，不能靠旧批准取消新工作。

## 对象与边界

仅approved/active需求进入此流程；draft/submitted仍可由原manage取消。completed/archived不反写为cancelled，已验收后的业务变化走后续需求/独立纠错。启用后旧cancel动作拒绝approved/active，避免绕过双方确认。

取消不是删除、退款或平台撤回：保留已上传文件、已验收事件、工时、贡献、原始Excel与Naumi积分。已有渠道发布状态不自动改变；允许原发布台账继续记录实际回执/人工召回，但原单取消后不能新建、批准或启动发布。项目引用保留，按原订单状态重新计算完成条件，不冒充项目自动完结。

## 影响与权限

固定申请时业务任务状态/执行人/已验收与未完成项、交付文件数量/字节、开放分片会话数量、待交接与待变更项。关联项目/渠道只显示当前调用者已有权限可见的简要列表；不可见项目/店铺的名称、ID和数量不写进共享订单快照或事件。内部依赖只持不透明摘要，用于一致性校验。

需要业务侧manager或原requester+request、执行侧dispatch；批准人不能是申请人或本单当前/历史任务贡献者，两侧不同人。应用须执行团队manage，并再次复核批准人的当前工作流成员/来源绑定。没有新增管理员代理或来源账号合并。

## 事务与并发

使用原订单advisory锁与CAS。文件落盘登记、分片会话、项目关联变更和渠道业务写入均沿用该订单锁；预览和每次批准/应用重新获取快照，相关项变化令impactHash不匹配。同一命令重放返回原结果，异输入冲突；审计/站内通知与状态改变原子提交。

每单最多20条申请、同时一条待决；proposed→approved→applied，独立拒绝/申请人撤回留档。终止操作不被资料增长的新增预算卡住。取消时未接收交接追加cancelled履历并清空pending，未应用变更明确标记superseded；已接受交接/已验收任务保持，未完成任务的原进度也不清零。

开放分片仍受原取消/到期清理，已收片不删除或立即释放磁盘；取消后新的分片/完成提交和直传落盘二次核验拒绝。正在传输的字节不等于已登记交付。后续旧版回滚不恢复已取消任务、不重放未知外部发布。
