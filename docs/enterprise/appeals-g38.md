# G38 员工绩效申诉与独立复核

状态：本地实现与集中验收完成；固定交付收尾中。承接 M23，不替代完整 M23 的周期制度、薪酬交接和真实员工试点。产品仍为 18482 原 UI；原始 Excel、schema8 真实库、Naumi 来源和账号映射保持原状。

## 1. 用户与流程

员工在已确认周期中选择本人参与的验收事实，核对原始计分与最新批准更正，填写争议、期望处理和证据说明并提交。主管在本团队待办中指定独立复核人和可选处理期限。员工可补充说明或撤回；复核人逐项查证后维持结果，或关联已独立批准的分摊更正结案。原周期快照与验收事实始终不变。

本模块不把员工“已查看”当认可，不给员工自动加分，不把待处理申诉显示为已核准。补充说明以新修订追加，不覆盖旧文本。证据由固定 period/fact/规则/本人原分摊及当前更正快照、员工文字说明组成；独立附件上传、其他指标改分、跨期调整继续在原总目标台账保留。

## 2. 状态机与操作

`submitted → in_review → resolved`；submitted/in_review 可由本人 withdraw。终态不可编辑。需要再次提出时新建申诉，可填写 previousId 关联同一本人/周期/事实的旧终态单；同一人同周期同事实最多一条未结申诉。

- create：expectedVersion=0，必须本人原分摊参与，确认 basisHash；新 UUID、commandId；reason/expectedOutcome/evidence 各有上限。
- supplement：本人未结单增加证据说明，version+1，不改固定申诉内容。
- assign：manage；指定本团队当前有效 review 成员，必须排除申诉人、任务贡献者、原验收者、周期创建/确认者、规则作者/发布者、原分摊批准者、已批准更正提案/复核人。可以替换离职/失效复核人；保留每次原因和版本，原期限仅显式改动。
- resolve：仅当前被指定且当前仍有 review 权限的独立成员；再次校验所有利益冲突和当前基准 hash。upheld 表示有理由维持当前结果；corrected 必须关联本申诉提交后新批准、同周期同事实、仍为最新且本人分值/份额确有变化的更正单。主管不能直接标已改分。更正本身仍走 G27 两人批准流程。
- withdraw：仅申诉人；不撤销已批准更正，不改变任何绩效分数。

## 3. 数据与接口

027 新增 performance_appeals、appeal_commands、appeal_revisions。主键 enterprise/id；查询带 team。JSON 文档含原始申诉、本人 basis 快照、补证、指派/处理结果。所有 mutation、幂等回执、不可变修订与 performance_audit 同事务。来源表、原周期、规则、贡献事实均只读。唯一 partial index 保证并发只产生一条未结单。

GET /v1/appeals：basis(periodId,factId)、list(periodId,scope=mine/team,状态,页)、detail、history、reviewers。POST：commandId/id/expectedVersion/reason/action。BFF /api/enterprise/workflow/appeals 使用原生会话、企业来源映射、同源、viewer 校验、受限体积与频率；客户端不可指定任意 principal。

本人仅见本人申诉；manage 可见本团队；review-only 仅见分配给自己的。其他员工/跨团队/跨企业返回404。本人基准只返回本人分数和份额，不返回其他人的分摊、总分或冲突名单。复核人候选仅 manage 可枚举。每次读取、写入与回执重放重新校验成员/权限；失效指派不得结案。

锁顺序：command → 与绩效更正共用的 enterprise/team performance 锁 → enterprise/appeal ID 锁。新建同 UUID 跨团队不得覆盖；所有基准与更正判断在同事务同锁内执行。读使用 repeatable read。列表/历史每页30，空页保留总数；正文最长4000，补证最多100条，理由2000。日期为显式 ISO 时间，未设置期限=null，不推测公司 SLA。
