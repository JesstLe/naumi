# G05/G06 任务拆分、分配与执行

## 产品与状态契约

同一原UI：已批准需求详情由dispatch主管编辑拆分方案（1–50项），每项标题、设计/美工工种、1–100工作量点、明确未来截止时间及前置任务。点数是计划工作量，不是最终绩效。保存方案仅approved内编辑，不自动发布。发布后active，任务可由符合工种员工认领或主管指派；指派assigned必须本人确认claim后才能start。依赖任务验收前不允许认领/开始。循环依赖、自依赖、重复ID、过期截止由领域规则拒绝。

正式员工工作区任务中心：全部可见/我的/可认领，搜索、状态、分页；每条读取真实order/task/version。任务详情展示需求、计划、进度、前置依赖、当前人员、操作记录。操作为指派→本人确认/认领→开始→进度0–99→阻塞（原因）→恢复；待开始可退回任务池（原因）。执行中交接需单独保留交接链，本轮不以release伪装交接。交付上传及验收在G07/G08接入，不用进度100或历史完成状态制造验收。

本机local-owner仅准备需求，任务正式执行必须员工工作区；未绑定真实员工时不创建假员工或冒用Excel姓名。原演示任务仍是独立模式，真实员工界面不显示演示数据。18482为产品方向，Naumi同源入口返回同一HTML。

## 读写与权限

- GET tasks：企业+团队+canRead范围先过滤，再分页30项；可读需求内的任务协作可见，非企业全量任务。mine只本人assignee，claimable仅active/open/工种匹配且依赖验收。查询不会写状态。
- GET assignees：仅dispatch查询当前团队有效账号/成员及工种；搜索分页30项，展示内部subject及已绑定的花名（若存在），不返回企业全量真名目录。每次assign重验目标成员与工种，不相信前端列表。
- 统一command：commandId幂等、expectedVersion乐观锁，订单/事件同事务；所有任务变更提升同一order.version。前端变更请求固定打开时workspace scope，失败保留表单；冲突需刷新核对，不自动改成新版本重发。
- 服务端仍独立校验request/dispatch/execute及本人身份；演示角色和花名不参与授权。正式BFF复用当前Naumi会话与源企业验证。
