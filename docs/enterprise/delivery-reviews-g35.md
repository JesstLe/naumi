# G35 交付版本评审、检查项与图片批注

产品入口保持18482原页面；/admin仅为来源。实施状态：服务/BFF/浏览器与开发态运行组合已验收；最终固定包/Git/回滚以本轮VERIFICATION.txt为准；不迁移真实schema8或确认真实人员。

## 业务合同

1. 评审针对一次真实 `submit-delivery` 事件，不只按任务ID或可变化的文件名归属。服务端冻结事件ID/订单版本/提交时间及本次assetId、revision、SHA256、bytes、name。相同文件被再次提交也属于新轮次。
2. 任务处于review且需求active时，非任务任何参与人的review角色发起评审；指定1—5名当前执行团队有效、独立的review成员，填写1—20个检查项。用户输入不携带冻结文件元数据。检查项在此轮冻结。
3. 每名指定评审人分别填写全部检查项(pass/fail/na)、总意见与approve/changes结论；na必须说明理由；approve要求没有fail且没有未解决问题。意见记录保留，不自动变成正式验收。
4. 指定评审人可在本轮任一文件添加问题；PNG/JPEG可绑定0—1归一化图片坐标（左上角原点），其他文件使用整文件意见。坐标展示附属于受保护图片预览；无图片预览权限不另开公开URL。参与人可回复，问题作者或本轮具有manage+review的独立评审人可解决/重开。解决必须附说明；不会据回复自动解决。
5. 新问题、解决或重开问题、替换评审成员都会清空当前结论，要求重新评审，旧结论在不可变审计历史保留。普通回复不使已有批准失效（批准时不存在未解决问题）。最多100个问题、每问题50条回复；超限报错，不静默截断。
6. 更换评审成员需manage+review且非参与人，并明确原因。用于离职/撤权接替，不转移旧人的批准。检查项不改；需要改交付规格走返工后新轮。
7. 正式accept-delivery仍使用原状态机、资产扫描与贡献事实。任务发起过结构化评审后（之前未采用的任务保留简单验收），同一事务内要求当前提交轮存在、指定人员仍有效独立、每人已批准且无未解决问题。request-rework不要求批准，允许随时退回。返工后新提交不继承旧结论；旧轮只读。cancel/accepted/archived后不再写评审。

## 权限、数据与事务

- 当前执行团队且原任务可读才可读取评审；来源提报团队不自动获得内部评审。普通参与人只可回复，不可自审或关闭问题。
- 024使用text保存原事件哈希ID，不假定UUID。评审文档总大小上限256KiB。024表：delivery_reviews、delivery_review_commands、delivery_review_revisions。当前JSON、不可变修订、幂等回执同事务；另保存runtime reviews_enabled开关；demand_assets_enabled独立记录原22启用状态，不因新24门槛隐式开启需求附件。
- 写入必须携带commandId、reviewId、expectedVersion、reason。开启需expectedOrderVersion；后续每次确认轮次仍为当前。命令→order→review固定锁顺序，原验收同order锁避免批准与返工/验收竞态。
- 回执重放重新授权，返回当前投影及原appliedVersion，不把旧响应覆盖新记录。相同提交仅一轮；全局企业reviewId冲突也不允许跨任务覆盖。
- GET /v1/delivery-reviews：context(orderId,taskId,page)、detail(id)、history(id,page)；30项分页。POST同路径执行命令。BFF复用原生会话和来源身份，不接收浏览器自报subject/权限。
- UI未知结果冻结原命令并原ID重试；冲突保留输入；关闭/换号/切团队丢弃迟到响应；浅色、390px适配，原任务详情新增“交付评审”。
