# 团队排期服务端正式化 PRD · S1

日期：2026-10-17。关联：32模块蓝图、排期V1/V2 PRD、`team-scheduling-server-contract.md`。

## 1. 阶段目标和完成定义

本阶段把排期配置从“浏览器角色模拟+localStorage”推进到“短时可信身份+实时团队权限+独立PostgreSQL事务API”，并用可操作的隔离验收页验证一个完整配置闭环。正式Naumi `/enterprise` 路由保持不变。

S1交付：可信身份验证器、数据库成员解析器、团队范围约束、配置工作簿API、独立个人布局API、原子幂等/审计、迁移和就绪检查、模块/HTTP/浏览器验收、代码副本回退材料。

S2接续：正式BFF登录和组织同步、现有团队排期页面的完整服务端适配、任务列表与排期命令、附件与迁移试点。S1不是钉钉登录上线或完整企业系统上线。

## 2. 企业使用场景

1. 运营在本系统提交需求，由规则或主管确认归属团队；本轮工作流新单记录可信当前团队，尚不从客户端表单自动建立跨团队归属。
2. 主管在团队范围内维护总表、人员分组、下发人员分组、普通表格、排期看板，先保存共享草稿，再发布。
3. 设计/美工读取团队已发布布局，保存自己的列宽、密度、筛选和展示配置；其他成员看不到此个人副本。
4. 两名主管同时编辑时，服务端拒绝旧版本保存；界面保留未成功的编辑，用户重新载入后人工合并。
5. 主管恢复历史布局时创建新发布版本，任务事实和其他视图保持不变。
6. 员工离职、账号停用、团队停用或授权到期后，下一次读写及幂等重放都重新核验。

## 4. 登录与组织来源

受信BFF在验证企业登录和团队选择后签发Ed25519短时令牌。工作流服务只持公钥，校验签名、固定算法、kid、issuer、audience、iat/exp和最长300秒有效期；拒绝额外权限声明。公钥可同时保留多个kid轮换。

每次事务从accounts、teams、team_members读取实时授权并加共享锁，拒绝停用/过期账号与成员。授权变更与已开始事务采用数据库锁串行化；不承诺中止撤权前已取得授权锁的进行中事务。签名令牌可在有效期内使用多次，jti不是一次性登录机制；写入去重由commandId承担。

数据来源：后续钉钉组织同步器或受控管理流程写上述身份表。S1不提供公开的创建账号/授予权限端点。真实钉钉Corp/App配置、SSO回调、账号映射和权限审批尚待接入。验收页的人物为合成账号，令牌签发器只在本机隔离工具内。

## 5. 工作簿与视图

一个企业团队对应一个配置工作簿。工作簿schema=3，不与本地Demo的schema=2混用。

- 全局version用于团队配置CAS；任意成功团队修改递增，包括草稿保存。
- fields/options为表级共享；只保存定义，不复制任务和自定义值。
- 每个View独立published、revision、draft、history。
- 默认5个视图沿用既有命名；“按设计师分组”默认仍按排期标签分列，不根据名称改为设计师泳道。
- 复制视图只复制已发布配置，revision=1，不复制草稿、历史或个人设置。
- 最多20个视图，含归档；名称唯一；最后一个可用视图禁止归档。
- 排序必须提交全量且无重复的视图ID序列，避免丢失隐藏/归档项。

## 6. 布局能力与约束

沿用V2列显隐、别名、宽度、顺序、预设色、密度、分组、父/任务分组锚点、表格/看板、卡片字段、筛选、条件规则结构。

名称列固定第一列且可见，宽度240–420；其他列100–420。系统列不可删除，最多20个自定义字段。最多10条条件规则、6个不重复卡片字段；仅枚举字段/操作符/预设色，不接受JavaScript、HTML模板、任意脚本或任务补丁。

API验证布局结构并持久化；S1验收页只暴露密度、首列名称/宽度、表格/看板/分组等核心控件。完整V2设计器仍在既有Demo，正式页面对接另列S2。

## 7. 团队草稿、发布与历史

保存草稿：校验expectedVersion和baseRevision；保存config、作者、时间。普通成员仍读旧published。多主管共享一个团队草稿，采用显式CAS，不做静默最后写入覆盖。

发布：必须存在基于当前view.revision的草稿；复制为published，view.revision递增，追加历史，清除草稿。工作簿version同时递增。

恢复：选择最近20个历史快照之一，发布为新的revision，不回退全局version、不重建任务、不恢复其他视图、不回灌数据库。

过旧历史返回HISTORY_NOT_FOUND；草稿来源过旧返回VIEW_VERSION_CONFLICT。布局历史最多20条，独立审计表不跟随此裁剪。新字段不自动加入所有历史列配置。

## 8. 个人布局

以enterpriseId/teamId/subject/viewId四元组存储，subject只从认证身份取得；URL、query或JSON没有代替他人保存的通道。与团队工作簿分开version；个人保存不推进团队version。

保存时baseRevision须等于当前已发布视图revision。团队发布之后，读取返回stale=true；客户端提示用户重新基于新模板确认，不自动覆盖个人内容。reset保留递增版本的空配置记录，防止删除后重建形成ABA版本重用。

个人布局仍受当前字段定义校验，不自动取得其他团队任务。个人筛选内容不进入团队审计详情；主管审计不读取其他人的个人操作记录。

## 9. 字段与排期选项

四字段类型：text、number、date、select。字段ID和类型创建后冻结；字段归档保留定义。选择项只允许追加，不自动删掉历史值可引用的选项；字段名称唯一。

排期选项采用稳定ID，允许改名/颜色和增加选项；S1尚未打通正式任务标签引用检查，因此保守禁止删除已有选项，而非假设无引用可删。表级配置修改与布局草稿独立、立即生效，必须由主管明确执行。

S1不保存真实task.values、scheduleTag或工时；后续走工作流命令与真实任务引用校验，不开放任意JSON patch接口。

## 10. 事务、重试和审计

事务顺序：解析严格请求 → 校验签名身份 → 实时成员授权 → 企业commandId锁 → 团队工作簿锁 → 去重/指纹 → 版本检查 → 写配置 → 写审计 → 写去重结果 → COMMIT。

同一commandId和同一完整输入返回首次结果及replayed=true；更换主体/团队/参数返回409冲突。撤销管理员权限后，旧管理员命令重放仍拒绝。首次成功结果是历史快照，客户端重放后应重新GET获取最新版本。

审计包括服务端主体、作用域、动作、版本、原因、视图ID、服务端时间，不接收客户端作者/时间。审计失败导致配置、去重和个人视图写入一起回滚。超时/死锁返回503 RETRY_LATER，使用同一commandId重试并查询现状，不凭网络失败假设事务未成功。

## 11. 业务工单联动

新可信身份创建的WorkOrder和WorkflowEvent附带当前teamId；所有读取/命令经过teamId相等检查，再执行既有角色/请求人/执行人规则。派单目标必须在同一团队有execute权限和对应工种，不能借另一团队的工种权限派单。

无teamId的历史foundation数据继续保留，但带团队身份不能直接读取；需要明确映射后迁移，不自动全归默认团队。无团队身份同样不读取带团队工单。

配置API只写schedule_*，不写orders、events、绩效结果。列别名、选项改名、恢复布局均不推进工单version或制造贡献事实。正式排期日期/工时/交接将在S2扩展命令，仍与配置版本分离。

## 12. 存储、运行与4核8GB

沿用独立Node服务+PostgreSQL，无需新增Redis、工作流引擎或32个独立进程。迁移002为新增表，在独立企业库显式运行；启动只检查迁移，不自动DDL。可在原资源规划内迭代，正式容量仍需部署前测量。

S1请求体上限128KiB，HTTP请求15秒，数据库锁3秒/语句10秒；验收连接池4或8，服务工厂由调用方配置。工作簿按团队整体JSON存储；最多20视图、每视图20历史，达到极端历史体积或高编辑频率时拆快照表和细粒度CAS，不凭本机小样本宣布万行性能或全公司容量通过。

schema_version=2表明迁移002具备；工作簿schema=3是文档格式，两者不相等。带排期存储的readyz检查两份迁移，缺任一份返回503；旧工厂不传排期存储时保持原行为。

## 14. 接续工作及实际待接资料
