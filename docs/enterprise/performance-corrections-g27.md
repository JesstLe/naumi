# G27 已确认周期的贡献分摊更正

## 目标

已确认周期保留冻结结果；发现多人协作分摊错误时，走独立更正单和复核，不修改验收事件、原分摊、原规则、周期快照或事实领取。原18482贡献页增加“更正与核对”，并从已确认周期进入。

本模块更正已确认事实的参与者份额，不改工作量总点数、质量、及时性、返工次数或参与者名单，不是奖金、薪酬或出勤调整。更正发生时间单独记录，原始周期计分与累计差额并列；不将旧事实重新计入后续周期，不把更正当作新完成任务。跨周期工资结转属于薪酬对接，不在本模块自动执行。

## 数据模型与状态

018新增performance_corrections，每单UUID、企业/团队/原periodId/factId、version、状态proposed/approved/rejected/withdrawn、baseRevision、appliedRevision、完整不可变提案内容、提交/复核主体与时间。proposed可由主管撤回或独立复核通过/拒绝；终态不可修改。拒绝/撤回后重提新单，不覆盖旧意见。批准后反向修正也新建更正单，不删除已批准记录。

同事实每次批准增加appliedRevision；新提案基于当前最后一次批准的份额，引用最新baseRevision及基准hash。允许多个待复核建议，但只有基准仍匹配的建议能批准；其余明确标记基准过期，须撤回后重新预览，避免丢失先前更正。

只接受原确认周期快照中确实存在且由performance_claims领取的验收事实；至少两名真实参与者，份额为每个原参与者一项、可为0、总和10000基点。单执行者固定100%，没有可更正的分摊。禁止给新名字/同名新人转移贡献。

## 金额与展示口径

沿原周期冻结row.baseMilli和row.scoreMilli，复用整数最大余数分配：

```
本次差额 = 新份额对应毫点 − 最新已批准份额对应毫点
原始计分 = 原周期冻结结果
累计更正 = 全部已批准更正的差额之和
当前核对计分 = 原始计分 + 累计更正
```

分摊工作量毫点同样处理；总计分和总工作量不变。参与任务数、及时率和返工次数保持原参与事实，不能通过改为0份额抹掉真实参与。累计负差额允许，但当前核对结果不得因算法溢出变负。已拒绝/待复核/已撤回单不计入差额。

核对结果只读实时聚合，附核对时间及各fact最新revision，不冒充新的冻结结算。CSV明确区分原始/累计更正/当前核对值；原CSV仍输出原始冻结结果。更多周期不重复领取旧事实。

## 权限、审核与幂等

当前团队manage或dispatch可预览/提案/撤回；review可通过或拒绝。批准/拒绝者既不是提案人，也不是该事实任何贡献参与者。所有操作先复核真实源会话、企业、当前团队资格，换号/跨企业/跨团队/过期或撤权拒绝；不能因已存在命令回执绕过撤权。

普通成员仅能读取自己参与的已确认周期核对值和已批准更正的本人份额/差额，不能读他人份额或待复核内容；主管/复核人可查看全团队与各状态。历史参与者停用不删除记录，但本人读取仍受当前授权约束。

预览零写入，返回原始/当前/目标份额及毫点差额、baseRevision与previewHash；提案携带相同输入和hash，服务端重算。批准再次校验基准及冻结输入，版本或已批准基准改变则409。命令ID企业范围唯一，命令主体/内容指纹一致才重放；所有写入沿原绩效团队锁，命令→团队锁顺序与周期确认一致。更正单、原绩效审计与命令回执同事务，故障全部回滚。

## API / 原UI

GET /v1/performance-corrections：action=list(periodId,page,state)、detail(id)、basis(periodId,factId)、reconciliation(periodId)。POST按operation=preview/propose/review/withdraw严格解析。Naumi BFF独立 `/api/enterprise/workflow/corrections`，同一会话/团队与源授权，不提供另一套身份。

原绩效周期详情增加“更正与核对”，不替换原始结果。界面提供原始/更正/核对表、按状态分页的更正单、选择多人事实→填写份额和原因→预览差额→确认提案、独立复核、拒绝和撤回。普通员工只看本人。错误保持当前输入，陈旧基准需重读后重新预览；切号/团队/关窗清除旧数据，迟到响应不打开旧单。浅色卡片/表格，390px布局。
