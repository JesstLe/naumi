# Naumi 项目内计费模块设计

日期：2026-10-03

状态：设计文档，等待用户审阅；尚未修改产品代码

代码基线：`e75846c`（本次检查时的 main）

## 1. 用户目标和已经确定的约束

用户希望以后调整计费时能够直接找到对应位置，常用价格和开关可以在后台修改，复杂规则集中在独立代码模块，避免每次改价都修改多个业务接口。

采用项目内的独立计费模块：跟 Naumi 一起运行、构建和发布，使用现有 PostgreSQL。没有新增独立服务、端口、容器或跨服务扣费请求。

本次重组保留当前生图调用链路、供应商配置和模型选择，不把现有流量接入尚未完成的 Router。默认配置与当前生效规则一致；不调整用户现有积分，不重算历史流水，不启用当前关闭的充值入口。

成功标准：

- 调整常用单价无需修改产品代码或重新发布。
- 一个明确的目录承载价格、报价、结算策略及积分账务逻辑；维护文档说明每类改动的位置。
- 前端预估、服务端预占和实际结算使用一致的报价定义。
- 调价不改变已创建任务及已创建订单的约定价格。
- 保持现有幂等、事务、部分成功结算、到期批次及异常任务处理能力。

## 2. 方案选择

| 方案 | 维护体验与代价 | 结论 |
| --- | --- | --- |
| 项目内独立模块，后台维护常用配置 | 代码边界明确，保留现有事务和部署流程 | 本次采用 |
| 只合并价格常量到一个文件 | 改价仍需发布，扣费和释放逻辑继续分散 | 无法完整达到目标 |
| 独立部署计费服务 | 多产品共享更方便，但增加通信故障、事务协调和运维成本 | 本次不采用 |

模块边界借鉴服务化思路，但调用方式仍是同一程序内的函数调用。

本次检索发现至少 24 个 API 文件直接引用预占、释放、结算或图片计费辅助函数。迁移必须覆盖实际调用点，不能只搬常量。

### 3.1 当前需要保持的行为

- 图片单价为「请求质量价格 + 分辨率价格 - 基础图片价格」。当前基础价格为 6，质量 low/medium/high/xhigh/max/auto 为 4/6/10/14/18/6；分辨率 1K/2K/4K/5K 对应总档位 6/8/12/16，即附加价 0/2/6/10。例如 medium、2K 当前为 8 积分。
- 当前按请求质量计费；实际执行质量及降级原因另做审计。审计中的成本估计不等于供应商真实人民币账单。
- 工具和 3D 功能存在独立价格及计费方式，不能一律替换成普通生图公式。迁移前逐项记录接口采用的现行计算及收费时机。
- 普通生图的用户自备供应商路径当前平台扣费为 0；此豁免范围不自动扩展到其他功能。
- 视频价格首次配置从现有 `VIDEO_TASK_COST` 读取；未配置时保持当前默认 20。
- 预占占用可用积分，正式结算才扣积分批次并记消费流水。当前名为 `refundCredits` 的操作通常是释放预占，不等于真实退款。
- 到期批次、FIFO 扣减、任务租约、重复结算保护和重复支付回调保护保留。
- 有些入口已保存计费开关快照，有些视频或画布流程结算时重新查询开关。第一阶段保持各入口现行行为，统一到任务快照时必须显式迁移并验证旧任务兼容。
- 计费是否实际开启涉及 Supabase/原生多用户模式及手动开关。后台需要展示有效状态和原因，不能把手动开关误写成所有情况下都生效的总开关。

## 4. 目标模块及依赖边界

```text
src/lib/billing/
  types.ts                配置、报价快照、结算结果与错误类型
  defaults.ts             与现有规则一致的初始配置
  catalog.ts              价格配置读取、验证、版本发布与公开视图
  quote.ts                报价和费用明细的纯函数
  policies/
    image.ts              图片任务的成功数量、质量及豁免策略
    tools.ts              各工具、3D 功能的规则
    video.ts              视频任务的计费策略
    credits.ts            积分有效期、赠送及到账策略
  service.ts              预占、结算、释放、到账、人工调整
  repository.ts           批次、预占与流水的数据库操作
  server.ts               现有数据库与模块的服务端组装入口
  README.md               修改导航和新增计费功能说明
```

依赖方向：业务入口 → 服务端组装入口 → 报价/策略/账务服务 → repository → PostgreSQL。前端仅使用安全的公开配置、报价类型和纯报价函数，不能引入服务端数据库模块。

`quote.ts` 不读取数据库、不调用供应商、不修改余额。`repository.ts` 接受明确的事务客户端，不导入业务接口。`service.ts` 的账务核心接受事务依赖；`server.ts` 连接现有数据库启动与运行环境。

`db.ts` 可以保留兼容函数，但不得与 `server.ts` 相互导入。迁移时以显式注入数据库依赖消除循环，不把整个数据库大文件和不相关业务重写。

任务领域继续拥有任务状态、租约和执行结果；支付领域继续拥有渠道验签和支付协议。计费模块拥有「多少钱、何时占用、实际扣多少、何时释放、如何记账」。

## 5. 报价与任务结算

### 5.1 报价快照

统一报价输入包含功能标识、用户计费上下文、数量和对应功能参数，例如请求质量、分辨率、用户自备供应商标记。返回的 `BillingQuote` 包含：

- 报价结构版本、价格配置版本、计费策略版本、功能标识。
- 计费是否有效及豁免原因。
- 数量、单价、附加项、最大预占积分和用于结算的明细。
- 请求参数，以及支持部分成功结算所需的每项价格。

快照只包含计费所需信息，不保存密钥、供应商凭据或原始敏感请求。

所有金额用整数表达：积分为整数，支付金额为人民币分。验证拒绝负数、非有限值、小数和超出数据库/整数运算范围的值；数量也须有范围限制。研究定价中的小数积分不直接迁入生产账务。

### 5.2 预估和价格生效

前端读取公开配置做预估；服务端不信任客户端传来的价格，创建任务时读取当前配置并重新报价。客户端预估附带配置版本；若创建前版本已变化且导致价格变化，返回明确的「价格已更新」结果并让用户确认新价格后再提交。该检查必须发生在预占和供应商调用之前。

创建任务后报价冻结。后台发布新配置只影响之后创建的任务。A+ 审核与生成之间、后台恢复与重试之间均使用任务已保存的报价，不重新套用当前价格。

报价保存于现有任务 JSON 字段或向后兼容的新增字段，不删除原有 cost、reserved_cost 等数据。旧任务没有新报价时，按其已保存的成本及原策略结算；不得使用新价格推算旧任务。

### 5.3 事务和幂等

以稳定任务/操作标识作为预占和结算身份，不通过每次请求随机创建新的结算身份。业务事务持有任务锁并验证租约后，调用使用同一事务客户端的账务方法。任务状态更新、批次扣减、流水和预占释放必须一起提交或一起回滚。

结算金额由策略根据报价快照和实际结果计算，不能超过冻结报价的授权金额。部分成功按对应成功项收费，失败项释放；现有不同功能的特殊规则先逐项保持。不能只在业务接口传一个任意金额然后无条件接受。

供应商已受理但结果未知的任务按现行机制保留待处理状态及预占，不把本地超时直接等同于失败退款，也不因账务重试重复调用供应商。

积分批次不足或并发冲突时，事务不能留下部分扣款、虚假流水或错误完成状态。现有 FIFO 函数的返回值与申请扣减值必须核对；发现不足时停止提交并进入明确的恢复流程，不默认视作全额扣减成功。

支付订单创建时冻结商品、金额、到账积分及配置版本。已创建订单回调按订单记录验金额并到账，不按当前积分包配置重算。人工调整和赠送分别保留来源与操作者审计。

### 5.4 故障处理

有数据库的生产环境读取配置失败时，对新收费任务返回可重试错误，不静默切成免费；已接受任务依靠保存的报价恢复。尚未发布任何后台配置时使用初始默认版本，这与配置读取失败是两种情况。

账务提交成功后，附加质量审计失败不能撤销扣费或重新执行生图。价格发布与管理员操作审计则需原子提交。报价模拟不得创建任务、占用积分或调用供应商。

无数据库的本地演示模式保持现有行为，通过显式运行模式与生产错误区分。

## 6. 后台计费管理

在现有管理员区域新增「计费管理」入口，权限沿用现有管理员鉴权。所有读写接口服务端校验权限，普通用户不能修改配置。

第一版可修改项：图片质量单价、分辨率附加价、已存在的工具与 3D 单价、视频单价、注册赠送数量、现有积分包售价和积分数，以及目前已有的计费与购买相关开关。默认值和有效状态来自当前运行配置，不把研究方案直接替换成线上价格。

购买相关开关继续服从已有渠道就绪和运行环境约束。配置默认保持关闭；价格调整不会顺带启用支付。该页面展示哪些配置能立即生效、哪些环境开关仍需要部署修改。

第一版复杂规则仍放在代码策略中，包括部分成功收费、BYOK 豁免范围、质量降级计费、异常任务释放、积分有效期及特殊商品权益。页面展示规则说明和维护位置，不提供任意脚本或通用规则编辑器。

页面操作流程：编辑草稿 → 查看改动与报价模拟 → 发布新版本。模拟支持功能、质量、分辨率、数量，返回费用明细，并标明是否计费。对自备供应商或固定价功能显示其实际策略。

发布采用版本号校验，两个管理员同时编辑时拒绝覆盖较新的版本。每次发布保存操作者、时间、完整配置及变更摘要。恢复旧配置通过创建一个新版本完成；不会改写历史版本、任务报价或订单。

沿用 `app_settings` 保存当前版本指针及配置，增加专用的配置版本记录表保存不可变历史。数据库事务同时写历史、当前指针和审计。发布成功后新请求读取当前版本；第一版不增加跨实例配置缓存，避免修改后不同进程采用不同价格。

旧管理员开关和赠送接口迁移为统一配置服务的兼容入口；新旧入口不分别保存两份有效值。公开配置接口只输出用户需要的有效价格，不暴露历史操作者、内部开关和成本审计数据。

## 7. 逐步迁移范围

1. 记录所有实际收费入口的行为矩阵：价格来源、计费单位、预占时机、成功/失败收费、幂等标识和开关读取时机。用现有功能和当前真实规则建立兼容基线。
2. 建立模块、默认配置和纯报价；旧函数委托统一实现，先保持所有默认行为。
3. 增加配置版本、管理员页面及公开报价视图；初始化取现有有效值，不改历史积分或订单。
4. 将普通生图、套图、A+、工具、画布、视频接入报价快照和事务内账务接口，按各功能原有语义迁移。每批迁移完成相应验证，再推进下一批。
5. 集中订单到账、注册赠送和人工调整；保持支付签名、回调金额校验、旧商品权益及幂等契约。
6. 删除重复计费公式和不再需要的内部兼容层，保留仍有外部调用的接口；补齐维护导航和现行价格说明，包括修正「分辨率不影响扣费」等过期文案。

迁移不新增供应商路由功能，不改变媒体存储，不重做管理员 BI，不把已有定价研究方案上线。内部实现可以分批提交，但本次最终交付需涵盖上述现有计费入口，避免留下两套有效价格来源。

## 8. 验证与验收

在现有 `verify-credit-billing.ts`、`verify-quality-billing.ts`、`verify-global-image-quality.ts` 和视频/画布 PostgreSQL 验证基础上，增加与变化直接相关的检查：

- 默认配置下各功能价格与迁移前矩阵一致，质量/分辨率组合和固定价工具不混用。
- 前端预估与服务端报价一致；配置变化时不静默接受不同价格。
- 调价后新任务采用新版本，正在审核/执行/恢复的任务保持原报价，旧任务和旧订单仍能完成。
- 部分成功收费与冻结明细一致，全部失败按现行策略释放，不超额收费。
- 重复结算、重复回调、并发任务和租约失效不会重复扣款或重复发放。
- FIFO、到期、预占、余额和账务流水守恒；余额不足导致整笔回滚。
- 已受理但结果未知保持当前处理方式；无需真实付费调用供应商。
- 非管理员无法修改配置，管理员并发发布冲突有明确提示，版本恢复及审计一致。
- 数据库读取故障不会免费接受新收费任务，报价模拟无副作用。
- 用户余额、历史流水和管理员 BI 查询保持兼容。

最终完成类型检查、生产构建和所涉功能的数据库集成检查，使用模拟供应商，不以真实付费生图作为默认验收方式。

## 9. 发布与回滚

遵循根目录 AGENTS.md 的已有发布授权和 `scripts/deploy-release.sh` 固定版本镜像流程。产品代码通过验收后按现有约定发布，无需另行申请发布权限。

发布前备份数据库、生产配置及媒体，记录当前应用版本，准备旧镜像回滚。数据库变更采用兼容的新增表/字段，不删除旧字段或重算旧账。部署前验证旧应用在新增 schema 下仍可运行，记录是否已开始使用新配置及哪些任务带新报价。

回滚不能只切旧镜像：旧应用可能不认识管理员新价格。若发布后已经启用新价格或产生旧应用无法理解的报价任务，应先暂停新收费任务并处理这些任务，再按明确兼容条件切换。无法安全回滚时报告阻塞，不擅自改账或重跑供应商请求。

发布后检查线上实际版本、健康、管理员配置鉴权、只读余额流水和报价功能，并确认默认生图与 Flow 原调用链路没有变化。服务器无法连接或迁移无法安全完成时，明确报告未发布。
