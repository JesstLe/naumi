# Image 家族容量感知分流方案

日期：2026-10-15。状态：方案待确认，尚未实施本方案、压测或发布。

本轮只整理本地设计文档，不连接47、不新增构建/候选、不切流或退役容器。此前 APIB 异步适配的未提交代码和两个验收候选另行保留，不把其局部测试当成本方案已上线。

## 1. 推荐结论

采用 **共享账户容量闸门 + 主用池容量感知调度 + 备用池溢出 + 持久公平队列**。

不是先按比例把任务分完、等TDH拒绝后再补救，而是每个实际生图单元在提交前先抢占渠道名额。TDH满载就跳过；所有兼容渠道都暂时没有容量时排队，而不是返回生图失败。

前端继续只展示既有 Image 家族，不增加供应商选择、不改变公开模型ID、默认绑定或客户售价。渠道权重与容量是两种独立配置：权重决定有空位时如何分配，容量决定这一刻还能否提交。

## 2. 初始渠道策略

| 渠道 | 角色 | 本地并发策略 | 满载/限流策略 |
|---|---|---|---|
| TDH | 主用池中的有限容量渠道 | 建议初始运行上限8；用户所述10作为待核实的供应商边界，不将8误称已实测最佳值 | 名额占满立即跳过，不继续向上游提交，不记为故障 |
| Geeknow | 主用池中的高并发渠道 | 保留用户已要求的本地不限供应商并发；持续统计真实在途数 | 明确上游限流则尊重Retry-After并冷却，其他可用渠道承接 |
| APIB / Sunburst | 备用池 | 设计为不套用TDH的小并发上限；实施时核实该账户的实际并发/请求速率约束 | 主用池对当前任务无可用容量或发生明确可回退失败时承接 |

主用池内保留已发布的优先级和权重；本方案不偷偷把TDH设成最高优先级，也不把APIB改成与Geeknow平均分担。管理员后续明确选择“高并发均衡池”时，才将Geeknow/APIB放在同一优先级并配置各自权重。

“本地不限供应商并发”仅表示没有人为小并发闸门，不表示上游有无限配额，也不表示本机内存、HTTP连接和下载解码资源无限。

本会话新接入地址是 `https://api.apib.ai/v1`，图片模型是 `gpt-image-2.5-sunburst`。APIB提供的APIMart协议文档不等于它与其他APIMart账号共享额度；实施前把用户口述名称映射到实际provider、账户额度组和模型，不按显示名合并供应商。

## 3. 80人同时生图的结果

假设80个用户各请求1张、参数都兼容、主用池有TDH/Geeknow、期间还没有任务完成，TDH运行上限8，Geeknow健康且可受理：

- TDH在途最多8个；后续请求抢不到TDH名额时立即尝试Geeknow。
- 若本轮分配已占满TDH的8个名额，其余72个可由Geeknow承接，APIB仍待命；若原优先级使Geeknow先承接更多，则TDH实际数可以少于8，不保证固定比例。
- Geeknow明确拒绝部分请求且确认尚未受理时，这部分尝试APIB；上游已经受理的任务留在原渠道查询。
- 三条渠道都暂不可提交时，未提交的任务留在持久队列，不变成红色失败项。
- TDH每完成一个任务就腾出一个名额，后续排队任务可再次参与调度。因此“最多8个”是任意时刻的在途上限，不是整批累计只能使用8次。

80人各请求4张时是320个实际生图单元。批量任务拆成单元调度；用户只产生一份原生业务任务和既有报价/预扣记录，不另建一套计费。

## 4. 执行流程

1. 原生任务接口完成鉴权、参数/素材检查、既有报价与任务持久化，返回任务ID。
2. 调度队列只登记原生任务与生图单元的引用，唯一键为业务操作ID加单元序号；重复提交返回原任务。
3. 调度器先恢复已经受理或受理未知的原供应商调用。这些调用不再重新选择渠道。
4. 对尚未提交的单元，筛选已启用、参数兼容、账户可用、未熔断的渠道。
5. 调度器按主用池的既有优先级/权重尝试原子抢占名额；有限渠道占满就尝试下一条。主用池没有可提交路径时尝试备用池。
6. 在一个短数据库事务内登记调度claim、供应商槽位和提交意图。事务提交后才发生上游网络请求；事务中不等待生图、轮询、下载或解码。
7. 上游受理后立即保存供应商task_id或可核验的request_id。异步调用交给后台恢复/轮询，页面关闭后仍可取回原结果。
8. 上游明确结束时释放供应商执行槽；下载、像素解码、存储和作品落库使用独立本地资源预算，验收通过后才标记用户成功并走既有幂等结算。
9. 无可提交渠道时记录等待原因和下次唤醒时间；渠道腾位、冷却结束或Worker扫描时重新调度。

原则：先找符合要求的空位，再执行；已受理任务永远优先恢复原调用。

## 5. 容量怎么算

### 5.1 同一个额度组共享计数

- 容量按实际供应商账户的额度组计算，不只按公开模型名称或某个App进程计算。
- 创作页、画布、Agent、套图/批量以及多App副本都走同一个闸门；同一密钥或已确认共享额度的别名不重复获得一份额度。
- 同一供应商若文字和图片额度实际独立，使用显式维护的资源组区分；供应商说明不清楚时不凭名称猜测独立额度。
- 替换密钥不自动清空旧在途统计；确认是独立账户才建立新的额度组。
- 仍使用同一上游账户但绕过本系统的旧服务也会占额度。实施前盘点原工作台/旧执行器，接入同一闸门、分配经确认的独立额度，或在核实排空后处理；不能只统计Naumi就保证TDH总并发。

### 5.2 两类租约分开

| 对象 | 用途 | Worker心跳过期后 |
|---|---|---|
| 调度执行claim | 防止两个Worker同时处理同一个单元 | 可由新Worker接管，但只恢复已记录的原调用 |
| 供应商执行槽 | 反映供应商是否仍在生图 | 不因浏览器断开、HTTP超时或Worker心跳过期而自动释放 |

供应商槽计数覆盖已保留、正在提交、已受理、处理中、受理未知的调用。明确未受理、明确失败/取消/完成才释放。提交意图已经持久化但task_id未保存时属于受理未知，先核查，不重新POST。

异步任务拿到task_id时仍在消耗供应商并发。GET查询不再重复占一个生图名额，但受独立查询速率预算约束。查询失败不等于生成失败。

### 5.3 配额修改是独立运营策略

建议提供账户额度组级、可审计的运行策略：

- `mode`：有限 / 本地不限；有限时填写`maxInFlight`，不限时使用null而不是伪造很大的数。
- `newSubmissionsEnabled`：是否接收新任务；停用仍允许查询已经受理的原任务。
- `revision`、修改人、修改时间和依据。
- 可选的上游提交速率、查询速率、限流冷却状态。

降低上限立即限制新提交，不中断现有任务；例如从10降到8时，在途9个会等待降到7个再放下一个。提高上限经管理员明确发布后生效，不被历史快照中的旧最小值永久锁住。实际供应商边界10若经确认，配置校验应阻止超出该边界。

模型、参数、报价、凭据引用仍冻结在原任务版本中。只有经过审计的实时容量/停用策略约束后续准入，不能借配额更新改变已受理任务的模型或售价。

## 6. 队列与用户体验

### 6.1 公平且持久

- 复用现有PostgreSQL、原生任务表和Worker；本轮不为排队再引入一套Redis调度系统。
- 新增统一调度索引/状态表，仅引用已有业务任务、用户和生图单元，不复制原任务正文、素材大字节或账本。
- 用户之间轮转，每轮优先取每人一个单元；同一人的批量任务不会一次抢走所有待分配名额。只有一人有任务时可持续使用空闲容量。
- 使用短事务、行锁/CAS和fencing token处理claim；采用可跳过已锁行的领取方式，避免所有用户等待一个长事务。
- 后台扫描兜底确保重启/通知丢失后仍能继续，通知仅用于提速，不是唯一触发源。
- 重试等待带退避和随机抖动，避免80个任务同一时间再次冲向刚恢复的TDH。

### 6.2 状态和积分

前端保持现有布局，只增加必要状态：排队中、生成中、结果处理中、核查中、已完成、已取消、失败。

- 排队中允许取消；取消尚未提交单元并按既有规则释放对应预扣，结算幂等。
- 已受理后，只有供应商确认取消才将该单元作为远端取消处理；“页面不等了”不等于上游已停止。
- 排队超时按独立的`queueDeadline`处理；实施时沿用或明确配置等待时限，不拿供应商请求超时冒充队列等待上限。
- 队列满时在调用上游前明确返回繁忙/可重试结果，不额外生成和重复扣费；不承诺任何负载下都能接收无限任务。
- 纯排队、限流跳过、轮询重试不新增费用。既有成功交付/部分成功/释放与人工核查规则继续生效。
- 状态未知的供应商成本与客户交付分开：未取得结果不直接记用户成功，也不无期限盲目续扣。复用已有未交付释放/人工核查机制，同时保留供应商原调用，防止重投。

## 7. 回退与熔断规则

| 情况 | 本单元处理 | 渠道处理 |
|---|---|---|
| 本地名额已满 | 尝试下一条；全部满则排队 | 不增加故障计数 |
| 管理员关闭新提交 | 不把新任务分过去；原受理任务继续恢复 | 新提交停用与查询停用分开 |
| 参数/参考图/质量能力不兼容 | 提交前筛掉；有其他兼容渠道才回退 | 不把业务参数错误当供应商故障 |
| 明确未受理的429或拒绝 | 释放本次槽位，尝试其他兼容渠道 | 尊重Retry-After；没有时按策略退避 |
| 明确余额不足或凭据失效 | 尝试其他渠道，若无则等待/终止并解释原因 | 对应账户停接新任务，提示管理员 |
| 网络断开、5xx、提交响应缺失 | 记受理未知，核查原调用；不直接换渠道重复生图 | 可暂停该渠道新提交，原调用保留 |
| 已保存task_id，查询超时 | 延后查询原任务，不重新POST | 不凭一次GET超时判生成失败 |
| 上游明确任务失败 | 按受控回退预算尝试下个兼容渠道 | 原调用成本保留，失败类别参与熔断 |
| 上游完成但下载/解码/入库失败 | 重试原结果下载或存储，不重新生图 | 与供应商生图故障分开统计 |

仅当上游契约或响应明确证明未受理时才把拒绝作为可回退依据，不笼统认定所有4xx/429都没有产生任务或费用。

熔断以具体账户/模型故障域为准：模型不可用不拖垮该供应商其他正常模型，账户余额耗尽则作用于共享账户。半开恢复只放少量探测，不让80个任务同时试错。每个单元有持久化的尝试预算，重启后仍记得已尝试渠道，避免循环回退。

## 8. 本地资源保护

47同时承接80个供应商在途任务，不应等于占着80条数据库连接或在内存中同时解码80张大图。

- 生图等待/轮询期间不长期持数据库连接、数据库事务或全局advisory lock；采用持久claim与短时续约。
- 上游生图并发、短提交HTTP并发、查询速率、图片下载并发、解码并发分别预算。上游不限不自动取消本地资源保护。
- 轮询根据任务状态退避，增加抖动并共享账户查询预算；不为每个用户启动独立无上限轮询器。
- 输入图片引用已有受保护媒体，避免为队列复制80份Base64；输出分批下载、校验和保存，沿用已有访问隔离与浏览器缓存路径。
- 本地具体HTTP/解码并发值在隔离模块测试和47旁路资源验收后确定，不在方案中把未经测量的数值当已验证容量。

## 9. 管理后台

沿用浅色布局，现有家族的“通道”区域增加以下必要字段：

| 信息 | 展示/操作 |
|---|---|
| 渠道角色 | 主用 / 备用，优先级、权重 |
| 准入状态 | 可用、满载、冷却、停用、受理待核查 |
| 运行容量 | 例如TDH `8/8`、Geeknow `72/不限` |
| 共享账户 | 额度组标识、已确认共享的模型/入口，不展示密钥 |
| 等待任务 | 家族排队数、最老等待时间、等待原因 |
| 异常 | 最近限流、下一次可尝试时间、未知受理任务数量 |
| 策略修改 | 当前值、拟修改值、依据、保存发布与审计记录 |

用户前端不暴露内部供应商切换；真实task_id、槽位、调度和成本证据由管理员查看。日志不记录密钥、完整提示词或私有图片地址。

## 11. 分模块实施

### A. 容量与分流

明确实际渠道/共享额度组，建立运行容量策略，原子申请/释放、有限与不限并存、全局统计以及主用/备用溢出。先不动前端名称和售价。

### B. 队列与异步生命周期

贯通各原生入口的公平持久队列、供应商槽、Worker接管、原任务查询、未知受理隔离、取消/超时与幂等结算。移除生图期间持有的长数据库锁/连接。

### C. 后台与集中验收

后台展示真实容量/队列/冷却状态，集中跑下列模块矩阵，再准备蓝绿发布包。每个模块更新实现记录；不将频繁零碎测试代替完整模块验收。

## 12. 验收矩阵

大并发测试使用隔离PostgreSQL和可控模拟供应商，不用80笔真实付费生成压测。真实供应商只做受控闭环；模拟容量通过不等于实际供应商容量已证实。

| 场景 | 必须取得的证据 |
|---|---|
| 80用户×1张，TDH上限8，Geeknow可用 | 全过程TDH峰值≤8；TDH本地满载后上游新增提交数0；其余已派发或明确排队；不因满载误报任务失败 |
| TDH已确认上限10 | 账户全部接入入口合计峰值≤10，而不只是一个App各自≤10 |
| 多App副本、多个入口同时请求 | 总额度共享、无超发；同账号别名/密钥轮换不绕过额度 |
| Geeknow明确限流，APIB可用 | 仅未受理单元溢出APIB；保留原角色优先级；已受理任务不重投 |
| 全部渠道忙/冷却 | 任务持久排队，释放名额后继续；正确记录等待原因和用户公平顺序 |
| 80用户×4张 | 320单元去重；用户轮转；部分成功与最终结算沿用原规则 |
| 一个用户批量、其他用户单张 | 批量不独占调度，空闲时容量仍可充分使用 |
| 异步已受理后关闭页面/Worker重启/租约过期 | task_id不变，新增付费POST为0；槽位不错误释放；新Worker可恢复 |
| POST响应丢失、无task_id | 受理未知有持久证据，不生成第二笔；可核查/人工处理而非静默释放后重投 |
| 下载/解码失败 | 只恢复原结果；未验收不记客户成功，供应商终态与客户交付状态分开 |
| 关闭渠道或降低运行上限 | 新提交立即遵守；已有任务不中断，旧任务恢复不被误切到其他渠道 |
| 取消/队列等待超时/重复请求 | 未提交部分正确释放；同单元只结算一次，已受理任务遵守真实取消能力 |
| 47旁路资源验收 | DB连接数不随每个长生图任务各占一条增长；队列/在途/下载/解码均可观察；内存和CPU有双槽余量 |

不得以“80个HTTP请求都返回200”替代容量证据。核心指标是TDH上游实际在途峰值、每单元POST次数、排队恢复、可用图片交付和账本一致性。
