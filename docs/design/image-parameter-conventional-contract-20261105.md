# 图片参数"约定优先"模式（按通道开启）设计方案

- 日期：2026-11-05；基线 main `bbda7e3ee4221f1141be739aa9e930db064b8bf8`
- 状态：**方案，待实现**。本文不代表代码已实现、已合并或已上线。
- 前置资料：[图片参数统一计划](../changes/2026-10-27-image-parameter-plan.md)、[参数护栏审计](../GUARDRAIL_AUDIT_20261024.md)、[供应商模型元数据](../supplier-model-metadata.md)、[模型管理](../admin-model-management.md)

## 1. 背景

**最初目的**：后台保存供应商支持的参数，是为了配置前后端映射时能直接看到"这个供应商实际支持什么"。例如前端显示 1K/2K/4K、供应商只支持 1k/2k，管理员就配 4K→2k；质量同理，可配 high→medium，或者不发送该参数。

**问题**：后来没有持续维护供应商资料，运行时却把资料当成准入白名单，导致经常误拦截。

**现状**：

- 2026-10-27 上线的参数计划已确立规则："已发布的人工映射决定实际发送，资料只做参考，不再做二次白名单"。
- 同期线上改为只用 apib 一家，之后误拦截基本没有再出现。
- 但这条规则只覆盖**已发布映射的通道**。通道没有映射或只配了一半时，运行时仍会读 `capabilities.*` 的旧能力字段来拦截。新接入的供应商恰好处在这种状态：

| 位置（基线 main） | 未配映射时的行为 |
|---|---|
| `src/lib/model-config/simulation.ts:63` | 池内通道 `nativeResolutions` 为空时，最大像素按 1536×1024 计算，2K/4K 被整体排除（PIXEL_LIMIT） |
| `simulation.ts:60` | 分辨率不在 `nativeResolutions` 内 → NATIVE_RESOLUTION |
| `simulation.ts:53-54` | 标为已验证但质量列表不全 → QUALITY_RANK / QUALITY_UNSUPPORTED |
| `simulation.ts:47,51` | qualityPolicy 缺档 / resolutionPolicy 映射缺档 → 排除 |
| `resolution-fallback.ts:19,44` | 声明过 `nativeResolutions` 就严格按它判断档位 |
| `image-parameter-plan.ts:32,56` | 旧质量映射只配了一部分、高级参数没有映射 → IMAGE_MAPPING_INVALID |
| `resolution-policy.ts:35` | map 模式缺档 → 409 |

**为什么早期 BYOK 不配置也能生图**（依据 `a570f32e^` 版本的 `src/app/api/generate-image/route.ts`）：

1. 只支持 OpenAI 兼容协议，按通用约定直接发送：比例换算成像素 size，quality 传原值。不查能力表，也没有映射。
2. 由上游自己判断，不支持就报错；上游明确不认 quality 时换默认档重试一次。
3. BYOK 不走站内计费，所以不需要"规格必须与报价一致"这层护栏。现有大部分拦截正是为这条护栏加的。

根本差别在于：**BYOK 默认放行；后台模型管理默认先核验，缺资料就拦截。**

## 2. 目标与非目标

目标：

- 新接入的通道**零配置就能生图**，效果和 BYOK 一样。
- 管理员**只配置例外**（如 4K→2k、high→medium、不发送），达到最初目的。
- 供应商资料**只用于提示和生成建议**，任何时候都不拦截用户请求。
- **apib 等现有通道行为逐字不变**，新模式先只对第二个供应商生效。

非目标（第一轮）：

- 不修改现有通道的配置和判断逻辑。
- 不改计费口径：报价仍按用户所选档位。
- 不自动降档，也不付费重新提交。
- 外部 Router、成本预设、Reverse Hub 专用适配器、模型池、视频暂不纳入。

## 3. 设计

### 3.1 开关

- 新增字段 `upstreamModels[].parameterMap.parameterContract?: "conventional"`。不填时维持现行行为。
- 粒度是**单个实际模型来源（upstream）**，只给第二个供应商打开。
- 适用协议与现有质量/分辨率策略的可编辑范围一致：`openai-images`、`new-api-flow`、APIMart 应用异步通道。
- `schema.ts:116` 已禁止在启用中的模型池候选上使用这些策略。所以第一轮开启新模式的通道**只挂在单通道公开模型上**，不放进 apib 所在的池。
- 开关属于已发布配置，会进入 modelVersion/digest。已受理的任务按冻结时的配置解释，开关变化不影响它们。

### 3.2 开启后的判断规则（只作用于该 upstream）

| 判断点 | 现行 | 约定优先模式 |
|---|---|---|
| 资料/能力白名单：`simulation.ts:53,54,60,63`，`resolution-fallback.ts:19,44` | 不在列表内就排除 | **跳过**。资料只在后台提示 |
| 映射缺档：`simulation.ts:47,51`，`resolution-policy.ts:35`，`image-parameter-plan.ts:32` | 排除或报错 | **空格 = 按协议默认传法发送前端值** |
| 高级参数没有映射：`image-parameter-plan.ts:56` | 报错 | 丢弃该参数，写入审计警告 |
| 已填写的覆盖（4K→2k、high→medium、不发送） | 生效 | 生效，以人工配置为准 |
| 前端可选档位 | 由多处共同决定 | 由管理员设置的 `displayResolutions` / 质量展示档决定 |
| 结构性约束：蒙版、编辑操作、参考图上限（已验证或管理员填写的）、字段冲突、非法字段名、透明与格式冲突 | 拦截 | **保留** |
| 资金类：幂等、预占、结算、未知受理状态 | 保留 | **保留** |

`image-preparation.ts:46,73` 的 `option.parameters.ratios/resolutions` 先核实来源：

- 如果是管理员在功能选项上显式设置的，属于人工限制，保留；
- 如果是由资料或能力自动派生的，新模式下不再派生。

### 3.3 协议默认传法

不新造规则，直接复用各协议适配器在"无映射"时的现有发送行为（`image-parameter-plan.ts:33` 注释所指的协议默认）。实现第一步就是逐协议盘点，并把结果登记到本文附录：每个协议的质量字段、分辨率/尺寸字段、比例字段，以及无映射时实际发送的值。

### 3.4 后台交互

- 映射编辑器增加开关"按协议默认发送，只配例外"。只在符合 3.1 条件的单通道 upstream 上显示。
- 每个格子显示：
  - 实际发送值。没填时显示"默认（将发送 X）"，X 由同一个编译器算出。
  - 供应商资料里的支持值，附来源和核对日期。
  - **黄色提示**：前端档位不在资料支持列表内，且没有覆盖。只提示，不阻止发布。
- **一键建议**：映射到不超过前端档位的最近一档资料值（如 4K→2k）；没有更低档时取最近档。须管理员确认后才发布。
- 请求预览、一次 CAS 原子发布，沿用 10-27 已有能力。

### 3.5 上游拒收

- 第一轮：受理前被上游明确拒收（400/422）时，用户看到准确原因，不扣费。审计记录 upstreamId、前端选择、实际发送的参数、上游错误摘要。
- 第二轮：后台在对应格子上标红，例如"上游 11-05 拒收 4K→4k"。可选：同一通道去掉被拒参数后重试一次，仅限受理前的明确拒收。

### 3.6 计费与记录

售价按用户所选档位计算。用户选择、实际发送值、实际输出尺寸分别记录，沿用 10-27 参数计划已有的字段。

## 4. 兼容与发布风险

- **旧镜像读不了新字段**：`parameterMap` 是 strictObject（`schema.ts:44`），旧镜像读到 `parameterContract` 会解析失败。必须按"扩展 → 启用 → 收缩"的顺序：
  1. 先蓝绿发布能识别该字段的代码。这时任何通道都不开启。
  2. 旧槽排空并停止后，才允许在后台开启。
  3. 开启后，如需回滚到旧镜像，**必须先关闭开关并发布配置**。回滚材料须注明这个前置条件。
- 默认目标站 103；47 继续"维持配置、合并后暂缓发布"的决定。

## 5. 验收

1. **apib 零差异对比**（合并门禁）：只读导出 103 的在线模型/计费配置，零网络调用。逐家族、逐档位、逐比例比较改动前后的结果，包括 simulate 的 eligible/excluded、`resolveImageResolution`、`compileImageParameterPlan`、报价。**有任何差异就禁止合并。**
2. **新模式用例**：
   - 资料为空，所有展示档都能出计划；
   - 覆盖生效（4K→2k、high→medium、不发送）；
   - 只配一半时，空格按默认发送；
   - 字段冲突在发布时被拒；
   - 冻结任务重新打开时按原解释；
   - 关闭开关后，行为与现行完全一致；
   - 旧镜像兼容顺序。
3. **真实验收**：在 103 建管理员可见的测试模型，逐档真实出图，核对实际发送值和输出尺寸，并记录付费测试次数。上游 200、脚本通过、合并、上线分别写明证据层级。

## 6. 上线步骤

1. 代码合入 main，蓝绿发布到 103。此时没有任何通道开启，线上行为不变。
2. 第二个供应商单独建一个测试模型，开启开关，只对管理员可见，不放进 apib 所在的池。
3. 管理员逐档真实验收。
4. 稳定后再开放给用户。之后视情况把 apib 切到新模式，或把新模式设为新建通道的默认值，届时另立任务。
