# 管理后台架构与 UI/UX 评估及改造路线

- 日期：2026-11-05；代码基线 main `e65c4b22`
- 线上观察（只读，未保存任何修改）：
  - 103 平台后台：`268076b7` / v2026.11.04-061136，模型配置 v117，28 个前端模型，19 个上游来源。
  - 47 企业专属站：`6eddec90`。中间件对 `/api/admin/*` 返回 404，`/admin/*` 跳转到企业管理中心（`src/middleware.ts:26-35`）。模型管理只在 103。
- 用户决定（2026-11-05）：**两站管理员密码暂不修改**。弱口令和共享密码的风险已告知，记录在案，不在本路线中执行。
- 关联方案：[图片参数约定优先模式](image-parameter-conventional-contract-20261105.md)

## 1. 总体判断

底层方向是对的：整份模型配置带版本并冻结执行；执行链路不读供应商资料；计费有幂等和 CAS 保护。

问题集中在入口层：

- 同一件事有多个入口、多种写法，配置成了拼图。
- 安全措施因接口而异，有的有，有的没有。

## 2. 安全

| # | 问题 | 证据 |
|---|---|---|
| S1 | 后台鉴权没有统一入口，中间件不拦后台接口。63 个接口的守卫有 8 种写法；同源校验 4 份、本地 `guard()` 9 份重复实现；限流、审计、幂等只覆盖部分接口；未授权时返回的状态码在 401/403/404 之间不统一 | `src/lib/admin-auth.ts:128-150`、`src/lib/bi/access.ts:17,30`、`src/lib/billing/access.ts:6,20`、`src/lib/teams/access.ts:11,31` |
| S2 | `owner-account` POST 会改绑站长邮箱并迁移全部资产，但只调用 `requireAdmin`：没有同源校验、二次验证和审计 | `src/app/api/admin/owner-account/route.ts:24-55` |
| S3 | `users` POST 可以改角色、封禁、删除用户，但没有"不能操作自己 / 至少保留一个管理员"的保护（BI 版有，见 `src/lib/bi/user-management.ts:127-137`）；`artworks` 的 ban-user 是第三个封禁入口，也没有保护 | `src/app/api/admin/users/route.ts:128-148`、`src/app/api/admin/artworks/route.ts:144-150` |

## 3. 架构

| # | 问题 | 后果 |
|---|---|---|
| A1 | 同一份 ModelConfig 有两种写法：新 UI 每个动作在服务端新建私有草稿后直接发布（`management-access.ts:218,233`）；旧"完整配置中心"（`components/admin/model-config/manager.tsx`）走草稿 → 预览 → 发布。两者共用一个全局版本 | 改一个模型的名字，其他管理员持有的版本就会冲突返回 409；任何一次 UNKNOWN 发布会挡住后续所有发布（`repository.ts:141-142`）；每次操作留下一份草稿且没有清理 |
| A2 | 积分售价有 4 个来源：成本预设、`mvp-credit-*` 规则、`business.options.pricing`、价目表（tariff）。生效优先级为 preset > credit 规则 > business option > tariff（`business-billing.ts:24-37,59-68`）。写入路径有 3 条，只有 `editManagedModelCredits` 校验价格矩阵是否完整 | 后台看到的价格不一定是实际扣费价格；计费发布不检查模型 projection，成本键改坏后要到执行时才报 INVALID_COST（`projection.ts:16-28`、`execution.ts:159`） |
| A3 | `management-access.ts`（33KB）在一个闭包里分派 20 多个 action，并直接执行 SQL；另有 5 个路由直接写 SQL；`settings` 路由逐字段写入、不在事务内 | 修改容易牵连其他功能；请求中途失败会留下部分生效的状态 |
| A4 | "上游来源"把账户、地址、协议、用途混成一条记录：tdhcodex 登记了 4 次，apimart 和 prompt-hubs 各 2 次 | 换密钥要改多处，余额和成本无法按供应商汇总 |
| A5 | 过时的兼容代码和测试仍在：`assertQuotedVersion` 已是空操作，但 `scripts/verify-canvas-admin-runtime.ts` 仍断言 MODEL_CHANGED；`/api/admin/mvp*` 已无调用方；`settings` 的模型字段在部分状态下仍写入 `app_settings` | 测试结论不可信；旧路径在部分状态下可能被意外触发 |
| A6 | `src/lib` 下有 81 对目录双向引用，根目录平铺 127 个文件 | 不专门大拆，按 AGENTS.md 的规则，在改到相关业务时顺带收敛 |

## 4. UI/UX（103 实际界面）

| # | 问题 |
|---|---|
| U1 | 导航层层重复：左栏 → 顶部子标签 → 页内链接 → 页内 tab，"完整配置""供应商余额"各出现两次；"新增前端模型"会跳到旧页面 `/admin/bi/models?tab=batch` |
| U2 | 一个模型的配置拆成 10 个弹窗，每个弹窗保存即生效；其中参数相关的有 4 个（统一参数映射、参数设置、分辨率设置、图像高级参数）。接入一个新供应商要跨 2 个页面、至少 6 个弹窗，中间看不到"待生效改动"的汇总 |
| U3 | 最初目的没有在界面上体现：上游值是自由文本，没有下拉候选；供应商资料只藏在折叠区里一行"供应商资料：1K / 2K / 4K"，显示的还是前端档位而不是真实取值；映射为空（如 Geeknow 通道三格全空）时只在请求预览里报错 |
| U4 | 映射弹窗宽 620px、内容高 3440px，各通道纵向堆叠，已停用的通道也混在里面 |
| U5 | 列表里的"积分售价"只是单个工具的参考价；21 个工具标签铺满整行；"另 1 个模型"意思不清 |
| U6 | 元数据库的"模型家族"筛选有几百个按钮，被"S-2.0-933-线路四"这类线路名污染 |
| U7 | 用户管理有 3 套界面、封禁有 3 个入口；"定价测算"与"价格表"并列；"运行健康"与"健康巡检"名称相近；部分页面登录后会跳回 `/admin/center`，而不是原页面（`admin-navigation.ts:6` 白名单不全） |
