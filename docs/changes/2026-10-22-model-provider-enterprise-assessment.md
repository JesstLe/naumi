## 已有基础，不能误判为缺失

- 不可变模型/计费版本、操作者草稿 revision、发布 active version CAS、操作 UUID、发布原因和历史记录；未知发布状态有恢复流程。见 `src/lib/model-config/repository.ts`、`access.ts`、`runtime.ts`。
- 供应商凭据引用及加密保存，已接受任务使用冻结配置/凭据；不是每次执行重新读取管理员最新选择。
- 应用内通道支持优先级和同优先级加权调度、PG 跨实例容量租约、健康冷却与恢复；已有的 Router 池仍是另一条执行路径。见 `channel-scheduler.ts`、`capacity.ts`、`projection.ts`。
- 图片供应商结果不确定时保留原任务，不无条件向备选重发；供应商调用账本、用户积分结算、采购成本待核查状态均已有实现。
- 元数据采集与人工维护有分层和版本检查。`supplier-models/imagegen-access.ts` 优先人工能力/映射，缺少时才用采集资料；配置发布后使用已解析快照。
- 有真实业务健康观察、带预算的主动普通生图探测和输出解码，不能说完全没有监控。见 `src/lib/model-health/`。

## 需优先收敛的结构问题

| 问题 | 源码/真实证据 | 运营影响 | 建议 |
| --- | --- | --- | --- |
| 公共模型映射与共享上游耦合 | `management.ts` 的 `applyModelQualityParameters`、`resolution-policy.ts` 的 `applyResolutionParameters`、`imagegen-policy.ts` 均修改 upstreamModels 上的参数 | 两个前端模型引用同一个上游配置时，修改其中一个的映射可能改变另一个 | 映射归属于“前端模型 × 供应通道”绑定；上游保留真实协议默认值；账号容量仍共享 |
| 展示规格受通道选择影响 | `quality-policy.ts:qualityPresentation` 取第一个有 qualityPolicy 的 upstream | 前端产品规格没有完全独立，增加/替换通道可能带来显示档位或标签变化 | 前端规格归公共模型；每条通道只回答如何实现该规格 |
| 能力事实存在多种表示 | `schema.ts` 同时有 verified/透明等布尔值与 imagegen 分项证据；质量另有 evidence、元数据库另有 capabilityState | “资料称支持”“管理员已允许”“实际输出已验证”容易被当作同一个状态 | 统一有效能力契约，分别记录能力、证据等级/时间、人工策略、当前可用状态；旧字段逐步兼容退场 |
| 单通道与多通道结果处理不完全一致 | `channel-fetch.ts` 调用 completedChannelImage 处理 URL/b64；`cutout/route.ts` 的直接 OpenAI 分支读取 b64_json | 上游实际返回正确图片，也可能因路径不同无法交付 | 所有单/多通道调用复用协议适配与统一结果归一化，不让“是否配置分流”改变响应处理 |
| 探测粒度不足以证明全部能力 | `model-health/executor.ts` 主动探测普通 generations；`targets.ts` 依据 generate 选目标 | 能生成普通图片不代表能编辑、透明、蒙版、多图或原生 4K | 按任务类型和关键参数组合建立受控验收矩阵；结果落证据库，标明版本和有效期 |
| 管理权限仍较粗 | 模型 read/draft/publish/credentials 共用 `biAuthorize` / requireAdmin | 多人运营时无法在本模块区分查看、编辑、发布和凭据管理 | 在现有鉴权上增加操作级权限；高风险变更可要求独立复核，保留应急流程 |
| 简化管理与完整配置入口并存 | model-management 与 model-config/manager 提供不同编辑/发布流程 | 运营理解多个入口、追踪一次配置的最终作用成本较高 | 统一配置领域服务和发布机制，UI 提供常用操作与高级配置两种视图 |

共享映射问题是代码结构风险，并不表示本次已证明两个线上模型发生串改；此次未修改配置来复现。权限结论限本模型配置管理模块，不把未检查的企业账号系统判断为完全没有权限或租户功能。

## 建议的数据边界与执行路径

1. **前端模型**：稳定 ID、显示名称、展示规格、适用工具、售价引用。
2. **供应商账户**：地址、协议、凭据引用、共享并发/限流、账户费用信息。
3. **上游模型定义**：实际模型 ID、接口契约、能力证据、公开资料/采购价格来源。
4. **模型与通道绑定**：启停、优先级、权重、独立参数映射、可接受交付标准。

元数据保持“管理员显式配置优先、采集资料兜底”。发布时解析成不可变有效配置，运行请求不临时依赖元数据最新值。显式不发送参数、false 和 0 均不能被默认值覆盖。人工允许也不能凭空赋予供应商真实透明/蒙版能力。

预览和运行共用一套无副作用参数编译器：检查不可替代的必要能力 → 逐通道转换参数 → 校验转换后的请求和交付要求 → 报价并冻结合格候选 → 结合健康/容量调度 → 统一提交/查询/响应归一化 → 校验实际产物 → 保存与结算。保留用户原选参数、客户报价、实际上游参数和实际产物四类事实。

固定一家、主备、同层加权分流作为同一套绑定/调度的不同配置。优先级 1 与 2 不等于按权重一起分摊。供应商已受理或费用未知时只恢复/查询原任务；本地幂等 ID 不能使跨供应商 POST 自动具有幂等性。

## 改造顺序与验收边界

- **第一阶段：执行一致性。** 绑定级映射、公共展示规格独立、统一参数编译与响应归一化、旧配置兼容。集中验证共享上游的两个公共模型互不串改，单/多通道行为一致，元数据更新不改变已接受任务，不出现重复供应商 POST 或重复扣费。
- **第二阶段：运营可维护。** 后台集中到模型详情、供应商账户、能力资料/验收、发布记录；展示每条通道实际发送值、排除原因、证据来源与最近验收结果。补充关键能力的预算受控验收，避免高频全量收费探测。
- **第三阶段：企业治理。** 操作级权限、风险变更复核、影响范围预览、限量放量与配置恢复、成本未决对账、告警。若对外提供企业独立接入，另验收组织/项目隔离、企业预算和配额。
- 高可用和容量不能仅由此配置模块推断。需另按真实并发、任务时长、可接受失败率、恢复时间与恢复点目标验证；本轮不承诺特定用户规模或零故障。

不因本轮评估新增微服务、改语言或引入 Kubernetes。先在现有 TypeScript、PostgreSQL、Worker、Router/Hub 基础上收敛职责，旧任务按原版本完成；任何应用部署仍遵守当前蓝绿及发布收尾约定。
