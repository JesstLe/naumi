## 首个检查点

- **兼容团队读报表。** `teamSnapshot`、`teamContent` 和 `teamConversation` 原来在持有账户、团队或成员行锁时读账本、聚合作品、分页或拆对话 JSON。现在只读快照做统计，结束后用短事务按当前授权和成员范围复核并写同一个审计事件；快速单素材查询和命令写事务保持各自边界。
- **租户新建核对负责人。** 原来并发读取全量旧团队列表和最多 100 条租户搜索结果，客户端最后才按邮箱找负责人。现用 `GET /api/admin/tenants?ownerEmail=...` 按唯一邮箱读取旧团队及开通状态，原租户列表和写入时的版本、归属校验保持不变。
- **平台 BI 执行追踪。** 过去最多 100 个候选、每批 4 个，每批慢请求可等 4 秒；波次叠加会让一次读长期挂起，还会重复取 Router 配置。现在一次读取配置，整个外部查询阶段共用 5 秒预算，最多 4 个在途；保留已经返回的证据，没有取到的标为暂不可用。不会提交、继续或重试生成。

已验证：`verify-team-subaccounts.ts` 在真实 PostgreSQL 阻塞作品聚合时确认扣费账户可更新；阻塞期间撤权后旧结果被拒绝，成功时仅写一条原有审计；团队隔离、会话、账务边界通过。`verify-saas-tenants.ts` 覆盖无团队、旧团队、已开通、大小写归一、非法和匿名核对，原租户审批不变。`verify-bi-trace-deadline.ts` 覆盖 5 秒总预算、最多 4 个请求、取消、保留部分结果和不返回凭据。无迁移或服务器操作。

## 第二个检查点

- **企业工作流读代理。** 核对 24 个路由的 GET 代理；其中 17 处原来只有超时，未向上游传入浏览器取消信号。改为由请求断开或原超时先到者结束外部读取。JSON 读响应使用共享的 16 MiB 解码上限，超限或错误格式返回 502 并取消流；文件／压缩包仍流式传递，接受条件保持原样。提交中的写命令继续沿用原超时，不把浏览器取消误当事务未受理。
- **来源证据。** 工作流候选、关联作品／生成与账务证据通过原来的会取账户锁的授权事务读历史。改用企业模块既有的只读投影与短复核机制，保留员工可读本人、管理者按授权查看、实时撤权的边界；快速单素材读取及提交链路保持专用事务。批量读取关联证据时不在客户端取消后再发起下一条读取。
- **创作记录客户端。** 仅在浏览器标签从隐藏恢复时补查；普通窗口聚焦不重启历史与详情请求，已有在途请求不重复发出。错误重试区分列表和详情，退出会话仍会立即清除并中止两类请求。沿用完整历史与总数。

验证：`verify-workflow-read-safety.ts` 使用独立 PostgreSQL 和本机 HTTP 服务，12 个 JSON 入口及文件流通过；覆盖部分 JSON 后断开、超限（声明与分块）、错误 JSON、已提交写命令继续并回执、本人查询权限、阻塞报表期间账户可更新、实时报表权限撤销。现有 `verify-saas-creations.ts` 的跨租户、历史、素材与账务检查通过，`verify-admin-query-recheck.mjs` 的实际 React 浏览器回归 26 项通过。TypeScript 检查通过。无数据库迁移，未连接或发布 47。

全历史上次热缓存实验确认“只去掉总数”不减少候选数据读取。本轮查看索引发现正式记录已有租户、成员时间索引，而旧图像任务索引以邮箱和类型开头；未筛选全平台历史缺少能直接支撑同一排序的索引。下一批应在合成数据验证按来源的有界键集、子任务／已归档来源去重、同时间稳定顺序及旧页码兼容，避免先加生产索引再猜收益。

## 第三个检查点

- **通知与站点策略。** 新 `badge` 读操作按同一订单可见条件仅计未读，不加载通知列表、总数和订单标题。页面隐藏时环境轮询不发请求；已有在途合并，收件箱打开时跳过被动角标请求，切换团队取消旧请求。兼容旧 Web 和旧工作流服务：只对明确的“不认识查询参数”回退一次，随后该页使用原收件箱接口。站点策略同样只在可见时刷新，并合并短时间内的焦点与定时请求。
- **工作流目录。** 原实现按候选企业重复校验账号、站点、成员和发起人授权，并持有账户锁。改为只读的集合查询，一次取当前账号可见候选、发起人授权和岗位；沿用同一站点策略与发起人有效期规则，独立站仍限固定企业，进入具体工作区仍单独复核，不赋予新权限。
- **历史分页。** 同一快照的候选已经校验来源、租户、日期、状态和历史去重。旧来源仅按来源、记录 ID 和账户回填当前页，不再重复前述判断，保持旧页码、精确总数、历史去重和权限约定。

## 第六检查点：排期预览和逐入口盘点
