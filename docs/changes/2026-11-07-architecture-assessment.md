# 10 万用户架构评估（2026-11-07，架构调整暂缓）

## 决定

用户 2026-11-07 决定：**先做不改架构的优化，架构调整暂缓。**

本文只记录评估结论和待办，不授权任何部署形态的改动。“10 万活跃用户”仍是建设目标，没有经过验证（见 `docs/PRODUCT_READINESS_100K.md`）。

## 结论

不需要推倒重来，也不需要拆微服务。现有的“模块化单体（Next.js Web）+ 独立 Worker + Postgres”方向不变。

要改的是部署形态：从“一台机器全包、部分状态只在单个进程内”，改成“Web 可以多开、数据库独立、媒体走对象存储”。这需要几处有限的代码改造，单靠调参数做不到。

## 证据（2026-11-07 只读核查 47）

- **机器：** 4 核、7.2GB 内存。Web（限 2GB）、Worker（限 1GB）、Postgres、nginx、fleet 和参考工作台都在这一台上。
- **数据库：**
  - 用户 249 个，库大小 4.3GB；`max_connections=100`；没有装 pg_stat_statements。
  - `app_image_jobs` 一张表 2.2GB，平均每个用户约 9MB 的任务快照。照这个比例线性外推到 10 万用户约 0.9TB。
- **媒体：** 存在本机 `/opt/naumi-staging/data/media`，再异步同步到 NAS。
- **流量（11-06 全天）：**
  - 约 20 名企业用户产生约 98 万个请求，大部分是画布轮询，每个打开的画布每小时约 2000 个。轮询已在 `40631eef` 优化，未发布。
  - 所有 JSON 接口都不压缩：Next 只压缩页面 HTML；nginx 没开 `gzip_proxied`，`gzip_types` 也只有默认的 HTML。
- **只能单机运行的状态：** `garment3d`、`packaging3d`、`tryon` 三个接口把任务存在进程内存 `JOBS` 里；另有部分限流只存在内存中。

## 必须做的架构项（暂缓，按规模触发）

| # | 内容 | 原因 | 何时做 |
|---|---|---|---|
| A1 | 3D 服装 / 3D 包装 / 试穿的任务状态从进程内存挪到数据库 | Web 多开后，查询可能落到另一份进程，出现“任务不存在” | Web 多开前 |
| A2 | 数据库独立部署（单独主机或云数据库）+ 连接池（PgBouncer） | 现在和应用抢 CPU/内存；多开后连接数会超过 100 的上限 | 约 1–2 万用户，或 DB CPU 持续偏高时 |
| A3 | 媒体改为对象存储 + CDN | 本机磁盘不能多机共享，带宽也不够；新增媒体会到 TB 级 | 与 Web 多开同步 |
| A4 | 发版流程支持多份 Web | 现行规则和蓝绿脚本按“1 个 Web + 1 个 Worker”设计（AGENTS.md §7） | 与 Web 多开同步 |
| A5 | Web 多开 + 负载均衡；Worker 多开（已有租约机制） | 单进程扛不住高峰 | 约 1–2 万用户 |
| A6 | 数据库只读副本、按企业/用户限流、供应商配额、能推送的地方用推送替代轮询 | 10 万量级 | 约 10 万用户 |

估算口径（尚未校准，需压测）：

- 10 万活跃用户，高峰同时在线约 1–2 万。
- 优化前，每个打开的画布约 0.6 请求/秒，高峰要扛约 1 万请求/秒；轮询优化后估计降到约 1–2 千请求/秒。
