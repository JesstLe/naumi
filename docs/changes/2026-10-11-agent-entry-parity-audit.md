- 已刷新远端，`origin/main` 为 `4f251af53224aef11866b5835b52daa6b8ce037c`；任务分支包含上轮会话与创作工具覆盖修复，不等同于线上版本。

- 小球是画布侧边 Agent 的状态视图和入口，不是第三个独立 Agent。统一方案应该是一个核心、两个场景适配器、三个入口，而不是三套 Agent。

## 用户明确的会话边界（2026-10-11补充，优先于下文简写）

**功能实现收敛，会话管理与状态独立。共用代码不等于共用会话实例。**

- 工作台拥有独立的 sessionId、上下文/参考图、消息、历史列表、输入草稿、运行状态、事件流、取消控制器和恢复游标。
- 画布侧栏与小球是同一画布会话的两个入口；小球只订阅当前画布会话，不跟随工作台状态。不同画布项目继续隔离。
- 同一用户可以同时执行工作台和画布任务；任一入口的新建、改名、删除、插话、停止、切换/恢复历史，只影响其所属会话。请求限流和积分余额等明确的账号级资源不伪装成会话级资源。
- 统一 controller/hook 应当是可复用的工厂/实现，工作台和画布各自实例化。不能使用一份全局 activeSession、messages、busy、AbortController 或 SSE 订阅；session store 必须按账号、场景、项目和会话定位，旧ID的迁移仍保留命名空间隔离。
- 同表持久化不等于混合历史；工作台排除 `cv-`，画布校验项目范围。控制接口必须校验真实账号与目标会话。通用 `/api/agent` PATCH/DELETE 当前也供画布操作，因此不能直接禁止所有 `cv-` 请求；画布专用历史路由与工作台专用历史路由保持双向范围校验。
- 共享模型目录/功能开关是能力配置；会话选择的模型、图片、生成参数与冻结执行版本仍属各自会话。统一改造时不得因另一入口改选择而静默改动正在执行的会话。

当前客户端已分别持有工作台 `sessionIdRef/streamAbortRef` 和画布 `assistantSessionId/assistantController`；运行时按 `(email, sessionId)` 保存独立 Agent 实例。

核对发现工作台历史 GET/POST/PATCH 已拒绝 `cv-`，但 DELETE 缺少同一道入口检查。已在 `src/app/api/agent/session/route.ts` DELETE 补上拒绝逻辑；不改画布停止调用，不迁移/合并任何用户历史。

## 已确认的分叉/遗漏

### 1. 富文本只升级了画布

`src/components/canvas/assistant-richtext.tsx` 使用 Markdown、GFM 表格/列表和代码高亮。工作台 `src/components/home/workbench-client.tsx` 的 `renderContent` 仍按换行和少量图片/视频正则处理，其余直接输出文字；表格、代码块等没有同一富文本实现。

此外，工作台 pending 分支仅显示执行提示和插话/停止控件，没有渲染已经累积的 `m.content`，流式正文到结束才可见。画布会逐段展示正文。

### 2. 运行中插话只在工作台接线

工作台 `sendInterject` 调用 `/api/agent` PATCH；画布侧栏 textarea 在 busy 时禁用，仅提供停止，没有插话回调或输入。服务端 PATCH 已使用共用 runtime，问题在画布前端能力没有接入，小球因此也没有独立插话功能。

### 3. 结束状态和断流处理不统一

画布前端要求 `done.ok === true` 才标记完成；断流保留已有输出并提示查历史。画布服务器增加 `canvas_terminal`，历史给出 completed/stopped/failed，成功回复先等待持久化。

工作台把读流 EOF 当作结束，没有相同完成标记要求；`final` 由 `session.running` 定时判断，保存是 fire-and-forget；停止导致 AbortError 后也把最后回复替换为“执行失败”。工作台历史 GET 返回原始 session，没有画布相同的终态归一化。上述不同路径意味着新增恢复/停止修复需要分别维护，且源码已有不一致。

这里只确认代码路径和风险，未通过模拟断网/重启或真实浏览器证明每一种竞态已经发生。

### 4. 模型展示、请求用途和管理目录不一致

工作台使用 `<TextModelSelect compact />`，组件缺省 feature 是 `canvas.text-generate`；提交通过 `authHeader` 发送全局 `naumi:text-model`。服务器 `/api/agent` 使用 `agent.text`/`agent.vision` 模型绑定。

画布明确使用 feature=`canvas.assistant`，请求走功能模型/报价包装。因此工作台显示的模型目录与服务器执行用途不是同一契约；不能保证显示候选、实际执行默认和模型管理范围始终一致。`agent.text` 是 ModelBinding，不是现有业务 FeatureId，修复不能简单把它塞入 TextModelSelect；需要明确公共 Agent 目录/策略与绑定映射。

工作台 PUT 还在 managed runtime 初始化之前检查旧 `AGENT_API_KEY`/通用 settings key，画布没有这道旧门槛；仅配置新供应商通道时，工作台可能在已配置模型的情况下被这道门槛挡住。这是源码条件风险，未修改真实配置做验收。

### 5. 工具展示仍有手写小表

画布 SSE 的工具开始标签只手写了 7 个工具，其余退化为“执行工具”；恢复历史则直接使用 `step.tool`。工具后端虽已补齐，新增工具不必然获得正确中文进度名称。应从统一工具元数据获取标签，而不是每个入口维护映射。

### 6. 会话控制器与 SSE 解析各维护一份

工作台：`send/loadSession/pollRecoveredRun/stopRun`。
画布：`sendAssistantMessage/restoreAssistantConversation/stopAssistantTask`。
两份控制器独立解析事件、更新 busy、处理取消和历史恢复，未形成统一能力契约和入口一致性回归。上轮的工具集同名测试只证明工具注册一致，并未证明生命周期/UI 功能一致。

## 需要保留的合理场景差异

- 工作台是账号级会话；画布是项目级会话，保留 `cv-` 隔离，不混入跨项目历史。
- 画布携带节点/图片/比例/分辨率，生成结果自动挂画布；工作台输出保留送画布/下载等操作。
- 图片工具沿用实际功能的独立执行模型和计费，不把对话模型当生图模型。
- 不因统一管理而统一所有价格、请求限额或收费策略。
- `/api/canvas/assistant` 仍有 legacy 非 Agent 模式，但本次全局搜索只找到实际生产前端发送 `mode: "agent"`；不是当前侧栏正在走另一套工具的证据。

## 统一实施方案（主体重构尚未实施；上文入口隔离补丁已实施）

1. 服务端共享会话执行/取消/持久化/终态服务实现，统一 running/completed/stopped/failed 事件；每个会话使用独立实例和定向控制，路由承担认证、场景校验和适配，不存在账号级全局活动会话。
2. 客户端复用 Agent controller/hook 实现并分别实例化：SSE 解析、多轮、停止、插话、恢复、新建/改名/删除、断流提示和产物去重；工作台和画布的状态/订阅/取消句柄独立，两个 transport 适配器保留路由/项目差异。
3. 共用富文本输出、工具进度元数据与能力清单；画布/工作台提供媒体操作扩展，不丢失视频、图片预览、送画布和下载。
4. 共用 Agent 模型目录与展示/请求契约；场景差异显式配置，移除 managed 模式下错误的旧凭证门槛。
5. 小球继续只订阅画布 controller，不新增会话或工具调度器。
6. 模块完成后集中跑入口矩阵：无图对话、带图、多轮、历史 CRUD、恢复运行任务、插话、停止/错误/断流、Markdown、工具标签和收费幂等；添加功能时要求矩阵同步更新。
