# 图片路由可靠性与1000并发受理

## 目标与基线
- 用户要求内部配置/路由可靠，并明确至少支持1000人并发。区分1000在线、1000同时提交、1000同时调用供应商三种指标；本模块验证1000独立请求同时进入持久任务队列与有界调度，不把本地模拟供应商压测当47整站容量结论。
- 分支codex/image-routing-reliability-20261020，基线d64494d4，已含origin/main3f940b86及此前本线程修复。共享checkout18个未提交文件保持。
- 现阶段仅本地源码/隔离PG/回环HTTP，不发供应商请求，不改47配置，不合main不发布。

## 已发现的内部缺口
1. provider budget发布与每次claim都使用LEAST历史值，导致并发限额只降不升；冻结任务反向压低新额度。
2. durable任务无跨实例执行上限；即使限了供应商并发，已经加载的图片、等待定时器仍可无界堆积。
3. dueImageJobs每轮只取3条；逐个HTTP派发，一个异常可截断剩余派发。
4. 本地容量不足等待15秒后转换为429并走失败结算，未真正发送的请求被当生图失败。
5. executor在过滤供应通道前先读取第一个启用条目的凭据，能力不匹配的条目可阻断后面正常通道。复现用首通道只支持1张参考、请求2张、第二通道支持4张；无效disabled配置本来就会被发布校验拒绝，不作为该bug证据。

## 修复设计
- 当前发布配置按同账号别名聚合最小有效额度，允许上调；冻结任务只读取当前预算、保留冻结参数与费用。不拆同账号额度，不取消供应商限流。
- PostgreSQL按job kind串行claim+活跃lease计数，generate默认16，suite/aplus各4，imagegen编排16。各lane可服务端配置1..256。parent与child分lane防相互占满；任务入队不受活跃额度限制。
- 恢复扫描每lane按可用额度取最多32，按lane轮转；4路有界HTTP派发，单条故障保留任务不阻塞其他用户。
- 本地容量满用可信类型ImageOperationQueued传回原任务，数据库保留pending、下次扫描；没有供应商POST时才允许此转换。root与fan-out共享dispatch标记，一旦任意子图发生可能收费请求就失去整体重提资格。SDK cause链仅识别本地类型，不信供应商同名JSON。
- 只对可执行通道读取连接信息，取消无关首条目的预先凭据读取。
- 建立活动lease索引；不改价格、管理员参数映射、历史未知任务或账本。
- APIB在本地容量不足时撤销本次未发送的marker，原taskId/已发送状态保持原恢复语义；本地排队不记供应商健康失败。
- 前端新增queued阶段：显示「已排队」，不显示生成百分比；两个真实画布生成函数中持续收到排队回执会延长本轮等待期限，不因排队超过旧6分钟而误报失败。开始执行/保存继续原进度，已有结果/手动位置/草稿保持。
